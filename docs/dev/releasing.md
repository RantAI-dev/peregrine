# Releasing

Until 1.0: minor versions (`0.x.0`) may break the API, CLI or options; patch versions (`0.x.y`) do not.

## Versioning and the CHANGELOG

1. All crates share one version (`[workspace.package] version`); crates inherit it with
   `workspace = true`, so there is one place to bump. `Cargo.lock` is committed and must move with it.
2. `CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): every
   user-visible change lands under *Unreleased* in the PR that makes it, and the section moves under
   the new version with its date as part of the release.
3. Titles of PRs and squash commits use the conventional prefixes (`feat:`, `fix:`, `perf:`,
   `refactor:`, `docs:`, `test:`, `ci:`, `deps:`, `chore:`; `!` for breaking). The release notes are
   generated by GitHub from PR *labels* (`.github/release.yml`): label the PR `breaking`, `perf`,
   `models`, `formats`, `isa` or `bug` so its entry lands in the right category, and `skip-changelog`
   to leave it out.
4. Before 1.0 the crates are not published to crates.io (`publish = false`); a release is a tagged
   commit with binaries, not a registry publish.

## The release step

Work down the list; do not cut the tag until every line holds.

1. **CI green on `main`**, including the SDE jobs and the MSRV check.
2. **S0.5, the AVX2 host gate.** The AVX2-only host (H2, bluefin) runs the full test suite on the
   exact release candidate — the commit the tag will name:
   ```sh
   git fetch origin && git checkout <candidate> && cargo xtest
   ```
   GitHub's runners cover the lower tiers only under SDE emulation or with `PEREGRINE_ISA`; H2 runs
   every kernel tier's production code on real AVX2 silicon before each release.
3. **Real-model tests pass on H1 (AVX-512) and H2 (AVX-2)**, and the accuracy gate holds
   (`docs/dev/accuracy.md`, `docs/targets.md`).
4. **Move the CHANGELOG's *Unreleased* section** under the new version with the date, bump
   `[workspace.package] version`, commit (`chore: release vX.Y.Z`), open and merge that PR.
5. **Tag `vX.Y.Z` on `main`.** Pushing the tag runs `.github/workflows/release.yml`, which on each
   target runner (linux-x86_64, linux-aarch64, macos-aarch64, windows-x86_64) runs the full test
   suite in release mode, proves the run-time ISA dispatch, builds the archives
   (`scripts/release/build.sh`, and `scripts/release/build.ps1` on Windows), and uploads them to a
   GitHub release whose notes are generated from PR labels. Nothing else publishes. A manual start
   is a dry run and never publishes: it builds and uploads the archives as workflow artefacts only
   (the publish job is guarded on a tag push):
   ```sh
   gh workflow run release.yml --ref <branch> -f dry_run=true
   gh run watch <id>          # then download the artefacts and check their listing and SHA-256
   ```
6. **Check the release.** Download every archive, `sha256sum -c SHA256SUMS` (on Windows:
   `Get-FileHash <zip> -Algorithm SHA256` against the same file), run `./peregrine tier`
   (x86-64: an `x86_64-avx2*` tier from the baseline binary; aarch64: `aarch64`; macOS: an
   `aarch64-neon*` tier; Windows: `peregrine.exe tier`), then
   `peregrine inspect` a model and smoke-test `serve` (`docs/quickstart.md`):
   (a) run the first `hf:` command with a cold cache (an empty `PEREGRINE_CACHE_DIR`), so the
   download path is exercised; (b) leave `peregrine serve` up for at least 60 s and answer a chat
   request after that, so a lifetime tied to the drain timeout cannot ship again; (c) exercise
   `serve --background`, `status`, `stop`, then `status` again (it must report no managed server).
   On the macOS archive also check `codesign -dv` reports an ad-hoc signature and that
   `scripts/install.sh --version vX.Y.Z` installs and runs it (the installer refuses Intel Macs):
   `./peregrine tier` must print an `aarch64-neon*` tier and `peregrine run` on a synthetic model
   must answer. On Windows unzip the archive and run `peregrine.exe --version` and
   `peregrine.exe tier` from it, then run
   `powershell -File scripts/install.ps1 -Version vX.Y.Z -BaseUrl <dir with the zip> -InstallDir
   <temp>` and start the installed `peregrine.exe`: it must report the same version and tier. Also
   check the installer left the user `Path` alone apart from the new directory — it keeps
   `%VARIABLES%` and the value's `ExpandString` kind (CI tests this on every PR).
7. **Golden sweep.** Before the tag, prove each supported system's golden set is current by
   starting the **Record goldens** workflow on the candidate commit and expecting zero new files:
   ```sh
   gh workflow run record-goldens.yml --ref <candidate> -f runner=macos-15
   gh workflow run record-goldens.yml --ref <candidate> -f runner=windows-2025 -f isa=scalar
   gh workflow run record-goldens.yml --ref <candidate> -f runner=windows-2025 -f isa=avx2
   gh run watch <id> --exit-status   # then read each run's recorded.txt artefact
   ```
   Each run's verify step compares the committed values and fails on a mismatch, and its
   `goldens-<runner>-<isa>.tar.gz` must hold nothing: a file that appears is a golden the release
   would otherwise skip, so commit it by name (`docs/dev/testing.md`) before the tag. The Windows
   AVX-512 set is not part of the sweep — the pool draws it at random — and a missing one only
   makes that tier skip.


## What ships

- `install.sh`, the `curl | sh` installer, and `install.ps1`, the PowerShell installer, as release
  assets: `releases/latest/download/install.sh` and `/install.ps1` are what the vanity host
  redirects to.
- `peregrine-vX.Y.Z-linux-x86_64.tar.gz`, `peregrine-vX.Y.Z-linux-aarch64.tar.gz`,
  `peregrine-vX.Y.Z-macos-aarch64.tar.gz` and `peregrine-vX.Y.Z-windows-x86_64.zip`: the stripped
  `peregrine`/`peregrine.exe` binary, `LICENSE` and `NOTICE`, with a `SHA256SUMS` covering every
  archive.
- The x86-64 binary is built for the plain x86-64 baseline: no `RUSTFLAGS`, no `-C target-cpu=native`
  (the build script refuses `RUSTFLAGS`, and the workflow asserts the baseline binary still picks the
  AVX2 tier on an AVX2-only runner). AVX2, AVX-VNNI-256 and AVX-512 are chosen at run time by the
  kernel table; aarch64 ships the same way. One binary per architecture, portable down the ISA ladder.
- Binaries are built natively per target on the release runners (no cross-compilation). Build them
  with `--profile dist` (fat LTO, one codegen unit): same speed as `release` on the S3.9 A/B, 29%
  smaller. Published benchmark numbers stay on `release` (see [`build-profiles.md`](build-profiles.md)).
- The macOS archive targets macOS 11.0 (`MACOSX_DEPLOYMENT_TARGET`), is ad-hoc signed
  (`codesign --sign -`) and **not notarised**. `curl` sets no quarantine flag, so the installer's
  path runs; a browser download needs the `xattr -d com.apple.quarantine` line in
  `docs/quickstart.md`. Intel Macs have no archive: they build from source.
- The Windows archive is built with `-C target-feature=+crt-static`, so the `.exe` needs no Visual
  C++ redistributable. It is **unsigned**: there is no Authenticode certificate yet, so SmartScreen
  warns about a browser download; the installer's download path does not carry the zone identifier.
  Windows on ARM64 has no archive: it builds from source.
- **v0.2.0 shipped the two Linux archives only**; v0.3.0 is the first release with all four and
  both installers. `scripts/install.sh` still tells a Mac pointed at v0.2.0 or older that the
  release has no macOS archive.
- Container images are not in the first release (the Dockerfile ships first, an image publish comes
  with it).

## The vanity download host

The public front door is **`peregrine.rantai.dev`**, using the same Cloudflare pattern as
`get.rantai.dev/lakehouse`: the domain is a redirect with no origin, and the files stay on GitHub.
The release workflow uploads `install.sh` as an asset, so the newest script is always at
`releases/latest/download/install.sh`.

Configured once in the `rantai.dev` zone (public DNS, outside this repository):

1. a proxied `AAAA` record `peregrine` → `100::` (no origin);
2. in the `http_request_dynamic_redirect` phase, rules scoped to `http.host eq "peregrine.rantai.dev"`:
   - path `eq "/install.sh"` → `https://github.com/RantAI-dev/peregrine/releases/latest/download/install.sh`;
   - path `eq "/install.ps1"` → `https://github.com/RantAI-dev/peregrine/releases/latest/download/install.ps1`;
   - path `starts_with "/releases/"` → a **dynamic** target (`target_url.expression`, not
     `target_url.value`) =
     `concat("https://github.com/RantAI-dev/peregrine/releases/download/", substring(http.request.uri.path, 10))`;
   - path `eq "/latest"` → `https://api.github.com/repos/RantAI-dev/peregrine/releases/latest`.

**Not `get.peregrine.rantai.dev`.** The zone's certificate is `rantai.dev, *.rantai.dev` (Universal
SSL), which covers one label: `peregrine.rantai.dev` is covered, but `get.peregrine.rantai.dev` is not.
That nested host needs Total TLS / Advanced Certificate Manager first, or a path on the existing
covered host (`get.rantai.dev/peregrine`) instead. `peregrine upgrade` accepts either through
`PEREGRINE_RELEASE_BASE` / `PEREGRINE_RELEASE_LATEST`.

The installer asset is cached briefly at the edge; after replacing an `install.sh` on an **existing**
release, the clean URL can serve the old copy for a few minutes. New releases have no older copy.

`peregrine upgrade` prefers `https://peregrine.rantai.dev/releases/download` and falls back to the
GitHub base, so the domain can be added (or be down) without breaking updates. `PEREGRINE_RELEASE_BASE`
and `PEREGRINE_RELEASE_LATEST` override both, for a mirror or a test fixture. Until the DNS record and
rules exist, the GitHub URLs work unchanged.
