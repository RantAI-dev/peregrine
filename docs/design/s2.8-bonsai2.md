## 0. Summary

Bonsai 2 is a `qwen35` hybrid whose matmuls are **PQ2_0**: 128 ternary weights in 34 bytes,
with a 2-bit code and one fp16 scale per 128. Every matmul input is also rotated by a
block Hadamard transform with an explicit sign vector, and every fourth layer is a Gated
DeltaNet layer whose recurrent step and causal conv are serial per token. On aarch64 all
four ran the portable scalar paths, so the headline model decoded at 11 tok/s on this host
while the x86 build was several times faster than PrismML's fork.

This note records the four kernels that fix that, the bit-invariance argument that lets them
ship, and the measured result. The kernels are in `peregrine-kernels/src/neon.rs`
(PQ2_0), `hadamard.rs` (the transform and the sign multiply), and `delta.rs` (the recurrent
step and the conv's inner accumulate); the rotation and the recurrent loop in
`peregrine-core` only changed the call they make.

**The rule that shapes the design.** A row's bits must not depend on the batch width, the
chunk, the pass width, the thread count or speculation. That rules out the obvious
two-kernel split ("one kernel for decode, another for prefill") unless the two agree bit for
bit, so every PQ2_0 path here computes the same eight 16-value integer sums per group and
folds them into the same eight float lanes in the same group order. The tests assert
`to_bits()` equality between the one-row kernel, the two-row decode kernel and the
four-activation prefill kernel.

## 1. The format, and the mapping onto `sdot`

A PQ2_0 block is `f16 d; u8 qs[32]`. Element `j` is `((qs[j/4] >> 2(j%4)) & 3) − 1`
times `d`; the files are ternary, so the codes are 0, 1 and 2. The activation side is
`QuantAct`'s ternary layout: `tq` holds the signed int8 codes in natural order, `td` one
scale per 16 values, `tls` the code sum of each 16-value run, and `tp` the same codes
permuted so that bit-plane `s` of a group is 32 contiguous bytes
(`tp[tp_off(g) + 64s + k] = tq[128g + 4k + s]`).

The x86 kernels use that permutation because `VPDPBUSD` lane `j` sums four *bytes* of a
plane, i.e. activations `16j..16j+16` over the four planes. `sdot` has exactly the same
shape: sixteen signed bytes per operand, four int32 lanes of four products. So one group is
eight `sdot`s — four planes, each split into its two 16-byte halves — and lane `l` of the
result is the 16-value sum of block `8g + l` of the group. The codes are 0..3, which are
valid positive `int8`s, so `sdot` needs no unsigned variant and no bias: the activation's
`−Σq` offset is applied through `tls` in the float fold, exactly as the scalar reference
does.

```
for each group g:                       # 128 weights
    p[0..8] = planes(load qs)           # 4 shifts + 4 masks
    a[0..8] = activation planes         # 8 loads of 16 bytes
    lo = sdot(p0,a0) ⊕ sdot(p2,a2) ⊕ sdot(p4,a4) ⊕ sdot(p6,a6)
    hi = sdot(p1,a1) ⊕ sdot(p3,a3) ⊕ sdot(p5,a5) ⊕ sdot(p7,a7)
    facc[0] += d·td[8g+0..4]·(lo − tls[8g+0..4])
    facc[1] += d·td[8g+4..8]·(hi − tls[8g+4..8])
out = hsum(facc[0] + facc[1])
```

`facc` is two `float32x4` lanes per (row, activation) pair. The fold is **per lane**, not
one horizontal sum per group: the eight values of a group never form a dependency chain,
and the accumulators run across groups. That was worth 1.5× over the scalar fold in the
first version (which was a serial chain of eight `fma`s and capped the kernel at
13.4 GMAC/s).

**Decode (two rows per pass).** `dot_rows_pq2` with one activation loads the activation
planes once and runs both rows' `sdot`s against them. Two open weight streams is what this
host streams best, as on x86 (`tern.rs`'s `R`).

**Prefill (one row, four activations).** `dot_batch_pq2` decodes a row's planes once per
group and meets four activations with them; `dot_rows_pq2` calls it per row for a batch.
Four is the register budget: eight plane registers, eight activation registers, two integer
accumulators and eight float accumulators.

**Why not `i8mm` for the GEMM.** `smmla` computes a 2×2 int32 tile from two 2×8 int8
operands, so it is the natural GEMM instruction — the repacked k-quant tiles use it for
1.5–1.6× (`s2.8-neon.md`, F2). PQ2_0 has no repacked tile on aarch64: its codes are packed
2 bits deep and the plane layout that makes `sdot` need no shuffles is the *wrong* layout
for a 2×8 operand, so an `smmla` kernel must first expand each 32-byte group to 128
natural-order codes (`vzip` chains), then assemble the 8-byte halves of two rows and two
activations. A prototype (`usmmla`-equivalent `smmla`, 2 rows × 2 activations, per-16
fold) measured **42.7 GMAC/s at eight activations against the `sdot` GEMM's 30.1**
(1.42×), but only because the weight expansion is loop-invariant and hoists out of the
activation loop; at two activations it measured 14.1 against 25.7. It also folds the eight
blocks of a group *before* multiplying by the group scale, which is a different float
association from the `sdot` GEMV that decode uses — shipping it would make a row's bits
depend on whether the pass had one activation or two. Matching the fold costs more than the
1.42× buys, so the GEMM stays on `sdot` and the tier is `neon-dotprod`, not `neon-i8mm`,
for this format. The measurement is recorded in the results folder.

## 2. The Hadamard rotation

`Rotation::rotate_rows` applies the sign vector and then an unnormalised FWHT per block
(4096 for 9B, 1024 for 27B; 1024 for the 2B and 4B). The scalar FWHT is 12 passes of
add/subtract; `fwht_neon` does strides 1, 2, 4 and 8 in registers over sixteen floats
(`vrev64`/`vext`/`vtrn` and vector add/sub) and the wider strides with 4-float loads and
stores. Every element is the same `a+b`/`a−b` the scalar loop computes, so the result is
**bit-identical** to it; the test compares `to_bits()`. The sign multiply is a separate
four-lane multiply (`hadamard::mul_signs`), also exact.

The rotation is 5 % of prefill and 12 % of a decode step on the 2B — it is on the serial
path of every layer, and a 1024-wide block is small enough that the vector path matters.

## 3. The Gated DeltaNet step and the conv

`delta_head_neon` mirrors the AVX2 kernel: two `float32x4` accumulators over the state row
for `S·k`, then one pass that writes `e^g·S + δkᵀ` and takes `S·q` on the way. It needs
`dk % 8 == 0`; the hybrid's `dk` is 128. The state is per v-head and the heads are separate
tasks, so the vector width never depends on the batch: the test allows a small tolerance
against the scalar reference (as the AVX2 and AVX-512 tests do — the reduction order
differs) and asserts exact equality on zero inputs.

`causal_conv_row` is the conv's inner accumulate: `y = y·w_cur + Σ_t hist_t·w_t`, one
multiply and one add per tap, in tap order. That is elementwise, so the NEON path is
bit-identical to the scalar loop (tested). The core keeps the ring, the channel split and
the snapshot copy; only the arithmetic moved.

## 4. What changed in the engine

- `MatKernels::detect` on aarch64 sets `pq2_rows = have_dotprod()` (it was always false),
  so `MatPath::RowsPq2` selects `neon::dot_rows_pq2`. `kernels_for(PQ2_0)` lists
  `Scalar, NeonDotprod`.
- `neon::dot` and `neon::dot_batch` answer for PQ2_0, so the per-row fallbacks are fast too.
- `fwht` and the sign multiply dispatch to NEON under `have_neon()`; `delta::tier()` grew a
  `Neon` rung and `delta_head` uses it when `dk % 8 == 0`.
- `recurrent::causal_conv` calls the kernel instead of its own scalar loop.

## 5. Invariance

| path | kernel | same bits as |
|---|---|---|
| decode, one activation | `pq2_two_rows` | `dot_pq2` (one row) |
| decode, odd row tail | `dot_pq2` | itself |
| prefill, 1–4 activations | `pq2_batch::<T>` | `dot_pq2` |
| prefill, any chunk | `dot_rows_pq2` → `pq2_batch` | `dot_pq2` |
| any thread count | rows split by index | a row's value does not read the split |

The unit tests assert the bit equality for 1..11 rows, one and four activations, and the
engine's own `bonsai.rs` test asserts that MTP speculation (draft + verify) changes no token
of the 4B file. The synthetic `batching_is_invariant_across_slots` test covers the same
property through the serving engine.

## 6. Measured result

See `benchmarks/results/spark-arm-2026-11-10-bonsai2/README.md` for the tables, the rounds,
the PrismML build and the shared-host note. In one line: on the 2B, prefill 14.8 → 404 tok/s
and decode 11.0 → 140 tok/s at ten X925 cores, against PrismML's 168 / 89 tok/s on the same
file, threads and requests; on the 4B with MTP, decode 64.8 → 80.7 tok/s.
