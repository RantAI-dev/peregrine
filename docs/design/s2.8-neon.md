## 0. Summary

The first release is x86-first (decision of 2026-11-09), so ARM does **not** gate it. It does,
however, run today with no vector kernel at all: `cpu::detected()` returns `Scalar` on every
non-x86 target, `simd.rs` and `kqsimd.rs` are `#![cfg(target_arch = "x86_64")]`, and a decode step
on a 1B model costs an order of magnitude more CPU than it needs to. This note specifies the ARM
tier that fixes that, and the rules it must obey so that the tier can be added without moving a
single token on x86.

The proposal in one paragraph: add two aarch64 tiers (`neon`, `neon-dotprod`) to the existing
`Tier` ladder, detect them at run time with `is_aarch64_feature_detected!` under the same
`PEREGRINE_ISA` cap every x86 tier already honours, and put the kernels in one new module
(`peregrine-kernels/src/neon.rs`) beside the scalar references, exactly as `simd.rs` sits beside
`quant.rs`. The first kernels are Q8_0 and Q4_K: a 16-byte `sdot` dot product, an eight-row GEMV
for decode, and the eight-row repacked tile GEMM/GEMV of S3.4 for prefill. All of them compute the
same integers as the existing kernels in the same order, so a row's bits are a function of its
weights and its activation alone — never of batch width, chunk, pass width, thread count or
speculation.

Decisions are numbered in §10; the ones that constrain the code are:

1. **Two tiers now, two named for later.** `neon` (asimd only) and `neon-dotprod`
   (`asimddp`/`sdot`). `neon-i8mm` and `neon-sve2` are in the ladder's design but not in the
   `Tier` enum yet, because neither has a kernel that earns it (§2.4).
2. **Integer dot products, folded exactly like the existing tiers.** `sdot` accumulates int32,
   which is exact; the fold (`d·S − dmin·M`, then `·dk`) keeps the operand order and the rounding
   of the path it replaces. Q8_0 and the per-row Q4_K kernel are therefore **bit-identical to
   their scalar references**, and the repacked Q4_K tile kernel is bit-identical to the AVX2 tile
   kernel (both reduce `S`/`M` in int32 and fold with the same `mul_add` chain).
3. **The kernel table stays the only dispatcher.** `MatKernels::detect` learns about aarch64; no
   model, block or scheduler code gains an `is_aarch64` branch.
4. **Goldens are per tier, as today.** The new tier names are `aarch64-neon` and
   `aarch64-neon-dotprod`; `aarch64` stays the scalar directory. Synthetic goldens are recorded
   for every tier that has a host, real-model goldens for the two models this host can hold.

Step 2 (PR `neon-2`) implements Q8_0 and Q4_K and the measurements of §8. Everything else in the
format order of §3 is follow-up work, listed with its estimate in §8.

## 1. What "fast on this machine" means

The measurement host is a DGX Spark (Lenovo ThinkStation PGX): 20 aarch64 cores in two clusters,
10 × Cortex-X925 (max 3.9 GHz, CPUs 5-9 and 15-19) and 10 × Cortex-A725 (max 2.8 GHz, CPUs 0-4 and
10-14), 121 GB of unified LPDDR5X, and `asimd`, `asimddp`, `i8mm`, `sve`, `sve2` and `bf16` in
`/proc/cpuinfo`. There is one NUMA node; the clusters differ in IPC and clock, not in memory
distance.

Three properties of the workload decide the kernel shapes:

* **Decode is bandwidth-bound.** A token reads every weight once. At 121 GB/s-class bandwidth and
  0.5–1.0 GB of Q4_K_M weights, a token costs tens of milliseconds of streaming no matter what the
  arithmetic does; the kernel's job is to not add compute on top.
* **Prefill is compute-bound.** The same bytes are reused across the prompt's activation rows, so
  what matters is int8 MAC per cycle per core, not bytes.
* **The cores are heterogeneous.** A thread pool of 20 spreads a matmul over ten fast and ten slow
  cores; the slow half sets the barrier. This is a scheduling question (`PEREGRINE_DYNAMIC`, worker
  layout), not a kernel question, but it is why the benchmark plan measures 10-thread X925-only and
  20-thread mixed runs separately (§8).

`docs/design/s3.4.md` §2.5 fixed the instruction budget picture on x86: one `vpmaddubsw` covers 32
byte-MACs and the kernel is limited by what surrounds it. On ARM the analogous instruction is
`sdot` (`vdotq_s32`, `asimddp`): 16 signed bytes × 16 signed bytes, four int32 lanes, one cycle
throughput on the X925's vector pipes. There is no `vpmaddubsw` saturation question — `sdot`
accumulates into int32 and cannot overflow for any format here (the widest term is
`63 · 127 · 32 = 256 032` per super-block sub-run, four orders below 2³¹) — so the ARM kernel gets
the AVX-512 kernel's freedom without its width.

## 2. Tiers, detection and forcing

### 2.1 The ladder

`cpu::Tier` gains two variants after the x86 ladder:

```text
Scalar < Avx2 < AvxVnni < Avx512 < Neon < NeonDotprod
```

Ordering is the cap's only job: `resolved_under(isa)` is `detected().min(isa.unwrap_or(top))`.
`top()` becomes `NeonDotprod`, so an x86 host (whose detection tops out at `Avx512`) and an ARM
host (whose detection tops out at `NeonDotprod`) both resolve correctly under the same "no cap"
default. `PEREGRINE_ISA` accepts the new names; forcing `scalar` on ARM turns every kernel off
exactly as it does on x86, which is what makes the scalar reference measurable on this host.

| Tier | Needs | Kernels |
|---|---|---|
| `scalar` | nothing | `quant.rs` references |
| `neon` | `asimd` | the scalar reference: no dedicated kernel yet (F1b) |
| `neon-dotprod` | `asimd` + `asimddp` | `sdot` byte dots, the fast path |
| `neon-i8mm` (later) | + `i8mm` | 8×8 `smmla`/`usmmla` tile GEMM |
| `neon-sve2` (later) | + `sve2` | vector-length-agnostic Q4_K/Q8_0 |

### 2.2 Detection

`cpu::detected()` gets an `aarch64` branch:

```rust
if std::arch::is_aarch64_feature_detected!("neon") {
    if std::arch::is_aarch64_feature_detected!("dotprod") { Tier::NeonDotprod } else { Tier::Neon }
} else { Tier::Scalar }
```

and `cpu.rs` grows `have_neon()` / `have_dotprod()`, cached in `OnceLock`s and gated on
`cpu::allowed("neon"|"dotprod")`. The kernels ask `crate::cpu::have_dotprod()`, the same cached
answer the x86 kernels get from `simd::have_batched()`. Hot paths ask those, never `is_aarch64_feature_detected!` per
row — the same rule the x86 kernels already follow.

`cpu_has!` stays x86-only (`is_x86_feature_detected!` does not exist on aarch64); the ARM checks
are plain functions in `cpu.rs`. `tier_of` learns `"neon"` and `"dotprod"`; unknown features keep
mapping to `top()`, so a `PEREGRINE_ISA` cap can never let a feature through by accident.

### 2.3 Tier names and `PEREGRINE_ISA`

`cpu::tier_name()` on aarch64 returns:

| CPU / cap | name |
|---|---|
| no `asimd` (or `PEREGRINE_ISA=scalar`) | `aarch64` |
| `asimd`, no `asimddp` (or cap `neon`) | `aarch64-neon` (scalar kernels) |
| `asimd` + `asimddp` (or cap `neon-dotprod`) | `aarch64-neon-dotprod` |

The names are golden directory names, so they follow the x86 convention (`x86_64-avx2`, ...) and
contain no host, user or model information.

### 2.4 Why `neon-i8mm` is not a tier yet

The host has `i8mm`, and the obvious question is why the tier name does not say so. Because no
kernel in step 2 would use it: `smmla`/`usmmla` multiply 8×8 int8 tiles into int32, which beats
`sdot` only when *both* operands are matrices. Q8_0's and Q4_K's dot products have one vector
operand, so `sdot` is the right instruction and `i8mm` changes nothing. A tier that reports
`i8mm` while running `dotprod` code would make golden names and `peregrine tier` lie about which
kernel ran.

The honest rung is the 8×8 repacked GEMM (`usmmla` over the Q4_K tile: unsigned 0..15 codes by
signed activations is exactly what `usmmla` takes), and that is follow-up F2 in §8. Until it
lands, an `i8mm` CPU reports `aarch64-neon-dotprod`. `sve2` is later for a different reason: the
kernels would be vector-length-agnostic rewrites, and the host's SVE width does not change the
roofline enough to justify carrying two shapes in the first release.

## 3. Format order

The order is set by the weight bytes of the gate models, not by format size:

| # | Format | Why this position | Step |
|---|---|---|---|
| 1 | **Q4_K** | 74 % of a Q4_K_M file's matmul bytes; the repacked tile of S3.4 is already specified and tested | 2 |
| 2 | **Q5_0** | the legacy small-model format; needs the tile GEMV/GEMM and one nibble+bit expansion | F1 |
| 3 | **Q8_0** | embeddings, the output head of several families, and the tokenizer fixtures; a single `sdot` per 16 weights | 2 |
| 4 | **Q6_K** | 14 % of a Q4_K_M file's bytes; the tile exists (`Q6K8`) but has no kernel on any tier yet | F3 |
| 5 | **PQ2_0** (Bonsai) | ternary; needs the tile-mode activation layout and `sdot` over packed trits | F4 |
| 6 | **F16 attention / F16, BF16 weights** | attention K/V already reads F16 directly (S3.6); the weight dots are float, not int8 | F5 |

Q8_0 before Q5_0 in the *implementation* order (step 2) even though Q5_0 is the more valuable
legacy format: Q8_0 is the format whose kernel is small enough to pin the whole NEON scaffolding
(dispatch, tier, tests, goldens) with the least risk, and every line of it is reused by Q5_0. In
the event step 2 shipped Q4_K and Q8_0 and left Q5_0 to F1, which is why the Qwen 0.5B file (44 %
Q5_0 by bytes) still runs those matrices on the scalar reference (§11).

Q4_K and Q8_0 in step 2 cover Qwen2.5-0.5B and Llama-3.2-1B Q4_K_M's matmul almost completely:
the remainder is Q6_K, which keeps the scalar reference and is measured as the control.

## 4. Kernel shapes

### 4.1 Q8_0: a signed byte dot per 16 weights

A Q8_0 block is 34 bytes: one f16 scale and 32 signed codes. The activation block is 32 int8
codes. `sdot` takes both operands signed, which is exactly the format, so the whole block is two
`sdot`s (weights `[0..16)` and `[16..32)` against the two activation halves), a lane sum, and

```text
acc += (w.d · a.d[b]) · s          // the scalar reference's expression, same order
```

The `s` is an exact int32. The expression is the same real number with the same rounding as
`dot_scalar`'s `acc += h(blk,0) * a.d[b] * s as f32`, so the kernel is **bit-identical to the
reference** — no tolerance, and the test asserts `to_bits()` equality.

Three shapes are built on that block:

* `dot_q8_0(w, a)` — one row, one activation (the dispatch behind `quant::dot`, the tail rows of
  a non-repacked matrix, and `PEREGRINE_ISA` comparisons);
* `q8_0_rows8(w, rb, a, out)` — eight rows, one activation (decode): the activation block is
  loaded once per block and reused for eight rows, and each row's block loop is the one-row loop;
* `q8_0_batch::<4>(w, acts, out)` — one row, four activations (prefill): the weight block is loaded
  once and multiplied against four activation blocks.

Both wide shapes call the same `fold` as the one-row kernel, so `dot_batch` at every width is
bit-identical to width one — the contract `a_row_is_bit_identical_across_batch_widths` pins.

### 4.2 Q4_K: two nibble halves per load

A Q4_K super-block is 144 bytes: `d`, `dmin` (f16), twelve bytes of packed 6-bit scales and mins,
and 128 bytes of nibbles. Sub-block `j` is 32 weights; `j` even reads the low nibble of bytes
`32·(j/2)..+32`, `j` odd the high nibble of the same bytes. The per-row scalar reference
(`quant.rs`, `dot_scalar` Q4_K) computes

```text
sumi = Σ_j sc_j · (Σ_l code_jl · q_{32j+l})       (int32)
summ = Σ_j m_j  · (bsums[2j] + bsums[2j+1])       (int32)
acc += dk_sb · (d · sumi − dmin · summ)           (one float fold per super-block)
```

The NEON kernel keeps both integer sums exact (four `sdot`s per sub-block per row) and the exact
float expression, in the same order, so the kernel is **bit-identical to the scalar reference**.
That matters twice: it is the A4 contract, and it keeps the non-repacked prefill path
(`PEREGRINE_KREPACK=0`, the A/B control) and the scalar tier comparable token for token.

The one structural trick worth recording: a 16-byte load of the tile's `qs` holds **two rows ×
eight bytes** (the tile interleaves eight rows, `kq.rs` §The Q4_K tile). `sdot` on that vector
against `[a_{8w..8w+8}, a_{8w..8w+8}]` (the same eight activations in both halves) puts row `r`'s
sum in lanes 0–1 and row `r+1`'s in lanes 2–3. One load therefore serves two rows, and — because
the low and high nibbles of the same byte are sub-blocks `j` and `j+1` — one load also serves two
sub-blocks. The kernel processes sub-block *pairs*, four loads and four masks/shifts feeding eight
`sdot`s for 2 rows × 64 weights. The expanded codes are never materialised, so the tile stays the
file's own 1152 bytes (S3.4 decision 9's size-neutrality).

### 4.3 Repacked Q4_K: GEMV and GEMM over `Q4K8`

The tile layout, the activation interleave (`KqActs`) and the fold are S3.4's; only the
instruction sequence is new. The two paths are:

* **GEMM** (width ≥ 4): groups of four activation rows from `KqActs`, eight output rows per tile;
* **GEMV** (width 1–3): the same tile, one activation row from `QuantAct` at a time, broadcast
  across the eight output rows.

They must agree bit for bit (S3.4 §4.4), and they do because both compute

```text
value = Σ_sb dk[sb] · ( d[sb] · S − dmin[sb] · M )        S, M exact int32
```

with the same `mul_add` chain in the same super-block order. The NEON kernels reproduce
`kq.rs`'s `dot_q4k8_ref` exactly, so a tile computed on this host and the same tile computed on an
AVX2 host agree to the bit too — the cross-tier check that the golden files make possible.

### 4.4 Activation quantisation and the rest of the forward pass

Step 2 does **not** vectorise `QuantAct::fill` (the activation absmax and int8 rounding), `vmath`
(softmax, rope, SwiGLU), or attention. Those are scalar on aarch64 today, and they cap the
end-to-end gain. The micro-benchmark isolates the kernel; the engine A/B in §8 reports the whole
step with the phases' share, and §8's follow-ups name the two that matter most for prefill
(activation quantisation, ~9 % on x86 and a larger share on ARM because it stayed scalar).

## 5. Batch invariance

The invariant is `ARCHITECTURE.md` invariants 1 and the synthetic test
`batching_is_invariant_across_slots`: for a fixed seed, a user's tokens must not depend on batch
size, on other users, on speculation, or on the kernel tier. On one tier it has to hold at the
arithmetic level:

> **A row's bits are a function of its weight bytes and its activation bytes only.**
> Not of the batch width, the prefill chunk, the pass width, the thread that ran it, or whether
> a draft was speculated before it.

The NEON kernels satisfy it for four separate reasons, and each is a test:

1. **Integers are exact.** `sdot` accumulates int32 and wraps only far outside any value these
   formats produce (the bound in §4.2 is 2 048 256 for the largest min term and 256 032 for a
   sub-run sum; both are four orders below 2³¹). The integer sums `S` and `M` are the same
   integers whatever order the lanes were added in.
2. **The float fold has a fixed order.** One fold per super-block, super-blocks in index order,
   with the exact operand order of the reference it replaces. No reassociation, no `fast-math`,
   no FMA contraction that the reference does not also perform. (Q4_K's per-row kernel uses the
   reference's plain `mul`/`sub`; the tile kernel uses the tile reference's `mul_add` chain. Each
   matches its own reference.)
3. **GEMV equals GEMM per row.** Both tile paths compute the expression above with the same
   operands in the same order; the tests below compare them at every width from 1 to 8.
4. **Rows are partitioned, never reduced.** The pool splits output rows between threads; no
   kernel sums across threads. A row's result is independent of the thread count by construction,
   which the existing thread-count golden test re-checks on this tier.

The tests that pin it:

| test | pins |
|---|---|
| `neon::tests::q8_0_matches_the_scalar_reference_bit_for_bit` | kernel ≡ `dot_scalar` on seeded random blocks, `to_bits()` |
| `neon::tests::q4_k_matches_the_scalar_reference_bit_for_bit` | same for Q4_K |
| `neon::tests::q4k8_gemv_and_gemm_agree_at_every_width` | tile GEMV (1–3) ≡ tile GEMM (4–8) ≡ `kq::dot_q4k8_ref` |
| `neon::tests::q8_0_batch_is_bit_identical_at_every_width` | batched Q8_0 (1–4, 8, 16) ≡ width one |
| `core::tests::simd::a_row_is_bit_identical_across_batch_widths` (extended to ARM) | the dispatch layer's contract |
| `models::tests::golden` (thread-count half) | thread count does not move a logit |

## 6. Golden outputs

Goldens are stored per tier name (`tests/golden/<tier>/`, `tests/golden/synthetic/<tier>/`), and
`PEREGRINE_GOLDEN=require` fails a present model that has no golden for the tier. The new
directories are:

| directory | recorded on | contents |
|---|---|---|
| `aarch64` | ARM host with `PEREGRINE_ISA=scalar` | the scalar reference; also what an ARM run without `asimd` uses |
| `aarch64-neon` | ARM host with `PEREGRINE_ISA=neon` | the `vmull` kernels |
| `aarch64-neon-dotprod` | this host, native | the shipping ARM tier |

Recording is `PEREGRINE_GOLDEN=record cargo test --release --test golden` and `... --test
synthetic`, per tier, on the host that has it — the rule S3.4 §4.3 already set. The real-model
goldens this host records are the two files in `docs/dev/testing.md` that fit in `/var/tmp/pg/models`
(Llama-3.2-1B-Instruct Q4_K_M, Qwen2.5-0.5B-Instruct Q4_K_M, both SHA-256-checked); the rest stay
unrecorded, and `require` skips them because the files are absent.

Two properties of the ARM goldens are worth stating before they are recorded:

* `aarch64-neon-dotprod` is **not** expected to equal `x86_64-avx2` on Q6_K, F16/BF16 or the
  ternary formats, because those kernels do not exist on ARM yet and the scalar reference runs
  instead. It *is* expected to equal `x86_64-avx2` on Q8_0 rows and on Q4_K tile rows, since both
  reduce the same integers and fold them the same way. Where it does not, the diff is a finding,
  not a re-record.
* The scalar directory (`aarch64`) is recorded **after** the kernels land, because step 2's
  dispatch changes which kernel a scalar-cap run selects (it still selects the scalar reference;
  the recording just proves it).

### 7.1 What is being compared

| arm | what runs | why |

| `PEREGRINE_ISA=neon` | `vmull`/`vpadal` kernels | the no-`dotprod` tier |

| `llama.cpp` `0c6dca2` | its NEON repack kernels | the external reference |

| model | bytes | role |
|---|---|---|
| `Llama-3.2-1B-Instruct-Q4_K_M.gguf` | 807 694 464 | the 1B gate model, Q4_K + Q6_K |
| `Qwen2.5-0.5B-Instruct-Q4_K_M.gguf` | 397 808 192 | the small model, prefill-heavy |

### 7.2 Protocol

`peregrine bench --model <file> --prompt-tokens 512 --tokens <n>` on the release profile, three
rounds per arm, arms **interleaved by round** (scalar, neon, native, llama, repeat) so a thermal or
co-tenant drift hits every arm. The median of the three is reported, and the spread as well; a
difference smaller than the spread is reported as "flat".

Threads: the pool width is `SessionCfg::threads` (default `available_parallelism`), and a
one-row step uses `PEREGRINE_DECODE_THREADS` when it is set. `taskset` restricts both, so the runs
are

| threads | affinity | what it isolates |
|---|---|---|
| 20 | all | what a user gets |
| 10 | `taskset -c 5-9,15-19` (X925 only) | per-core kernel speed on the fast cluster |
| 10 | `taskset -c 0-4,10-14` (A725 only) | the slow cluster, and the mixed-pool barrier cost |

The X925/A725 split is reported as `X925 tok/s ÷ A725 tok/s` per arm. It is a property of the
cores (IPC and 3.9 vs 2.8 GHz), not of the kernel, but it explains why a 20-thread run is not 2×
a 10-thread X925 run and why a later scheduling change (not this PR) is worth measuring.

llama.cpp side: `llama-bench -m <file> -t <threads> -p 512 -n 128 -r 3` for the same three
affinities, taking the faster of `-fa auto` and `-fa 0` per metric (as S3.4 §12.3 did). CPU-only:
`GGML_CUDA_DISABLE=1` / `-ngl 0`, because the comparison is the CPU kernel.

Reported columns: prompt tok/s, decode tok/s, and the ratio to scalar. The claim this PR makes is
**NEON vs scalar on this host**, with llama.cpp as context. A number below llama.cpp's is not a
regression: it is the gap the follow-ups in §8 close.

### 7.3 Micro-benchmarks

`cargo run --release -p peregrine-bench --example neonbench` (this PR: the Q8_0 and Q4_K per-row
kernels, the eight-row Q8_0 decode kernel, the four-row Q8_0 batch, and the Q4_K tile GEMV and
GEMM, each beside its scalar reference) and `kbench` (the portable per-format harness, which builds
and runs on aarch64 unchanged) give per-kernel GMAC/s, which is where a kernel bug and a kernel
speed-up are distinguishable. `kqbench` imports `kqsimd` directly and stays x86-only.

## 9. Open questions

1. **Q6_K on ARM.** It is 14 % of the 1B model's matmul bytes. Leaving it scalar is a real cost
   (the §8 measurement will show it), but a Q6_K `sdot` kernel needs the int16/int32 bound worked
   out from scratch — `sdot` is int32 so there is no bound problem, only the 6-bit unpack (four
   `sdot`s per 16 weights after a `ushr`/`and` pair). F3 is cheap; the question is whether it
   belongs in the first ARM release or in the follow-up wave.
2. **Mixed X925/A725 scheduling.** A 20-thread matmul waits for the A725 half. Fixing it means
   weighting the partition by core class, which the pool does not model yet (S3.5/S3.6 territory).
   Out of scope here; §7.2 measures the size of the prize.
3. **`PEREGRINE_ISA` on ARM and the scalar goldens.** Recording `aarch64` requires a
   `PEREGRINE_ISA=scalar` run on this host; CI's aarch64 job has no model files and no goldens, so
   nothing in CI depends on those files existing. They are recorded for parity with x86, not for CI.
4. **`kernels_for` and the README support table.** The table prints tiers per format; after this PR
   the Q4_K/Q8_0 rows gain `neon`/`neon-dotprod` on ARM builds only. The table is generated from
   `kernels_for`, which is a compile-time list, so the ARM entries must be `cfg`'d rather than
   unconditional — verified in step 2.

## 10. Decisions

1. Two tiers in the enum (`Neon`, `NeonDotprod`); `i8mm`/`SVE2` documented, not named, until a
   kernel uses them (§2.4).
2. `Tier::top()` replaces the hard-coded `Avx512` as the no-cap default; the x86 ladder and every
   x86 name are unchanged.
3. Integer-exact kernels with the reference's fold order; bit-identity is tested, not assumed (§5).
4. Goldens per tier, recorded on the host that has the tier; `aarch64-neon-dotprod` is compared
   against `x86_64-avx2` for Q8_0/Q4_K rows before it is recorded (§6).
5. Step 2 ships Q4_K and Q8_0 only, with measurements; the format order and estimates are §3/§8.
6. No change to `peregrine-core` beyond what the kernel table needs; ARM branches do not appear in
   model or scheduler code.

## 11. What landed (2026-11-09)

The two PRs this note covers are `neon-1` (this note) and `neon-2` (the kernels). The
implementation follows §2–§6 with three differences, each found while building it:

1. **`neon` runs the scalar reference, not `vmull` kernels.** The `Tier` rung exists (detection,
   `PEREGRINE_ISA`, tier name) but the plain-asimd kernels are F1b: every ARM CPU that matters for
   this engine has `asimddp`, and a second instruction shape for the `vmull`/`vpadal` sequence
   would double the tile kernel for no measured host. An `asimd`-only CPU therefore reports
   `aarch64-neon` and runs `quant.rs`, which is the same thing `scalar` runs.
2. **The Q4_K tile GEMM walks the batch in groups of four** (`const N: usize` × 4) and the GEMV
   one activation row at a time, exactly the shapes §4.3 describes. Four activation rows is what
   fits the 32 vector registers beside the eight row-pair accumulators; a wider group is the
   follow-up that shares the tile across more rows, and the micro-benchmark (§11.2) says the
   instruction rate is already at the useful bound for this shape.
3. **`pool::physical_cores()` falls back to `available_parallelism()`.** Linux/aarch64 does not
   print `physical id`/`core id` in `/proc/cpuinfo`, so the engine's default decode pool was one
   thread on this host. The fallback is a no-op on x86 (the two fields are there) and honours a
   `taskset` mask, which the affinity runs in §11.2 need.

### 11.1 Verification

* `q8_0_matches_the_scalar_reference_bit_for_bit`, `q4_k_matches_the_scalar_reference_bit_for_bit`,
  `q8_0_batch_is_bit_identical_at_every_width`,
  `q4k8_gemv_and_gemm_agree_with_the_reference_at_every_width`: `to_bits()` equality on seeded
  random data, widths from 1 to 8, at every batch shape.
* With `PEREGRINE_KREPACK=0` the NEON tier reproduces the scalar reference **bit for bit** on both
  real gate models (Llama-3.2-1B Q4_K_M, Qwen2.5-0.5B Q4_K_M): every Q8_0 row and every per-row
  Q4_K row is the reference's own bits, and nothing else in the forward pass differs across
  architectures.
* `aarch64` (scalar) goldens equal `x86_64` (scalar) goldens **bit for bit** on all 51 synthetic
  models and both real models. `aarch64-neon-dotprod` equals `x86_64-avx2` on the models whose
  formats the tier covers end to end (for example the Q4_K-only synthetic model); where it does
  not, the difference is the formats that still run the scalar reference on ARM (F16/BF16 weight
  dots, Q6_K, the ternary formats), not a NEON fold. The tier is still the x86 tiers' output on
  new silicon for every kernel it ships; the remaining gaps close with F3/F4/F5.
* After #122 landed, the repacked Q8_0 tile is part of this tier too: the aarch64 kernel reads the
  same `Q8_08` tiles with `sdot` and applies the tile reference's fold, so the Q8_0 models move
  exactly as they did on x86 (logits change, tokens almost never). The scalar tier and
  `PEREGRINE_ISA=neon` (no `sdot`, so no tile kernel) are untouched.
* The two stored `x86_64-avx2` real-model goldens (Llama-3.2-1B, Qwen2.5-0.5B) differ from this
  tier's output in the last bits: the prompt argmax agrees at all 29 positions and the greedy
  stream diverges after 16 tokens. Both were last touched in #109, before the S3.4/S3.5 kernel
  PRs that followed, so staleness of those two files is the likely explanation (they are not on
  the H2 golden host's model list, so nothing re-records them). Flagged for the AVX2 host to
  re-record or confirm; not a NEON finding, and not something this PR can settle without an x86
  machine.

### 11.3 What is next

F1 (Q5_0) moves the Qwen family, F3 (Q6_K) the Llama family's other 42 %, and F5/F6 (attention,
`exp`, activation quantisation) move every model: the tile GEMM reaches 78 GMAC/s per core while
the engine's prefill reaches roughly a fifth of the aggregate that 20 such cores imply.
