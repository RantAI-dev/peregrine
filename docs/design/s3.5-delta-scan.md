# Chunked Gated DeltaNet scan for Bonsai 2 prefill (S3.5, design note)

Design only, no code. The question this note answers: does Bonsai 2's recurrent share make the
Gated DeltaNet (GDN) scan worth chunking during prompt processing, the way S3.5 proposed? The
answer from the profile is **not yet**: it is 3.0-3.4 % of the prefill wall, against ~90 % in the
PQ2_0 matmuls. The chunked scan is recorded here as a deferred option with the fold it changes.

## What the profile says

`PEREGRINE_PROF=1`, `peregrine bench --prompt-tokens 512|4096 --tokens 1`, bluefin (Zen 2, four
physical cores), the same tree this note lands on. `gdn_delta` is the scan; the other buckets are
the rest of the hybrid pass (matrix products, attention, rotation, conv, norms). The share is the
bucket over the sum of the per-token buckets, i.e. the prefill wall.

| model | prompt | gdn_delta µs/token | matmul µs/token | scan share of prefill |
|---|---:|---:|---:|---:|
| Bonsai 2 2B | 512 | 215.2 | 5824.9 | 3.3 % |
| Bonsai 2 2B | 4096 | 200.6 | 5632.6 | 3.0 % |
| Bonsai 2 4B | 512 | 586.4 | 15177.8 | 3.4 % |
| Bonsai 2 4B | 4096 | 525.0 | 14146.1 | 3.1 % |

The scan is per token per layer and nearly flat in prompt length, so its share *falls* as the
prompt grows and attention becomes visible (2.7-3.2 % of the wall at 4096 on both models). It is
three times the <1 % #133 measured on the dense Qwen3.5-2B, which is what a recurrent share should
look like, but it is not where a prefill PR earns its keep. The chunked ternary GEMM in this PR
moves the matmul bucket ~17 %, i.e. ~15 % of the wall.

## Why chunking is not a drop-in

Today the scan folds the recurrent state one position at a time, in the order the tokens were
written. The fold is what makes a row's arithmetic independent of the batch: no matrix inverse, no
block boundary, and the same f32 operations in the same order whether the position is decoded alone
or read inside a 16/64-token prefill chunk.

A chunked scan would replace that with the closed form over a chunk of `C` positions:

1. build the `C × C` lower-triangular decay-weighted product of `(I − β k kᵀ)` factors,
2. invert it (or solve against the chunk's `β kᵀ v` right-hand side),
3. carry the state forward once per chunk.

That is what FLA's `chunk_gated_delta_rule` and the `fla`/`mamba` CUDA kernels do, and it changes
the fold: the low-rank factors are applied in a different order, and the `C` positions interact
through a solve that the per-position fold never performs. Integer or f32 associativity does not
save it — the two forms are algebraically equal, not bit-equal.

## What a KL gate would have to hold

Because the change is a real numerical change, it must be gated the way the other accuracy steps
are (`docs/targets.md`, S3.3):

- **Reference.** llama.cpp cannot load PQ2_0, so the comparison is against PrismML's fork
  (branch `prism`, commit `62c418c`, `benchmarks/engines/prism_llama_cpp.py`) or Peregrine's own
  exact f32 reference (`PEREGRINE_EXACT=1` plus a scalar scan). The fork is the only engine that
  runs the same file; the exact reference is the only one that isolates the fold.
- **Metric.** Per-token KL against the current scan on a fixed prompt set, not a single prompt:
  the scan's error compounds over the sequence, and the chunk size is the only knob.
- **Gate.** The same threshold the other numerical changes use for the model, measured at 512 and
  4096, plus the batch-invariance and prefill-chunk tests (`prefill_chunk.rs`) extended to demand
  chunk-size invariance, not only token invariance.

## Sketch, if it is ever taken

- `recurrent.rs` already has the state layout and the per-position fold (`blocks/recurrent.rs`,
  `blocks/rotate.rs`). A chunk kernel would be a second implementation behind the same interface,
  selected by a `PEREGRINE_SCAN_CHUNK` option (0 = current per-position fold), so the old path is
  the A/B control.
- The chunk size wants to be small (16-32): the `C × C` solve is `O(C³)` and Bonsai's `n_v` is
  128 per head, so the win over the per-position fold is in the state carry, not the solve.
- The scan is 3 % of prefill; the implementation is a new kernel, a new option, a KL run and a
  chunk-size invariance test. It is a follow-up, not part of the batched-GEMM PR.
