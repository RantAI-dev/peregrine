## 0. Summary

Peregrine's prefill is 85.7 % weight matmul (`docs/design/prefill.md` §3), and that matmul runs
at 14.1 int8 MAC/cycle per core against llama.cpp's ~23 on the same machine. The gap is not
bandwidth (4 % of the DRAM roof) and not scheduling (the ratio is flat across 1-24 threads); it
is the *instruction mix* of the k-quant kernel.

This note specifies the fix: **repack the k-quant weights into 8-row tiles at load, interleave four
activation rows into one buffer, and let a single `vpmaddubsw` feed a 4-column × 2-row cross
product** — llama.cpp's "8x8" layout. The expected effect is to move the per-super-block scale
multiply, the activation loads and the float fold from *per activation* to *per 8 columns*, which
is where most of the instruction budget actually goes (see §2.5).

Three things fall out of the design, and they are the reason this is a design note and not a patch:

1. **The result is not bit-identical to today's kernels.** The 8 accumulator lanes change meaning
   from "8 sub-block positions of one output" to "8 different outputs", so the reduction moves
   from the float domain into the integer domain. The exact real number computed is the same; the
   rounding is not. The goldens move on the AVX2 and AVX-512 tiers (§4.2).
2. **Batch invariance forces the decode path onto the same fold.** A row computed in a 64-row
   prefill and the same row computed alone in a decode step must be bit-identical, or
   `batching_is_invariant_across_slots` fails. That means the single-row path cannot keep today's
   `tile_q4_k`: it needs the repacked GEMV with the same per-(output, activation) expression (§4.4).
3. **The int16 accumulator is safe for Q4_K and not for Q5_K/Q6_K.** llama.cpp sums eight
   `vpmaddubsw` results in int16; for Q4_K that reaches 30 480 of 32 767, for Q6_K it would be
   128 016. The Q4_K path can copy llama.cpp's structure; the Q6_K path cannot (§4.1).

One correction to the input document, made after reading the v0.9.0 source: `prefill.md` §6 Gap 1
says llama.cpp's AVX2 kernel "gets 64 MACs per `vpmaddubsw`". It does not. On AVX2 a
`vpmaddubsw` does 32 byte-MACs, and in llama.cpp's layout all 32 are useful — the same as
Peregrine's. 64 is the AVX-512 figure (`_mm512_maddubs_epi16`). The gap is real and the lever is
the same, but the *reason* is the amortisation of the scale multiply, the activation loads and the
float fold, not a doubled MAC rate. §2.5 gives the corrected instruction budget and §6 the
consequent expectation. This is raised as an open question in §9.

And one thing the input document does not count: the prefill's **activation** traffic. Because the
prefill path works one output row at a time, it reads the activation array once per output row —
about 507 GB per 512-token prompt, a hundred times the weight traffic that `prefill.md` §3
reports. The repacked tile cuts that 32×. §2.6 works the arithmetic out; §9 Q10 asks whether the
correction belongs in this PR or in the prefill note's own follow-up.

## 1. Where the gap is, restated from the measurement

From `docs/design/prefill.md` (12 threads, 512-token prompt, `PREFILL_CHUNK = 64`,
`Llama-3.2-1B-Instruct-Q4_K_M.gguf`, AMD Ryzen AI 9 HX 370 under WSL2, 1.74 GHz):

```
wall        3.4072 s   (150.3 tok/s; the bench harness reports 154.0)
ns_matmul   2.9214 s   (85.7 %)   498.96 G int8 MACs -> 170.8 G MAC/s
                                1.67 GB/s of weight traffic (4 % of a 41.7 GB/s roof)
ns_attn     0.1612 s   ( 4.7 %)
ns_other    0.3155 s   ( 9.3 %)   serial: scales 2.07x from 1 to 12 threads
ns_head     0.0091 s   ( 0.3 %)
```

Per core: 24.6 G int8 MAC/s = **14.1 MAC/cycle** (measured roof for this instruction mix: 101.8 G
MAC/s per core = 58.5 MAC/cycle). The matmul's weight bytes are formatted:

| format | weight bytes | share of the matmul (projected) |
|---|---|---|
| Q4_K | 467.1 MB | 86 % |
| Q6_K | 117.0 MB | 14 % |
| F32 (the norms) | 0.3 MB | — |

So S3.4 is a Q4_K project with a Q6_K second.

The kernel path for a 64-row prefill is
`MatPath::PerRow → quant::dot_batch → simd::dot_batch → simd::wide_q4_k`
(`crates/peregrine-kernels/src/table.rs:81`, `crates/peregrine-kernels/src/simd.rs:1603`,
`simd.rs:1392`). `wide_q4_k` unpacks the super-block once and runs it against every activation, but
its *inner* group is still `TILE = 4` activations and its per-activation work is unchanged from the
tiled kernel.

## 2. What llama.cpp actually does (read from v0.9.0)

### 2.1 The weight layout: `block_q4_Kx8`

`ggml/src/ggml-cpu/repack.h`:

```c
struct block_q4_Kx8 {
    ggml_half d[8];      // super-block scale for quantized scales
    ggml_half dmin[8];   // super-block scale for quantized mins
    uint8_t scales[96];  // scales and mins, quantized with 6 bits
    uint8_t qs[1024];    // 4--bit quants
};
```

Eight Q4_K super-blocks (eight *output rows* of the weight matrix) in one structure:

* `d[8]`, `dmin[8]`: the eight rows' f16 super-block scale and min scale, one each.
* `scales[96]`: the eight rows' 6-bit scales and mins, repacked. `make_block_q4_Kx8`
  (`ggml/src/ggml-cpu/repack.cpp:3177`) writes **12 bytes per sub-block index** — llama.cpp's own
  packing of ggml's 12-byte Q4_K scale block, eight rows at a time, with the remaining bits in a
  second 12-byte group at `scales[48..96]`. The kernel unpacks it with the same
  `kmask1/kmask2/kmask3` bit tricks `simd.rs:275` already uses, on eight rows instead of one.
* `qs[1024]`: the eight rows' nibbles, interleaved **eight bytes at a time**
  (`make_block_q4_Kx8`: `memcpy(&elems, &in[src_id].qs[src_offset], 8)` with `src_id = i % 8`,
  `src_offset = (i / 8) * 8`). The layout is a sequence of 16 *windows*: window `w` holds bytes
  `8w..8w+8` of each of the eight rows, side by side — 64 bytes per window, 1024 bytes in all.
  The bytes inside a window are the row's own ggml nibbles, untouched: in ggml's Q4_K layout
  `qs[32g + l]` holds weight `64g + l` in its low nibble and weight `64g + 32 + l` in its high
  nibble, so one 8-byte window carries **sixteen weights of that row — eight in the low nibbles
  and eight in the high nibbles, and the two groups are 32 positions apart in the row**.

**Size: 1152 bytes, exactly 8 × `sizeof(block_q4_K)` (8 × 144).** The repack is a permutation, not
an expansion. This is the single most important fact for §5.1: the repacked copy costs the same
bytes as the original, so it can *replace* the mapped bytes instead of doubling them.

The kernel reads it as eight 32-byte chunks per 64-weight quarter (`repack.cpp:2856-2863`):

```c
rhs_raw_mat_0123_0 = loadu(b_ptr[b].qs + sb * 256);        // rows 0-3, window 0
rhs_raw_mat_4567_0 = loadu(b_ptr[b].qs + 32 + sb * 256);   // rows 4-7, window 0
rhs_raw_mat_0123_1 = loadu(b_ptr[b].qs + 64 + sb * 256);   // rows 0-3, window 1
...
```

i.e. 32 bytes = four rows × eight bytes = four rows × 16 nibbles = **16 weights per row per
chunk**.

### 2.2 The activation layout: `block_q8_Kx4`

```c
struct block_q8_Kx4 {
    float  d[4];              // delta
    int8_t  qs[QK_K * 4];     // quants
    int16_t bsums[QK_K / 4];  // sum of quants in groups of 16
};
```

Four *activation rows* per structure, interleaved in **eight-byte chunks**
(`ggml_quantize_mat_q8_K_4x8_generic`, `ggml/src/ggml-cpu/repack.cpp:262`):

```c
int src_offset = (j / (4 * blck_size_interleave)) * blck_size_interleave;  // blck_size_interleave = 8
int src_id     = (j % (4 * blck_size_interleave)) / blck_size_interleave;
```

so `qs` is `[row0 bytes 0-7][row1 bytes 0-7][row2 bytes 0-7][row3 bytes 0-7][row0 bytes 8-15]…`
— one 32-byte load holds eight weights of all four rows. `bsums` holds the 16-weight run sums in
the order `[run][row][sub-run]` (`index = (((j & 31) >> 3) << 2) + ((j >> 8) << 4) + ((j >> 6) & 3)`),
so one 32-byte load holds the run sums of all four rows.

`ggml_quantize_mat_t<8, GGML_TYPE_Q8_K>` (`repack.cpp:330-340`) is what the GEMM path calls; the
4-byte-chunk variant (`4x4`) is used by other paths and is *not* compatible with the GEMM's loads.

**Size: 1168 bytes = 4 × 292**, and Peregrine's `QuantAct` already spends 292 bytes per row
(`qk` 256 + `dk` 4 + `bsums` 32, `crates/peregrine-kernels/src/quant.rs:74-79`). The interleaved
activation is therefore also size-neutral per row.

### 2.3 The `_sp1`/`_sp2` shuffle trick

This is the heart of it, and it is worth stating precisely because it is easy to misread.

The weight side (`repack.cpp:2903`, `:2929`) shuffles the unpacked nibble vectors twice:

```c
const __m256i rhs_mat_0145_00_sp1 = _mm256_shuffle_epi32(rhs_mat_0145_00, 136); // 136 = sel [0,2,0,2]
const __m256i rhs_mat_0145_00_sp2 = _mm256_shuffle_epi32(rhs_mat_0145_00, 221); // 221 = sel [1,3,1,3]
```

The activation side (`repack.cpp:3024`, `:3049`) does the same with the other two selectors:

```c
const __m256i lhs_mat_01_00_sp1 = _mm256_shuffle_epi32(lhs_mat_01_00, 160); // 160 = sel [0,0,2,2]
const __m256i lhs_mat_01_00_sp2 = _mm256_shuffle_epi32(lhs_mat_01_00, 245); // 245 = sel [1,1,3,3]
```

(The selectors are per 128-bit lane; `_mm256_shuffle_epi32` applies the same four-element pattern
to both halves.)

What they do, in one line: **each 4-byte group of a column is duplicated into two dwords so that it
can be paired with two different activation rows, and each 4-byte group of an activation row is
duplicated so that it can be paired with two different columns.** After the shuffles, the two
32-byte operands line up as a 4-column × 2-row cross product:

```
rhs_sp1 dwords:  B0(0-3) B1(0-3) B0(0-3) B1(0-3) B4(0-3) B5(0-3) B4(0-3) B5(0-3)
lhs_sp1 dwords:  A0(0-3) A0(0-3) A1(0-3) A1(0-3) A0(0-3) A0(0-3) A1(0-3) A1(0-3)
products:        (B0,A0) (B1,A0) (B0,A1) (B1,A1) (B4,A0) (B5,A0) (B4,A1) (B5,A1)
```

So **one `vpmaddubsw` computes eight distinct (column, row) partial products of four bytes each** —
32 byte-MACs, every one of them useful. `_sp2` is the same trick on the other four bytes of the
window, and the low/high nibble split (`rhs_mat_0145_00` = `chunk & 0x0F`,
`rhs_mat_0145_10` = `(chunk >> 4) & 0x0F`) is the third axis, giving the four combinations
`{sp1,sp2} × {low,high}` that cover all sixteen weights of the window.

The two weight column groups are made by a permute and a blend (`repack.cpp:2866`):

```c
const __m256i requiredOrder = _mm256_set_epi32(3, 2, 1, 0, 7, 6, 5, 4);   // = {4,5,6,7,0,1,2,3}
rhs_raw_mat_0145_0 = _mm256_blend_epi32(rhs_raw_mat_0123_0, _mm256_permutevar8x32_epi32(rhs_raw_mat_4567_0, requiredOrder), 240);
rhs_raw_mat_2367_0 = _mm256_blend_epi32(_mm256_permutevar8x32_epi32(rhs_raw_mat_0123_0, requiredOrder), rhs_raw_mat_4567_0, 240);
```

`0145` is the column set {0,1,4,5}, `2367` is {2,3,6,7} — the split that lets the two 4-column
groups be shuffled independently.

One detail an implementer has to get right, because it is not visible in the shuffle constants: the
weight window's two nibble halves are **32 positions apart in the row** (§2.1), so they pair with
*different* activation chunks. The kernel's `_0` accumulator group takes the low nibbles
(`rhs_mat_0145_00..03`) against the activation chunks 0-3, and the `_1` group takes the high
nibbles (`rhs_mat_0145_10..13`) against the activation chunks 4-7 (`repack.cpp:3074-3090`). The
activation chunk `j` of a 64-weight quarter holds the codes of the weights `64·sb + 8j .. +8`.

### 2.4 Where the int16 sums and the scale madds happen

Inside the AVX2 branch (`repack.cpp:2817-3157`), for one super-block, eight columns and four
activation rows:

| step | instruction | count | what it covers |
|---|---|---|---|
| nibble unpack | `vpand` / `vpsrlw` | 16 + 8 | the low/high nibbles of the eight 32-byte chunks |
| column regroup | `vpermd` + `vpblendd` | 8 + 16 | `0145` / `2367` |
| the shuffle trick | `vpshufd` | 80 | `_sp1`/`_sp2` on both sides |
| dot products | **`vpmaddubsw`** | **64** | 4 columns × 2 rows × 4 bytes each |
| int16 accumulation | `vpaddw` | 56 | 8 maddubs summed per accumulator (3 + 3 + 1 + 1 adds) |
| **scale** | **`vpmaddwd`** | **12** | **one per (8 columns × 4 rows × 64 weights)**, against a vector of the eight columns' 6-bit scales |
| min term | `vpmaddwd` | 4 | against the precomputed per-row `bsums` and the eight columns' mins |
| int32 accumulation | `vpaddd` | 8 | |
| **float fold** | **`vfmaddps`** | **8** | **one per (8 columns × 4 rows) per super-block** |

The two lines to compare with Peregrine are the last two. In `wide_q4_k` (`simd.rs:1362-1442`):

* the scale is applied **per activation, per 32-weight sub-block**: `q4k_acts` does
  `_mm256_madd_epi16(_mm256_maddubs_epi16(q4l[j], q8l), scl)` — one `vpmaddwd` per `vpmaddubsw`;
* the float fold is `q4k_fold` (`simd.rs:362`), **one per activation per super-block** — seven
  vector ops plus a load and a store of the float accumulator, which lives in a 128-entry YMM stack
  array because 64 live accumulators do not fit in sixteen registers.

In llama.cpp the scale madd serves eight columns at once and the float fold serves eight columns
and four rows at once.

### 2.5 The instruction budget (and the correction to `prefill.md`)

Counting the AVX2 Q4_K GEMM from the source (`repack.cpp:2817-3157`) and Peregrine's
`wide_q4_k`, per **(column, activation) pair per super-block** (256 weights):

| | Peregrine `wide_q4_k` | llama.cpp AVX2 |
|---|---|---|
| `vpmaddubsw` | 8 | 8 |
| `vpaddw` (int16 accumulation) | — | 7 |
| `vpmaddwd` (scale, then the min term) | 8 + 1 | 1.5 |
| `vpaddd` (int32 accumulation) | 8 | 1 |
| activation loads (32 B) | 8 | 2 |
| activation permute + `_sp1`/`_sp2` shuffles | — | 6 |
| scale broadcast (`vpbroadcastw`) / scale unpack | 8 | 1.6 |
| float fold + accumulator spill | 8 | 7.5 |
| weight unpack / regroup / shuffle | 0.4 | 2.8 |
| **total instructions** | **~48** | **~37** |

Both kernels issue eight `vpmaddubsw` per (column, activation) per super-block, and in both every
one of the 32 byte-MACs inside a `vpmaddubsw` is a distinct useful product. **The MAC rate per
instruction is the same.** What differs is the overhead around it: llama.cpp issues roughly 1.3×
fewer instructions per (column, activation, super-block), because the scale multiply, the
activation loads and the float fold are amortised over eight columns instead of one. (llama.cpp
pays for this with a lot of `vpshufd`: the `_sp1`/`_sp2` trick costs 32 shuffles per (super-block
quarter, 8 columns, 4 rows), which is why its "weight unpack / regroup / shuffle" line is the
larger of the two.)

**The instruction gap (1.3×) is smaller than the measured per-core gap (1.63×).** So the
instruction count is not the whole story, and the design has to say so rather than assume the rest
follows. `prefill.md` §6 Gap 1 attributes the gap to "64 MACs per `vpmaddubsw`"; reading the
v0.9.0 source, the AVX2 kernel does 32 byte-MACs per instruction and the 64 figure belongs to
`_mm512_maddubs_epi16` in the AVX-512 branch (`repack.cpp:2729`). Since the baseline machine has
AVX2 in both binaries (no AVX-512 in either), the 64 figure cannot be the explanation there.

The remaining 1.25× has to be latency and ports rather than instruction count — the candidates are
the 64-float accumulator spill (a store and a load per activation per super-block, with
store-to-load forwarding on the critical path), the float fold's dependency chain, and the load
port pressure from 256 bytes of activation per (column, activation, super-block). The repacked
kernel attacks all three: four float accumulators instead of 64, one fold per eight columns, and
the interleaved activation. §8's micro-benchmark is what tells us which one it was.

### 2.6 The second effect: activation traffic

The instruction budget is not the whole story either, and the arithmetic behind the *bytes* is
worth doing, because `prefill.md` counts only the weight traffic.

Today the prefill path is `MatPath::PerRow`: **one output row at a time**
(`crates/peregrine-kernels/src/table.rs:81`, `crates/peregrine-core/src/blocks/linear.rs:138-149`).
`wide_q4_k` reads the whole activation array once *per output row* — for every super-block of the
weight row, it reads 256 bytes of codes from each of the 64 activations. So for a matrix of `W`
output rows and `K` weights, the activation traffic is

```
B × K × W bytes          (B = the batch width)
```

while the weight traffic is only `W × K/256 × 144` bytes. The ratio is **B × 256/144 ≈ 114×** at
`B = 64`: the activations are read a hundred times more often than the weights.

For the prefill as a whole that comes to about **507 GB of activation reads** — one byte per int8
MAC, against the 4 891 MB of weight traffic that `prefill.md` §3 reports. Spread over the 3.407 s
prefill that is ≈ 150 GB/s of reads served from L1 and L2, not from DRAM. `prefill.md` concludes
"the prefill is compute/issue-bound, not bandwidth-bound" from the *weight* traffic alone; the
activation traffic is the number it does not have.

At the rate the kernel actually achieves, 150 GB/s is 7 bytes/cycle/core, comfortably under the
L1's capability, so this traffic is not by itself the binding constraint. But the repacked kernel
changes it by **32×** — eight output rows share one pass over the activation (8×) and one 32-byte
load serves four activation rows (a further 4× on the load *instructions*, not on the bytes) — so
it takes the activation reads from 507 GB per prefill to about 16 GB, and takes the load-port
pressure and the L1 footprint with it.

The tile also removes the accumulator spill outright: four float accumulators (one per activation
row, eight columns per lane) instead of 64 in a stack array.

This is a hypothesis, not a measurement: `perf` is unavailable on the baseline host
(`prefill.md` §7), so the activation-traffic figure cannot be read off directly there. The
micro-benchmark in §8 is the instrument that would confirm it — the repacked kernel's advantage
should scale with the batch width (the more activations, the more the tile amortises), and a
kernel-level A/B at widths 1, 4, 8, 16, 32, 64, 128 would show it.

The design conclusion is unaffected — the lever is the same (repack into 8-row tiles, interleave
four activations, amortise the epilogue over eight columns) — but the *estimate* in §6 has to be
built from the measured target rate, not from the MAC-per-instruction ratio.

## 3. Peregrine's equivalent

### 3.1 The repacked weight store

New structure in `peregrine-kernels`, next to the Q4_K block definitions:

```rust
/// Eight Q4_K super-blocks — eight output rows — interleaved for the repacked GEMM.
#[repr(C)]
pub struct Q4K8 {
    /// The eight rows' super-block scales (f16).
    pub d:    [f16; 8],
    /// The eight rows' super-block min scales (f16).
    pub dmin: [f16; 8],
    /// The eight rows' 6-bit scales, one per 32-weight sub-block: `sc[sub_block * 8 + row]`.
    pub sc:   [u8; 64],
    /// The eight rows' 6-bit mins, in the same order.
    pub m:    [u8; 64],
    /// The eight rows' nibbles: 16 windows of eight bytes per row, side by side.
    pub qs:   [u8; 1024],
}
```

Two deliberate differences from llama.cpp's `block_q4_Kx8`:

* **the scales and mins are stored unpacked.** llama.cpp keeps ggml's 6-bit packing and unpacks
  it in the kernel with a bit-fiddling sequence that spans two 12-byte groups; Peregrine already
  has `unpack_q4k_scales` (`simd.rs:275`) and can do the unpacking **once, at load**, and store
  plain `u8` scales and mins. The cost is 128 bytes instead of 96 per eight super-blocks, so the
  block is 1184 bytes instead of 1152 — **+2.8 %** on the Q4_K weights (467 MB → 480 MB on the
  1B model). The benefit is that the kernel's scale load is one 8-byte load and one
  `vpbroadcastw` per sub-block, with no bit tricks in the inner loop.
  *If the orchestrator prefers byte-for-byte size neutrality, the alternative is to store
  ggml's 12-byte packing per row (96 bytes per eight rows) and extend `unpack_q4k_scales` to eight
  rows at once. It is a one-line change to the store and a slightly hairier kernel; see §9 Q3.*
* **the nibble windows are 8 bytes, as in llama.cpp**, so the weight side of the shuffle trick is
  byte-identical to llama.cpp's and can be read straight off the reference kernel.

**What landed (step 2).** The scales and mins stay **packed**: `scm[sub_block * 12 ..]` holds six
bytes of six-bit scales and six of six-bit mins for the eight rows, and `Q4K8` is **1152 bytes**,
byte-for-byte the size of the file's eight blocks. Decision 9 decides it. With the unpacked scales
the store is 2.8 % larger, and decode streams every byte of the Q4_K weights once per token, so the
extra 32 bytes per tile came straight off the decode rate (measured on the bluefin host: −1.3 %,
the whole of the regression the first A/B saw). `kqsimd::unpack_scales` undoes the packing once per
super-block, before the window loop, so the inner loop still reads a ready scale and min vector per
sub-block and the kernel keeps the simple shape decision 3 asked for.

### 3.2 The interleaved activation

The kernel needs four activation rows side by side. Peregrine's `QuantAct` is *per row*, so the
interleave cannot live there; it belongs in the per-layer batch scratch, next to `st.acts`:

```rust
/// The k-quant interleaved activation: four rows side by side, eight bytes per row per
/// window (llama.cpp's `block_q8_Kx4`), plus the four rows' per-256 scales and per-16 run sums.
pub struct KqActs {
    /// `n / 256 * 4` bytes per group of four rows: the interleaved int8 codes.
    pub q:   Vec<i8>,
    /// `n / 256 * 4` scales: the per-256 activation scale of each of the four rows.
    pub d:   Vec<f32>,
    /// `n / 16 * 4` run sums: the per-16 activation sums, in the interleaved lane order.
    pub bs:  Vec<i16>,
}
```

It is filled **once per layer** (or once per ubatch, which is S3.5's business), not once per
matmul. That matters: `prefill.md` Gap 2 measures the activation quantisation inside the serial
"other" bucket (9.3 % of the prefill). Building this buffer once per layer instead of once per
matmul group is the same fix S3.5 wants, and it is a natural by-product of S3.4 — but the two must
not be conflated; see §9 Q7.

Rows are grouped in fours; a batch whose width is not a multiple of four is padded to a multiple
of four with zero codes (the padded rows' results are discarded). The zero padding is exact: a
zero activation code contributes nothing to any dot product, and its own output is discarded.

### 3.3 The AVX2 kernel

For a tile of eight output rows and a group of four activations:

```
for each super-block sb of the tile's rows:                  # k / 256
    d[8], dmin[8]      -> eight f32 column scales and min scales
    sc[8][8], m[8][8]  -> the eight sub-block scales and mins (unpacked, one u8 each)
    for each of the four 64-weight quarters:
        for each of the eight 32-byte weight chunks:
            # the two column groups, the nibble halves, the _sp1/_sp2 shuffles
            # -> 8 vpmaddubsw, each a 4-column x 2-row cross product
            # -> the int16 sums (at most eight maddubs per lane: the Q4_K bound)
            # -> one vpmaddwd against the eight columns' scales
            # -> one vpmaddwd against the mins and the four rows' bsums
        # the float fold: one vfmaddps per (column, activation) per super-block
```

Register budget (AVX2, 16 YMM):

| | count | note |
|---|---|---|
| int16 accumulators | 4 | one per (column group, row group): `00`, `01`, `10`, `11` |
| float accumulators | 4 | one per activation row, eight columns per lane |
| nibble vectors | 8-16 | the unpacked low/high nibbles of the current chunk |
| scale / min vectors | 4 | |

That fits, with room for the shuffle temporaries. The float accumulator count is **4 instead of
64** — the spill disappears.

The float fold must reproduce `q4k_fold`'s expression exactly, so that the same real number is
computed:

```rust
// per super-block, per column c (a lane) and activation row t:
let s = cvtepi32_ps(sumi);            // the int32 sum over the super-block's sub-blocks
let m = cvtepi32_ps(minterm);         // the int32 min term
let x = fnmadd(dmin_v, m, mul(d_v, s));
acc[t] = fmadd(x, dk_v, acc[t]);
```

`sumi` and `minterm` are the *integer* sums over the super-block's eight sub-blocks, computed in
int32 (exact). The current kernel keeps those sums split across eight lanes and reduces them in
float at the very end; the repacked kernel reduces them in int32 and carries one lane per column.
§4.2 works out what that costs.

### 3.4 AVX-512

The AVX-512 tier gets the same structure with 16 columns per tile and ZMM registers:

* the weight tile interleaves **16** output rows (llama.cpp's `block_q4_Kx16`, `repack.h`), and one
  `vpmaddubsw` on a ZMM does **64 byte-MACs** — this is where the "64 MACs per instruction" figure
  belongs;
* `_mm512_shuffle_epi32` applies the same selectors per 128-bit lane, so the `_sp1`/`_sp2` trick is
  unchanged in shape;
* the scale madd is again one per 16 columns.

llama.cpp's AVX-512 branch (`repack.cpp:2082-2815`) is the reference for the shape, and it uses
`_mm512_maddubs_epi16` (not `vpdpbusd`) for the accumulation, so the int16 bound of §4.1 is
unchanged: the number of *products* per int16 lane is what matters, not the vector width.

The AVX-512 variant is **not** in the 1.5 pw budget's critical path: the baseline machine has no
AVX-512 in either binary, and the H2 host ("bluefin", Zen 2) has none at all. See §9 Q6.

### 3.5 Under VNNI

`vpdpbusd` (AVX-VNNI-256, and AVX-512-VNNI) accumulates four u8 × i8 products straight into int32
lanes: no int16 stage, no saturation question, and half the instruction count of
`vpmaddubsw` + `vpmaddwd`.

For the k-quants it does not fit, and the reason is the scale. The Q4_K scale is a 6-bit number
that applies to a 32-weight sub-block of one *column*; `vpdpbusd` multiplies u8 by i8 and
accumulates, so there is no place to put a per-column scale inside the dot product. Two ways out:

* **Scale afterwards.** `vpdpbusd` gives the int32 sum of four products; multiplying it by the
  6-bit scale afterwards is exact (int32 × int16 → int32, and the product is far from 2³¹). But
  the scale differs per *sub-block*, so the accumulator must be kept per sub-block: eight int32
  accumulators per (column, activation) — eight times the registers. Not viable.
* **Fold the scale into the activations.** Not possible: the scale is a property of the weight.

There is a third option that does not work either: folding the scale into the multiplicand. The
Q4_K code is ≤ 15 and the scale is ≤ 63, so `code × scale` needs ten bits and does not fit in the
`u8` operand `vpdpbusd` takes; and the scale cannot be folded into the *activation* either,
because it is a property of the weight.

One variant is worth naming because it is the obvious next question: keep the `vpdpbusd`
accumulator per *sub-block* and apply the scale afterwards. It is exact — `vpdpbusd` gives the
int32 sum of four products, and multiplying that by the 6-bit scale is an exact int32 operation —
but it costs one extra multiply and one extra add per sub-block against the `vpmaddubsw` +
`vpmaddwd` pair it replaces, and the scale multiply on int32 lanes is not a single instruction on
every CPU. So it is not a win.

The practical conclusion: **on a VNNI machine the k-quant kernel keeps the
`vpmaddubsw` + `vpmaddwd` structure**, and VNNI buys nothing there. It does buy a great deal on
the *legacy* formats (Q8_0, Q4_0, Q5_0) and on the ternary formats, where the scale is per
32-weight block and can be applied after the accumulation (as `docs/design/s2.6.md` §3.2 already
argues). The AVX-VNNI-256 tier therefore aliases the AVX2 k-quant results, exactly as S2.6
Decision 1 already does for the ternary ones.

Under **AVX-512-VNNI** the same argument applies to the k-quants; the 16-column ZMM kernel keeps
`_mm512_maddubs_epi16`.

### 3.6 Q5_K and Q6_K

llama.cpp v0.9.0 has **no x86 repacked kernel for Q5_K or Q6_K**: `ggml_repack_get_optimal_repack_type`
(`ggml/src/ggml-cpu/repack.cpp:5055-5076`) offers `q5_K_8x8_q8_K` and `q6_K_8x8_q8_K` only under
NEON. On x86 both formats run the ordinary `ggml_vec_dot_*_q8_K` path. So Peregrine would be
*ahead* of llama.cpp here, and the structures to copy exist (`block_q5_Kx8`, `block_q6_Kx8` in
`repack.h`) but the kernels do not.

* **Q6_K** is 14 % of the matmul on the Q4_K_M model, so it is worth doing. The codes are 6-bit
  (0..63) and the scales are int8 per 16 weights, with a −32 offset. The repacked
  `block_q6_Kx8` interleaves the `ql` and `qh` halves across the eight rows. The int16 bound
  (§4.1) is the constraint: at most **four products per int16 lane** are safe, so the Q6_K kernel
  must widen to int32 after every second `vpmaddubsw` instead of after eight. The −32 offset is
  applied exactly as `wide_q6_k` does today (`simd.rs:1582`), against the per-16 run sums.
* **Q5_K** adds a fifth bit per weight, held in a per-row `qh` byte mask. The int16 bound allows
  at most **eight products per lane** (8 × 31 × 127 = 31 504), so the Q5_K kernel also has to
  widen earlier. Q5_K does not appear in the Q4_K_M model's matmul at all (the model is 74 % Q4_K
  and 14 % Q6_K by weight), so it is the natural thing to cut if the budget is tight. See §9 Q5.

## 4. Exactness

### 4.1 Where the int16 intermediates could overflow

`vpmaddubsw` computes, per 16-bit lane, `u8 × i8 + u8 × i8`, **saturated** to int16. llama.cpp's
AVX2 Q4_K kernel then sums **eight** such vectors with `vpaddw` (int16, wrapping) before the scale
`vpmaddwd` (`repack.cpp:3074-3101`):

```
lane value after the maddubs : |2 · code · act| ≤ 2 · 15 · 127 = 3 810      (no saturation)
lane value after 8 adds      : |8 · 2 · code · act| ≤ 8 · 3 810 = 30 480  (< 32 767 ✓)
```

**Q4_K is safe**, with 2 287 of headroom (7 %), *provided the activation codes are within ±127*.
Peregrine's quantiser clamps to exactly that (`simd.rs:1707`: `_mm256_min_ps(_mm256_max_ps(r, lo), hi)`
with `lo = -127`, `hi = 127`), so the bound holds by construction. Even at ±128 the bound would be
30 720, still inside int16. The bound is a property of the *format*, not of the data: Q4_K codes
are 0..15 by definition.

The same sum for the other formats:

| format | max code | products per int16 lane at 8 maddubs | safe? |
|---|---|---|---|
| Q4_K | 15 | 16 × 15 × 127 = 30 480 | **yes** (7 % headroom) |
| Q5_K | 31 | 16 × 31 × 127 = 63 008 | no — cap at 8 products/lane (31 504) |
| Q6_K | 63 | 16 × 63 × 127 = 128 016 | no — cap at 4 products/lane (32 004) |

This is exactly why llama.cpp ships no x86 Q5_K/Q6_K repack: the 8-maddub int16 accumulation is a
Q4_K structure. Peregrine's Q6_K kernel must widen to int32 after every second `vpmaddubsw`
(4 products per lane) and Q5_K after every fourth (8 products per lane).

The wider intermediates are safe by a wide margin:

* the scale `vpmaddwd`: `int32 = int16 · int16`, bounded by 30 480 × 63 = 1 920 240 per lane;
  adding the pair gives 3 840 480, well inside int32;
* the min term `vpmaddwd` against the run sums: the run sums are ≤ 16 × 127 = 2 032, two of them
  plus the 6-bit min give ≤ 63 × 4 064 = 256 032;
* the int32 accumulator over a super-block: 8 sub-blocks × 63 × 4 products × 127 × 15 ≈ 3.8 M.

**Conclusion: the int16 stage is safe for Q4_K and must be restructured for Q5_K and Q6_K.**

### 4.2 Whether results stay bit-identical to today's kernels

**They do not, and they cannot.** The reason is the lane structure.

Today (`simd.rs:1362-1442`), the float accumulator of one output row has eight lanes, and each lane
carries a *strided* share of the super-block's products (lane ℓ holds four products per sub-block,
at different weight offsets). The row's value is the final `hsum_ps(acc)` over those eight lanes.
The per-super-block expression is

```
value = hsum_ℓ ( Σ_sb dk_sb · ( d_sb · S[ℓ][sb] − dmin_sb · M[ℓ][sb] ) )
```

with `S[ℓ][sb]` and `M[ℓ][sb]` the *per-lane* integer sums.

In the repacked kernel, the eight lanes are eight *different outputs*. The per-super-block
expression becomes

```
value_c = Σ_sb dk_sb · ( d_sb · S[c][sb] − dmin_sb · M[c][sb] )
```

with `S[c][sb] = Σ_ℓ S[ℓ][sb]` and `M[c][sb] = Σ_ℓ M[ℓ][sb]` accumulated in **int32**.

Both compute the same exact real number — the int32 sums are exact, and the two expressions differ
only in where the addition of the eight lanes happens — but they round differently:

* the current kernel rounds each lane's super-block contribution to float before summing the lanes;
* the repacked kernel sums the lanes exactly in int32 and rounds once.

So the difference is a rounding difference of the order of the last ULP of the result, amplified by
the number of terms. It is **not** an approximation difference: both are within one rounding of
the exact value of the same integer-exact expression.

What that means under **ADR 0003** ("lossless by default"):

* **Same tokens as the reference for a fixed seed.** The reference is the exact f32 path. The
  repacked kernel is not claimed to be *closer* to the exact path than the current one is, but the
  KL against the exact f32 path does not change in magnitude, because the change is a re-rounding
  of the same integer-exact expression, not a new approximation. The KL budget (≤ 1e-4,
  `docs/targets.md`) is unaffected. What *can* change is a near-tie in the argmax, so the greedy
  token streams on the gate models must be re-checked, not assumed.
* **Deterministic per tier.** Preserved: the repacked kernel is a pure function of the weights and
  the activations, with no dependence on the batch width (§4.4) and no dependence on the thread
  count (the rows are still partitioned, never reduced).
* **KL unchanged.** As above.

### 4.4 Batch invariance, and what it decides about the decode path

`crates/peregrine-models/tests/synthetic.rs:648` (`batching_is_invariant_across_slots`) runs each
prompt alone in a one-slot engine and then the same prompts together in a four-slot engine where the
schedule mixes a 64-row prefill chunk with one- and two-row decode steps, and requires the token
streams to be identical. The same prompt is therefore evaluated **both** in a wide prefill batch
**and** in a narrow decode batch, and the two must agree.

Today that holds because `tile_q4_k` (batch ≤ 4) and `wide_q4_k` (batch > 4) are bit-identical:
they use the same `q4k_fold`, the same integer grouping (`_mm256_add_epi32(sumi, _mm256_add_epi32(pl, ph))`
in both, `simd.rs:691` and `simd.rs:1379`), the same scale vectors and the same final `hsum_ps`.
The wide kernel only removes the *repeated decoding* of the weight row; it does not change the
arithmetic.

The repacked kernel changes the arithmetic (§4.2), so the invariant now constrains the design:

> **The decode path must use the repacked kernel too, with the same per-(output, activation)
> expression — or the invariant breaks.**

Concretely: the single-row path cannot stay on `tile_q4_k`, because `tile_q4_k` reduces the eight
lanes in float at the end while the repacked GEMM reduces them in int32. The two would disagree in
the last bits, and a near-tie would flip a token.

Two repacked paths are therefore needed, and they must agree:

* **the repacked GEMV** (one activation row): llama.cpp's `ggml_gemv_q4_K_8x8_q8_K`
  (`repack.cpp:1464`). It reuses the same 8-column weight tile, but reads the activation in the
  plain per-row layout — there is no four-row interleave to build for one row — and broadcasts it
  across the eight columns. Its inner structure is the same 4-byte-group shuffle trick
  (`repack.cpp:1625`: eight columns × four bytes against one activation row's four bytes).
* **the repacked GEMM** (four activation rows at a time): the §3.3 kernel, with the interleaved
  activation.

They agree bit-for-bit if, and only if, both compute for each (column, activation)

```
value = Σ_sb  dk[sb] · ( d[sb] · S − dmin[sb] · M )        (S, M exact int32)
```

with the same sequential FMA chain over the super-blocks. The int32 sums `S` and `M` are identical
in both paths (integer arithmetic is exact and associative, and both apply the scale per
sub-block), so the float expressions are the same expression with the same operands in the same
order. The two paths must also use the *same* `dk`/`d`/`dmin` values — which they do, because both
read the same `d[8]`/`dmin[8]` of the tile and the same per-256 activation scale.

This is the point where the design has to be checked against the *other* consumer of the same
invariant: `PEREGRINE_EXACT=1` (the f32 reference path) and the scalar reference kernel. Both are
unaffected — they do not use the repacked kernel — so the reference stays the reference.

**Batch widths.** With the repacked path in place:

| width | path | notes |
|---|---|---|
| 1 | repacked GEMV | decode, and the one-row output head |
| 2-3 | repacked GEMV, repeated per row | the speculative block (`draft_len + 1 ≤ 4`) |
| 4 | repacked GEMM | the first group of the interleaved activation |
| 5-128 | repacked GEMM | `MAX_BATCH = 128` (`crates/peregrine-core/src/blocks/linear.rs:14`) |

The old `tile_q4_k` / `wide_q4_k` remain as the fallback for: a CPU without AVX2 (the scalar tier),
the tail rows of a matrix whose row count is not a multiple of eight (§5.1), and
`PEREGRINE_KREPACK=0` (the A/B switch) — which is also the AVX-512 tier's default (§10, 2026-11-07).

## 5. Where it fits

### 5.1 Repacking at load

**Where.** At load, next to the existing PQ2_0 tile repack
(`crates/peregrine-models/src/qwen35/load.rs:395-404`, `tern::repack_tiles`). The PQ2_0 path is the
precedent: the ternary weights are repacked into 16-row tiles into a `TileStore` at load, and
`TensorInfo::tile_off` points into it. The k-quant repack is the same shape, one level up.

**Memory.** The repack is **size-neutral**: `Q4K8` is 1152 bytes for eight super-blocks, against
8 × 144 = 1152 bytes of the original (the scales and mins keep ggml's 12-byte packing, §3.1). So:

* the repacked store *replaces* the mapped bytes for the Q4_K tensors rather than sitting beside
  them;
* the mapped pages for the Q4_K range are never touched again, so they do not become resident;
* the resident cost is therefore the repacked copy (467 MB on the 1B model) in place of the
  file-backed pages that would otherwise be resident — **no net growth**, provided the engine does
  not also read the original bytes.

If the original bytes *are* also needed (the tail rows of a matrix whose row count is not a
multiple of eight), keep only the tail rows in a small side buffer and drop the rest.

**Load time.** The repack reads the Q4_K bytes and writes the same number of bytes: for the 1B
model, 467 MB read + 480 MB written ≈ 0.95 GB of traffic, roughly 0.1-0.2 s at 5-10 GB/s, plus the
first-touch faults on the destination. The destination should be an anonymous mapping with
transparent huge pages, like `TileStore::new` (`crates/peregrine-core/src/model.rs:170-187`), with
`PEREGRINE_TILE_HUGEPAGES=0` as the A/B control.

This is a real cost on the CLI's startup path and it is the main argument for making the repack
**optional and lazy**: repack a matrix the first time it is used, or repack the whole model in one
pass at load. See §9 Q2.

**mmap vs copy.** The file stays mapped for the tensors that are not repacked. For the repacked
tensors, the mapping is not read at all after the repack. The repacked store is anonymous memory
(huge pages), so it is not evictable — the same trade the PQ2_0 tile store already makes.

**Which tensors.** Only the k-quant matrices that the repacked kernel handles, and only when the
matrix's row count (the number of output features) is a multiple of eight. llama.cpp makes the same
restriction (`cur->ne[1] % 8 == 0`, `ggml/src/ggml-cpu/repack.cpp:5011-5016`); Peregrine's matrices
have `dims[0]` = the input width and `dims[1]` = the output rows, so the condition is
`dims[1] % 8 == 0`. For Llama-3.2-1B: 2048, 8192, 128 256 — all multiples of eight. For a model
where they are not, the tail rows fall back to the old kernel and the matrix is not repacked at
all (simpler than a partial tile).

### 5.2 The kernel table

`crates/peregrine-kernels/src/table.rs` gains:

```rust
pub enum MatPath {
    ...
    /// Repacked 8-row k-quant tiles against the interleaved activation layout (AVX2 and up).
    KqTiles,
}

/// Whether the k-quant matrices may be repacked into 8-row tiles.
pub kq_tiles: bool,
```

`MatKernels::detect` sets `kq_tiles` from `have_batched() && options::get().kq_repack`.
`PEREGRINE_KREPACK`'s own default is the resolved tier's: on below AVX-512 and off on it (§10,
2026-11-07), and the switch overrides it both ways.
`MatKernels::path(fmt, tiled, act_ptq1)` returns `MatPath::KqTiles` for `Q4_K`/`Q5_K`/`Q6_K` when
the matrix carries a tile offset. `MatKernels` gains a `kq_tiles_q4k(w_tiles, rows, acts, out)`
wrapper, mirroring `tiles_pq2` (`table.rs:98`).

`kernels_for(fmt)` (`table.rs:167`) is the table the `peregrine support` command and the README
print; the k-quant rows gain a tier entry when the repacked kernel lands:

```
Q4_K     scalar, avx2          (the repacked 8x8 AVX2 kernel)
Q5_K     scalar, avx2          (when PR 4 lands)
Q6_K     scalar, avx2          (when PR 3 lands)
```

The `Tier` enum is unchanged: the repacked kernel is AVX2, and the AVX-512 and AVX-VNNI tiers run
the same code (or the AVX-512 variant, per §9 Q6). The *golden* directories are per tier, so the
table and the goldens stay in step.

### 5.3 Which batch widths use it, and does decode stay on dot/tile?

As laid out in §4.4: **all of them.** The repacked path covers widths 1 to 128 for Q4_K, with the
GEMV for 1-3 rows and the GEMM for 4 and up. The decode path does *not* stay on `tile_q4_k` — that
is forced by the batch-invariance requirement, not by taste.

The consequence for decode is worth stating: decode on this machine is close to
bandwidth-bound (the weights stream once per token), so the repacked GEMV's win is smaller than
the prefill's. It is not zero — the GEMV still amortises the scale madd, the float fold and the
weight unpack over eight columns — but the headline number for S3.4 is the **prompt** rate.

### 5.4 Q5_K and Q6_K

Covered in §3.6. In short: Q6_K is worth 14 % of the matmul and should be in scope; Q5_K is not in
the Q4_K_M model's matmul at all and is the first thing to cut. Both need the int16 stage
restructured (§4.1): Q5_K accumulates four maddubs in int16, Q6_K two.

## 6. Measured expectation

The prefill's phase split is `docs/design/prefill.md` §3 (12 threads, 512-token prompt, chunk 64):

```
wall 3.4072 s = 150.3 tok/s (the bench harness reports 154.0 tok/s for the same run)
ns_matmul 2.9214 s, ns_attn 0.1612 s, ns_other 0.3155 s, ns_head 0.0091 s
```

Two targets, from two different arguments:

* **llama.cpp's measured per-core MAC rate.** `prefill.md` §6 Gap 1: Peregrine 24.6 G int8 MAC/s
  per core, llama.cpp ≈ 40 G MAC/s per core — a factor of **1.63**. This is the number to commit
  to: it is what the same work, the same layout and the same instruction set actually achieve on
  this machine, and a faithful port of the reference kernel should land on it.
* **the instruction budget.** §2.5 counts about 1.3× fewer instructions per (column, activation,
  super-block) — less than the measured gap, so the instruction count alone does not get there.
  The rest has to come from the accumulator spill, the fold's dependency chain and the load-port
  pressure (§2.5, §2.6). A factor of **2.0** is the optimistic end of the range, and it needs the
  repacked kernel to be *better* than the reference on the spill, not merely equal to it.

| matmul speed-up | `ns_matmul` | wall | prompt tok/s | vs llama.cpp (258.1) |
|---|---|---|---|---|
| 1.00× (today) | 2.921 s | 3.407 s | 150.3 | 0.58× |
| **1.63× (llama.cpp's per-core rate)** | 1.792 s | 2.278 s | **224.8** | 0.87× |
| 2.00× (the optimistic end) | 1.461 s | 1.947 s | **263.0** | 1.02× |

Scaled to the bench harness's 154.0 tok/s, the same two rows read **≈ 230 tok/s** and **≈ 268
tok/s**.

So: **S3.4 should take the 512-token prompt from 154 tok/s to between 225 and 265 tok/s**, with
the honest expectation at the lower end — "the prompt runs at llama.cpp's per-core rate" is the
commitment, and the stretch is "the prompt beats llama.cpp". The residual gap to llama.cpp after
the conservative target is `prefill.md` Gap 2 (the serial "other" bucket, 9.3 %) and Gap 3 (the
chunk size, 9-11 %) — both S3.5.

In machine terms:

| | today | llama.cpp | target |
|---|---|---|---|
| int8 MAC/cycle per core (1 thread) | 14.1 | ~23 | 23 |
| share of the measured int8 roof (58.5 MAC/cycle) | 24 % | 39 % | 39 % |
| `vpmaddubsw` per cycle per core | 0.44 | ~0.40 (derived) | 0.7-0.9 |
| activation bytes read per output row per super-block | 256 B | 8 B | 8 B |

The last two rows are the ones to watch. The `vpmaddubsw` rate should rise towards the machine's
~1.83/cycle for the same instruction mix, and the activation traffic should fall by 32× (§2.6).
Neither is directly observable on the baseline host (`perf` is unavailable there), so the
micro-benchmark in §8 is the instrument: a repacked kernel that reaches 0.7 `vpmaddubsw`/cycle at
width 64 is on track, and one that stays at 0.45 is not.

## 8. The A/B plan

Two hosts, per `docs/targets.md`:

| host | CPU | role |
|---|---|---|
| **H2 "bluefin"** | Ryzen 3 PRO 4350G, Zen 2, **AVX2 only**, 8 threads, bare metal | the primary A/B: no AVX-512 confound, quiet, repeatable |
| **H1 "desktop (Zen 5)"** | Ryzen AI 9 HX 370 (Zen 5/Zen 5c), AVX-512, WSL2 | the headline prefill number (the `prefill.md` baseline) and the AVX-512 tier |

Both run the same A/B, interleaved, per `docs/dev/benchmarking.md` rule 2 (A, B, A, B, …, at least
three rounds each; report the median and the spread).

**The switch:** `PEREGRINE_KREPACK=0` (the old kernels) versus the default (the repacked kernels).
`PEREGRINE_NO_WIDE=1` stays as the second control (the old tiled path), and `PEREGRINE_DYNAMIC=0`
is the load-imbalance control `prefill.md` Gap 4 asks for.

**What to measure:**

1. **The kernel micro-benchmark** at the widths that matter — 1, 4, 8, 16, 32, 64, 128 — on the
   real weight rows of the model, one core, `taskset -c 0`. This is where the GEMV/GEMM split and
   the break-even width show up. It is the fastest loop and the one that decides whether the
   GEMV is worth its own PR.
2. **The prompt rate** — 512-token and 4k prompts, 8 threads on bluefin, 12 threads on the
   desktop — against the `prefill.md` baselines (154.0 tok/s on the desktop; the bluefin numbers
   to be captured in the same session so the A/B is on one host).
3. **The decode rate** — the repacked GEMV against `tile_q4_k`, to confirm the win is smaller
   there and to bound the regression risk.
4. **The load time and the RSS** — before and after the repack, on the 1B model.
5. **The exactness** — the KL against the exact f32 path on the bluefin host, using the `kld` tool
   and the method in `docs/dev/accuracy.md`, with the numbers in `docs/targets.md` as the "before".
   And the gate models' greedy tokens, which must be unchanged.

**What would falsify the design:** the micro-benchmark showing the repacked kernel slower than the
old one at width 64 (the prefill width) — that would mean the shuffle traffic costs more than the
amortisation saves, and the whole lever moves to the activation layout instead. And a repacked
kernel whose advantage does *not* grow with the batch width would falsify the activation-traffic
reading of §2.6 (the tile should amortise more as the batch gets wider); if the gain is flat in the
width, the win is the instruction mix alone and the 2.0× stretch in §6 is out of reach.

## 9. Open questions for the orchestrator

1. **The "64 MACs per `vpmaddubsw`" claim.** `prefill.md` §6 Gap 1 states it; reading llama.cpp
   v0.9.0's AVX2 source, a `vpmaddubsw` does 32 byte-MACs and all 32 are useful — the same as
   Peregrine's. 64 is the AVX-512 `_mm512_maddubs_epi16` figure, and the baseline machine has
   AVX2 in both binaries. The gap is real and the lever is the same, but the *reason* is the
   amortisation of the scale multiply, the activation loads and the float fold over eight columns
   (§2.5). Do we correct `prefill.md`, and does S3.4's success criterion become "llama.cpp's
   measured per-core MAC rate" (≈ 23 MAC/cycle, → ~225 tok/s) or "a 2× matmul" (→ ~265 tok/s)?
   *Recommendation: correct `prefill.md`, and take the conservative target (≈ 225 tok/s) as the
   commitment, with 265 tok/s as the stretch.*
2. **Memory: replace the mapping, or keep both?** The repack is size-neutral, so the repacked store
   can *replace* the mapped bytes for the Q4_K tensors (no net RSS growth, ~0.1-0.2 s of load
   time). Or the original stays mapped and readable (the RSS grows by the Q4_K size: 467 MB on the
   1B model). Or the repack is lazy, per matrix, on first use (no startup cost, a first-use
   stall). Do we accept the load-time cost, and is a lazy repack worth the complexity?
   *Recommendation: replace the mapping, repack eagerly at load, and make it switchable.*
3. **Size neutrality vs kernel simplicity: packed or unpacked scales?** Storing the 6-bit scales
   and mins unpacked costs +2.8 % on the Q4_K weights (480 MB vs 467 MB on the 1B model) and
   removes the bit tricks from the inner loop; storing them in ggml's packing keeps the bytes
   identical to llama.cpp's and needs an eight-row `unpack_q4k_scales`. Do we pay the 13 MB?
   *Recommendation: unpacked. The inner loop runs a billion times; the memory is paid once.*
4. **Accepting the fold change.** There is no way to have the 8×8 cross product *and* today's
   eight-lane float reduction: the eight lanes cannot be both "eight sub-block positions" and
   "eight outputs". So the Q4_K result changes in the last bits, the AVX2 and (if it lands) the
   AVX-512 goldens move, and the fold change has to be argued as a re-rounding of the same
   integer-exact expression (§4.2). Do we accept that, or does the orchestrator want the fold
   change kept out of S3.4 (which would mean S3.4 delivers no speed-up)?
   *Recommendation: accept it, with the gate models' token streams checked unchanged as the gate.*
5. **Q5_K in or out?** Q5_K does not appear in the Q4_K_M model's matmul (74 % Q4_K, 14 % Q6_K by
   weight) and needs its own int16 restructuring. With 1.5 pw, is it in or out?
   *Recommendation: out. Put the effort into Q6_K and into proving the AVX2 path.*
6. **Does the AVX-512 tier get a 16-column kernel now?** The AVX-512 branch would use
   `_mm512_maddubs_epi16` (64 byte-MACs per instruction) and 16 columns per tile. It is a
   different kernel, not a wider version of the AVX2 one, and it is not needed for the H2 host.
   If it is out of scope, the AVX-512 tier runs the AVX2 repacked kernel and its goldens move too
   (same values as the AVX2 tier's, since the arithmetic is identical).
   *Recommendation: out of S3.4; the AVX-512 tier runs the AVX2 kernel and aliases its goldens,
   exactly as the AVX-VNNI-256 tier already does.*
7. **Where does the interleaved activation live, and does it fix part of Gap 2?** The interleave is
   across rows, so it belongs in the per-layer batch scratch, not in `QuantAct`. Filling it once
   per layer instead of once per matmul group would also remove the activation quantisation from
   the serial "other" bucket (`prefill.md` Gap 2, 9.3 % of the prefill). Is that in scope for S3.4
   (it falls out of the layout work), or does it stay in S3.5 (which owns the prompt path)?
   *Recommendation: build the buffer in S3.4 because the kernel needs it, but leave the *filling*
   policy (once per layer vs once per ubatch) to S3.5, and do not claim the Gap 2 win here.*
8. **The tail rows.** A matrix whose output-row count is not a multiple of eight cannot be tiled.
   Do we (a) not repack such a matrix at all (the whole matrix uses the old kernel), or (b) repack
   the aligned prefix and keep a small tail buffer for the rest? (a) is simpler; (b) is faster for
   the affected matrices.
   *Recommendation: (a). Most models' dimensions are multiples of eight, and (a) keeps one code
   path per matrix.*
9. **The gate for "the same tokens".** ADR 0003 says the default path gives the same tokens as the
   exact reference for a fixed seed. The fold change moves the logits in the last bits. Do we
   require the *gate models' greedy token streams* to be unchanged (a check on nine Q4_K_M models),
   or is the KL budget (≤ 1e-4) the whole test?
   *Recommendation: both — the KL is the budget and the token streams are the binary gate.*
10. **The activation traffic `prefill.md` does not count.** §2.6 works out that the prefill reads
    about 507 GB of activation codes per prompt — one byte per int8 MAC, a hundred times the
    weight traffic — because the prefill path works one output row at a time. That is ≈ 150 GB/s
    of L1/L2 reads, which is below the machine's L1 capability but far from free, and it is not in
    `prefill.md`'s accounting at all. The repacked tile cuts it 32×. Two consequences: the
    "the prefill is compute/issue-bound, not bandwidth-bound" conclusion in `prefill.md` §6 needs
    qualifying ("not *DRAM*-bound"), and the conclusion that the *weight decode* is not the
    bottleneck ("`PEREGRINE_NO_WIDE=1` costs only 3.9 %") now reads differently — the weight decode
    is not the bottleneck, but the *activation* re-read is. Does S3.4 own the correction, or does
    it go with the prefill note's own follow-up?
    *Recommendation: correct `prefill.md` in the same PR as this note, and add the activation
    traffic to `StepStats` (a counter of activation bytes read) so the claim is measured rather
    than derived.*

## 10. Decisions (orchestrator review)

1. **`prefill.md` is corrected in this PR.** The 64-MACs figure is the AVX-512 kernel's, and the activation
   traffic belongs beside it. The target is llama.cpp's measured per-core rate (≈ 225 prompt tok/s on the
   desktop's Llama-3.2-1B Q4_K_M); 265 is the stretch.
2. **The repacked store replaces the file's bytes for those tensors**, like the PQ2_0 `TileStore`: the
   mapped pages of a repacked tensor are never touched after the repack, so they don't stay resident.
   Measure the RSS in PR 1 to confirm it. The extra 0.1–0.2 s of load time is accepted.
3. **Unpacked scales**, for the simpler kernel; the 2.8 % memory is accepted.
4. **The fold change is accepted** under ADR 0003. Lossless here means deterministic per tier, the same
   row result at any batch width, every invariance test passing, the synthetic oracle checks within their
   tolerance, and the KL against llama.cpp no worse than today's within its error, re-measured on bluefin
   for every real model with Q4_K/Q6_K tensors. The goldens that move are re-recorded in the same PR.
   Greedy tokens of the real models may differ at near-ties; the KL is the gate, not "tokens unchanged".
5. **Q5_K is out** of this item (PR 4's Q5_K moves to a later step); **Q6_K is in** (PR 3).
6. **AVX-512 runs the AVX2 kernel** for now. A 16-column variant comes later, after its own A/B.
7. **The interleaved activation and its once-per-layer fill come with S3.4**, because the kernel needs
   them. Spreading the other serial work over the threads stays in S3.5.
8. **Tail rows** (the rows past a multiple of 8) keep today's kernels, in decode and in prefill alike, so a
   row's result depends only on its index, never on the batch.
9. **The gate** is decision 4's list, plus the decode A/B: decode must not get slower on either machine,
   since batch invariance moves decode onto the repacked GEMV too.
10. **`StepStats` gains an activation-bytes counter** in PR 2, so the 32× claim is measured, not inferred.

**2026-11-07 — the AVX-512 tier's default, after the decode A/B.** The repacked Q4_K kernel stays on
by default below AVX-512 and is **off by default on the AVX-512 tier**
(`x86_64-avx2-avx512-vnni-gfni-vbmi`). That tier runs the AVX2 repacked kernel (§9 Q6), and on the
desktop's Llama-3.2-1B Q4_K_M the A/B measured prefill **+24.9 %** but decode **−3.5 %** against the
old kernel — so decision 9 ("decode never slower") stands as written and the AVX2 kernel does not
ship as that tier's default. At the `avx2` tier the same repack costs **−1.4 %** decode, which the
prefill win pays for, so it stays on there. An AVX-512 (16-column) repacked kernel is the follow-up,
in its own PR, with its own A/B; if it lands it becomes that tier's default and its goldens move.
The `avx2`-tier figure is just outside the ~1 % band the desktop's null A/Bs show, and bluefin and
H0 measure decode parity (bluefin, Llama-3.2-1B: 39.1 → 38.2 tok/s, inside the run spread; Qwen3.5-2B
24.1 → 24.1), so the AVX2 default stays on.
`PEREGRINE_KREPACK=1` / `0` still overrides the default in both directions, and `peregrine tier`
prints which applied (`kq_repack off (AVX-512 tier default)`). The store is not built at all where
no kernel reads it. The AVX-512 goldens are therefore the non-repacked values: the synthetic Q4_K
goldens are main's, and the real-model AVX-512 goldens equal the old AVX2 values below the tier line.

**2026-11-07 — how far the fold moves real-model logits (bluefin).** With the repack on, a real
model's logits move far more than "the last bits": on a 16-token prefill, median |Δlogit| 0.056 on
Llama-3.2-1B (max 0.58) and 0.28 on gemma-3-1b (max 4.1), and greedy tokens differ on 6 of 12
model/prompt pairs. This is amplification, not a kernel error:

- **One matmul.** On real Q4_K matrices, with the same activations, the old and repacked kernels
  evaluate the same `Σ_sb dk·(d·S − dmin·M)` with the same integers. They differ by a few ulps of
  the sum (worst 4.3e-6 absolute). The repacked fold is the nearer to an f64 reference in 49 of 51
  Llama cases and 10 of 12 gemma cases, with a worst relative error about 4× smaller, because it
  reduces in int32 before converting. Old `wide` ≡ old `tile`, and repacked GEMV ≡ GEMM, bit for bit.
- **The stack.** The layer-0 drift is at rounding level (4.6e-7 Llama, 1.2e-7 gemma), and it grows
  about 1.2–1.4× per layer. A 1-ulp change to every element of `blk.0.attn_norm.weight`, on the old
  path, moves the logits *more* than the whole fold change does (rms 0.138 vs 0.094 on Llama; 0.82
  vs 0.54 on gemma). A 1-ulp change to `output_norm.weight` moves them by one ulp, so the
  measurement is sound.
- **The KL against llama.cpp is flat** (20 chunks, the same base for both): Llama-3.2-1B 0.002416 →
  0.002434, Qwen2.5-0.5B 0.003470 → 0.003452, gemma-3-1b 0.005885 → 0.006118 (about one standard
  error).

So "the logits move in the last bits" holds per matmul, not per model. `tests/kq.rs`'s end-to-end
bound (`1e-3·max(|x|,1)`) passes only because the synthetic model's random weights don't amplify;
the per-matmul ≤ 1-ulp checks in `kqsimd.rs` are the kernel's real bound.

## 11. The Q5_0 tile (2026-11-08)

Qwen2.5-0.5B and SmolLM2-360M are "Q4_K_M" files whose `d_model` (896 and 960) is not a multiple
of 256, so llama.cpp's quantizer falls most of their matrices back to Q5_0. That format had no
repacked kernel, and the phase measurement in `/var/tmp/report-05b-prefill.md` put it at 100–104
G MAC/s against 236 for the repacked k-quants — the whole of the 0.5B's prefill deficit. This
section is the Q5_0 analogue of §3.

### 11.1 The layout

Q5_0's block is 32 weights in 22 bytes (`f16 d`, `u8 qh[4]`, `u8 qs[16]`), so the tile is built per
block rather than per 256-weight super-block. Eight rows make **176 bytes**, exactly `8 × 22`:

```text
0    d      the eight rows' f16 block scales       16 bytes
16   qh     the eight rows' fifth bits             32 bytes
48   qs     the eight rows' nibbles               128 bytes
```

* `qs[window * 64 + row * 8 + k]` is row `row`'s nibble byte `k` of physical window `window`
  (`0` = the file's `qs[0..8]`, `1` = `qs[8..16]`). The file stores each of the sixteen bytes once,
  so the tile does too: logical eight-weight groups `0` and `2` are the low and high nibbles of
  window `0`, groups `1` and `3` the low and high nibbles of window `1`.
* `qh[group * 8 + row]` is row `row`'s eight fifth bits for logical group `group`; bit `k` is
  weight `8·group + k`. This is the one deliberate change from the file's layout: instead of a
  32-bit word per row, the bits are grouped by eight-weight window, one byte per row per group.
  A group is then exactly one byte per row, which the kernel spreads with two `vpshufb`s per
  32-byte half — the byte a row needs is already the byte the shuffle selects. Spreading the
  file's 32-bit word per row would cost a full expansion per row per block.

The activation needs **no new layout**. Q5_0's scale is per 32 weights, which is exactly
`QuantAct::q`/`d`/`sums`; the kernel reads the per-32 layout the decode path already builds, so
there is no `KqActs`-style interleave and no 256-alignment requirement. That is also why the
GEMV and the GEMM are one code path (§11.3).

### 11.2 The AVX2 kernel

One block is eight output rows × 32 weights = 256 byte-MACs, so the minimum is eight
`vpmaddubsw`; the tile reaches it. For each of the two physical windows the kernel loads two
32-byte vectors (rows 0–3 and 4–7, eight nibbles each) once, then reads them as low and high
nibbles for the two logical groups. Per group it spreads the fifth bits, ORs them into the
nibbles, and runs two `vpmaddubsw` per activation. Four groups accumulate in int16; the bound is
**8 products per int16 lane = 8 · 31 · 127 = 31 496 < 32 767** (`the_q5_0_int16_stage_has_headroom`).
One `vpmaddwd` per half and one `vphaddd` turn the block into eight int32 row sums; the bias
`16·Σq` is subtracted exactly in int32, and the block's fold is

```text
acc[r] = (d[r]·dk) · (S[r] − 16·Σq) + acc[r]      (one f32 multiply, then one FMA)
```

The eight lanes of the accumulator are the eight output rows (permuted by `vphaddd`'s lane order),
so there is no per-row horizontal reduction and no 64-float spill. The kernel is one const-generic
over the activation count `N`; the GEMV is `N ≤ 3` and the GEMM `N ≥ 4`, and both instantiate the
same per-(row, activation) expression, so they are bit-identical by construction. The batch width
changes only how many independent rows ride along.

The kernel reads the activation once per eight output rows instead of once per row: the measured
activation traffic of the 0.5B's 512-token prefill falls from 278.6 GB to 90.1 GB
(`StepStats::bytes_acts`), the 8× the tile is worth plus the k-quant share.

### 11.3 Gating, tails and goldens

The switch is the existing one: `kq_tiles` is `have_batched() && PEREGRINE_KREPACK`, on by default
below the AVX-512 tier and off on it (decision 10). `MatPath::KqTiles` now covers `Q5_0` as well as
`Q4_K`; a matrix whose output rows are not a multiple of eight keeps today's kernel on the rows
past the last whole tile, so a row's result depends only on its index. The store is size-neutral,
so decode streams the same bytes.

The AVX2 Q5_0 synthetic goldens move (the fold is the same real number, re-rounded; the greedy
tokens are unchanged on the synthetic models). The AVX-512 goldens do not, because that tier's
default keeps the repack off.

### 11.4 With the eight-row decode kernel

The Q5_0 tile and #104's eight-row Q5_0/Q8_0 decode GEMV overlap on the same format, so the two
paths have to be exclusive and each has to be complete on its own:

* with the repack on (the default below the AVX-512 tier), a Q5_0 matrix takes `MatPath::KqTiles`
  for every whole group of eight rows, at every batch width; the rows past the last group use the
  ordinary per-row kernel. The eight-row dispatch in `MatPath::PerRow` never sees a repacked Q5_0
  matrix, so a row is computed by exactly one of the two layouts.
* with the repack off (the AVX-512 tier's default, or `PEREGRINE_KREPACK=0`), the matrix is not in
  the store: decode (`nb == 1`) goes through `simd::q5_0_rows8`/`q8_0_rows8`, and prefill keeps
  `dot_batch`. Q8_0 has no repacked layout, so its decode always takes the eight-row kernel.

Both paths are bit-identical to their own one-row reference (`q5_0_rows8` matches `tile_q5_0::<1>`;
the tile's GEMV matches its GEMM), and the dispatch-layer test
`a_row_is_bit_identical_across_batch_widths` pins the `dot_batch` widths. `PEREGRINE_PROF2=full`
attributes the tile's time to `fmt Q5_0` like the per-row kernel's, because the format timer wraps
the whole per-job range in `matmul_group`, whichever path it took.

On bluefin, 5 alternating rounds against #104's head (main + #104), the combination keeps both
gains: Qwen2.5-0.5B prefill 271.7 → 458.2 tok/s at 512 and 206.5 → 299.8 at 4096, decode 71.6 →
83.6 and 58.8 → 65.5; SmolLM2-360M 299.1 → 436.5 / 199.9 → 261.1 prefill and 88.4 → 109.8 / 57.3
→ 64.5 decode; Llama-3.2-1B flat (206.3 → 207.4 / 156.5 → 157.0 prefill, 46.8 → 46.9 / 37.2 →
37.2 decode). The decode figures are above #104 alone because the tile streams the weights as one
sequential eight-row tile rather than eight row streams.
