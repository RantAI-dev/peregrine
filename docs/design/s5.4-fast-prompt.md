## 0. Summary

ik_llama.cpp processes prompts faster than Peregrine on AVX-512 (Peregrine at 0.52–0.64 of
it, `docs/benchmark.md`), and §11 of the prefill study found why: for a wide pass it re-rounds
each 256-weight block of a Q4_K or Q6_K row onto a new 8-bit grid and runs a kernel that needs
no per-32-weight scale multiply and no minimum term. That kernel reaches 91 GMAC/s where the
exact Q4_K kernel is at its ceiling of 74–76 (the core's limit is 121). The re-rounding is an
approximation: the fork's own logits move by 0.0011 nats of mean KL divergence between a narrow
and a wide pass, and its top token changes on 2.1 % of positions.

Peregrine's default stays exact (ADR 0003). This design adds the same trade as an **explicit
option, off by default**: `--fast-prompt`. With it on, prompt tokens are read with the 8-bit
form of the weights; generated tokens are still computed with the exact weights. The option
ships with an accuracy report, as ADR 0003 requires of every lossy feature.

## 1. What the option changes, and what it does not

**Changes.** While `--fast-prompt` is on, every weight pass that carries *prompt* rows (the
prefill of a chat, completion or decision request) computes the Q4_K and Q6_K matrix products
from the 8-bit form defined in §2 instead of from the file's own codes. Since S5.4j, on the
tiers whose table says so (AVX-512), a prompt row's **attention** is also computed in the
mode's own summation order (§5k): a tiled order of the same sums, whose rounding difference is
orders of magnitude below the form's. A row's scores, soft-max denominator and value mix are
then a function of that row's own visible key range alone — never of the batch, the prefill
chunk, the pass budget or the pool — and everything that is not a fast prompt row keeps the
exact engine's attention bit for bit, on every tier.

**Does not change.**

- The default. Without the option nothing in the engine differs by a bit from today.
- Decode. A pass that carries only generated tokens uses the exact kernels. Given the same
  cache contents, sampling, speculation and the drafter behave exactly as they do today.
- Embedding and rerank passes, the float formats, Q8_0, Q5_K, the ternary formats, and Q5_0 on
  the tiers whose table does not select it (on aarch64's `dotprod`/`i8mm` caps it does since
  S5.4h, §5h; no x86 tier does, §6).
- The attention of every row that is not a fast prompt row, and the attention of every row on
  AVX2, aarch64 and scalar (S5.4j, §5k). A model whose formats are all outside the tier's
  table stays the exact engine bit for bit, attention included.
- The chat template, the tokenizer, the sampler.

## 2. The 8-bit form

Per matrix row and per 256-weight super-block, exactly the fork's `q8_k_r16` arithmetic
(`docs/design/s5-prefill-avx512.md` §11.1), so the two engines' fast modes are comparable:

1. dequantise the block's 256 weights to f32 with the format's own formula, each sub-block in
   file order. Q4_K's is `w = q·Ld·d − dmin·Lm` with the fork's own operation order: `q·Ld` is
   an exact int16 product, `(−dmin)·Lm` one f32 multiply, and the weight one f32 fma. Q6_K
   never forms an f32 weight: its products are the int16 `(q − 32)·L` — the six-bit code is
   *signed*, the format's `−32` offset is inside the product — and the block's `d` enters only
   the scale;
2. `m = max |w|` over the 256 weights; `scale = m / 127` (f32, a division). An all-zero *Q4_K*
   block has scale 0 and codes 0 (Q6_K's all-zero block takes item 4 and keeps `scale = d`);
3. `code_i = round_to_nearest_even(w_i · (1/scale))`, an int8 in `-127..=127`, with the
   reciprocal rounded to f32 first — the fork multiplies by a rounded reciprocal, it does not
   divide (`PackerQ80::convert`, `iqk_gemm_kquants.cpp:16-26`, `:2464-2466`);
4. Q6_K's exact case is kept: when `max|p|·(1/127) < 1` — i.e. the block's integer products
   `(q − 32)·L` all fit in int8 — the codes are those products and `scale = d · 1 = d` (no
   rounding at all).

A product is then `Σ code_i · a_i` in integers over the block, times `scale`, times the
activation scale: one multiply per (row, block) where the exact kernel has one per 32 weights
plus a minimum term.

The **scalar twin is the definition** (ADR 0005): a plain loop that builds the form and one
that multiplies with it. Every SIMD body (AVX-512 first, then AVX2 and NEON) must equal it bit
for bit. The integer sums are exact in any grouping, so this is a statement about the epilogue
only, and the three tiers can agree with each other as well; the goldens stay per tier anyway.

**Where the form lives** is an implementation choice the first build step measures (§5): a
resident copy built at load (one byte per weight more memory: about +1.2 GB for a 1B Q4_K_M
file, cacheable in the packed-weight cache), or a conversion of each tile inside the pass (no
memory, a cost per pass that only wide passes amortise; this is what the fork does). The
results are identical either way; only speed and memory differ.

## 3. The guarantees in fast mode

ADR 0003's default guarantee has four parts. With `--fast-prompt` on:

| Guarantee | Default | With `--fast-prompt` |
|---|---|---|
| Same tokens as the exact reference path | yes | **no**: by how much is the accuracy report (§4), not published until S5.4c |
| A request's result does not depend on batch size, chunk size, pass budget, other users or thread count | yes | **yes, within a tier**: a format the tier's table selects is 8-bit for prompt rows at *every* pass width (the fork only switches above 32 rows, which is why its results depend on `-ub`), and a matrix without a form takes the exact kernel at the exact engine's own block widths, so a row's bits never depend on the batch |
| The same tokens on every CPU tier, up to the tier's golden | yes | yes, with a fast-mode golden per tier **where the tier selects a format**; where it selects none the mode is the exact engine bit for bit and the test asserts that |
| A conversation continues the same whether its beginning was restored from the cache or read again | yes | **no**: a token that was *generated* has an exact cache entry, and the same token read again as *prompt* (after the prefix store dropped it, or on another server) gets the 8-bit one |

The last row is the one new kind of difference, and it is inherent in the trade: making it go
away would mean decoding with the 8-bit form too, which is slower for decode (twice the bytes
per weight through a memory-bound pass). It is stated in the option's help and in the report.

**S5.4f restates the tier guarantee.** Which formats take the form is a property of the CPU
tier, read from one table (`MatKernels::q8k_uses_form`): AVX-512 takes Q4_K and Q6_K (unchanged
by S5.4f), AVX2 takes Q6_K only, aarch64 takes Q4_K and Q6_K on every cap and, since S5.4h,
Q5_0 where its multiply is a NEON body (`neon-dotprod` and `neon-i8mm`), and on x86 a tier with
no SIMD body takes none. **S5.4j adds one more per-tier property to the same table**
(`MatKernels::fast_attn`): whether a prompt row's *attention* takes the mode's own order. AVX-512
does; AVX2, aarch64 and scalar keep the exact engine's attention for prompt rows, so their
fast-mode goldens did not move. The mode's bits
therefore depend on the tier — as the exact engine's bits already do (§5b's per-tier goldens) —
and on nothing else: within a tier they are independent of batch, chunk, pass budget, other
users and threads. The attention order's half of that is pinned by
`fast_mode_is_prompt_invariant` (every chunk of 16…128, 1/2/4 threads, alone and beside a
decoder), its new 4 096-token sibling, a kernel-level test that a fast row's output is its own
at every group size and pool width, and the twin-vs-body tests on the full length grid (§5k). Generated rows, embeddings, rerank and decisions stay exact on every tier;
`peregrine tier` and the server's startup line name the formats this CPU takes, and say so when
the set is empty and the option changes nothing.

The option is a property of the server or the command, not of a request: all requests of a
process see the same mode, so the prefix store never mixes caches of the two modes. A packed
8-bit copy on disk is keyed by the file's hash and the form's version.

## 4. The accuracy report (required before it ships)

On the gate models of `docs/targets.md` that have Q4_K/Q6_K matrices (Llama 3.2 1B, Qwen 2.5
0.5B, SmolLM2 360M, Gemma 3 1B, Qwen 3 1.7B; all Q4_K_M), 40 chunks of 512 tokens of wikitext-2
with the `kld` tool (`docs/dev/accuracy.md`), each chunk read as a prompt:

1. fast mode against Peregrine's exact mode: mean, median and 99 % KL divergence, RMS Δp, same
   top token;
2. both modes against the unquantised (F16) model, so the report says how much of the Q4_K_M
   error budget the option spends (the fork's is 44 % on the 1B);
3. the task-accuracy suite (`benchmarks/accuracy/`) with the option on and off;
4. the tool-calling comparison (`scripts/tool-e2e.py`) on Qwen 2.5 0.5B with the option on:
   the same calls or not.

**Bound to ship:** mean KL divergence of fast against exact no worse than **0.0040** on the 1B,
the same top token on at least **96 %** of scored positions, and no task-accuracy score outside
the paired test's noise. (Re-baselined by S5.4j, on the project lead's recommendation, to the
arithmetic the mode implements: the `q8_k_r16` form of §2 measures **0.0035** on the 1B, and
ik_llama.cpp's own `-rtr` path, which is that arithmetic, measures **0.0034** in its own
binary. §5c's 0.0015 came from a measurement of the fork's *other*, finer wide path. **The
owner's confirmation of the re-baseline is pending**, so the option keeps its "Experimental"
label in every help text and in the README until it lands.) The numbers go in `docs/targets.md`
beside the KV-cache precisions, and the option's help text quotes the 1B's.

*(S5.4c, 2026-11-12: **the 0.0015 half was not met — 0.003514 was measured — and it is the
bound that is wrong, not the form.** The 0.0011 this was taken from is §11.2's `-ub 16` vs
`-ub 512` measurement with `-rtr` off, which in the fork is a `Q8_1`/`Q8_0` conversion (one
scale per 32 weights); the `q8_k_r16` arithmetic §2/§5a implements is the fork's `-rtr`
path and measures 0.003401 on the same file and corpus, against Peregrine's 0.003514. The
"44 %" has the same origin: its divisor, `docs/targets.md`'s 0.00248, is Peregrine against
llama.cpp on the same file, not a distance from the unquantised model. §5c has the tables,
the control experiment and what a re-baseline would mean; the decision is the owner's.)*

## 5a. As built: the kernel, and what it costs (S5.4a)

Built 2026-11-12 on the desktop. The form, its scalar twin, the AVX-512 bodies of both, and a
`kqbench` mode that measures them; nothing is dispatched (`crates/peregrine-kernels/src/kq8.rs`,
`kqsimd.rs`'s `q8k_*`, `KQBENCH_PROMPT=1`). Raw numbers, the conformance harness and the exact
commands: `benchmarks/results/desktop-zen5-2026-11-12-s5.4a/`.

**The layout.** Eight output rows of a matrix are interleaved per 256-weight super-block, the
way the engine's `Q4K8` tile interleaves them, because the AVX-512 kernel's weight operand is
one 512-bit load per (eight-weight group, activation row): eight rows × eight codes. One
super-block of the form is 2112 bytes — 2048 of codes (`qs[group·64 + row·8 + k]` is weight
`group·8 + k` of row `row`, stored as the fork's `code + 128` so `vpdpbusd` can take it as its
unsigned operand), the eight rows' f32 scales, and 32 bytes of padding that keep every 64-byte
load on one cache line. One weight costs **1.03125 bytes**, against the file's 0.5625 (Q4_K)
and 0.8203 (Q6_K). Q5_0's form is the same object built from its 32-weight blocks, one scale
per 256 weights, so one kernel multiplies all three.

**The multiplication.** `vpdpbusd` over the biased bytes; the bias is paid back once per
(row, super-block) as `−128 · Σa` in int32 lanes, where `Σa` is the activation's
whole-super-block sum (`KqActs::sum256`, which the exact kernels do not read); then one
`d · dk` multiply and one fused multiply-add per (row, block). The integer lanes cannot
overflow: a lane sees 32 instructions of four products, `128 · 255 · 127 = 4 145 280`, and
`vpdpbusd` wraps rather than saturating six orders of magnitude above that. Eight activation
rows per group is the widest that keeps the sixteen accumulators and the scale vector in the
ZMM file — the same budget the exact Q4_K tile kernel uses, and the same eight.

**The measurement** (one thread, 2048 × 8192, 1024 tiles, load 8.3, MONOTONIC 10 % fast so
every GMAC/s is ~10 % conservative; exact = today's kernel, resident = the form built once,
per-pass = built inside the pass):

| format | 1 act | 8 | 16 | 64 | 128 | 512 |
|---|---|---|---|---|---|---|
| Q4_K exact | 33.6 | 65.3 | 62.7 | 63.2 | 74.4 | 66.2 |
| Q4_K resident | 22.0 | 85.3 | 73.6 | 84.0 | 95.5 | 91.9 |
| Q4_K per-pass | 1.6 | 10.6 | 18.6 | 45.4 | 68.3 | 82.1 |
| Q6_K exact | 18.8 | 39.7 | 38.9 | 43.3 | 46.7 | 45.3 |
| Q6_K resident | 19.4 | 92.2 | 73.4 | 83.2 | 89.0 | 90.1 |
| Q6_K per-pass | 1.4 | 10.0 | 17.0 | 42.8 | 61.1 | 79.9 |
| Q5_0 exact | 21.4 | 42.4 | 49.0 | 49.2 | 45.1 | 42.9 |
| Q5_0 resident | 22.0 | 87.3 | 81.5 | 89.8 | 92.2 | 90.6 |
| Q5_0 per-pass | 1.5 | 10.0 | 20.9 | 51.7 | 62.1 | 81.8 |

GMAC/s/core. The conversion runs at 1.4–2.0 G weights per second, and §10/§11's number for
the fork's own kernel at this shape is 91 GMAC/s at 512 activation rows: the resident form
measures 91.9.

From that table:

- the resident form is **ahead of the exact kernel at every width above eight rows** (+17 % to
  +132 %), and *behind* at one row, where the pass is bandwidth-bound and the form's 1.03
  bytes per weight cost Q4_K 35 %;
- the per-pass form **overtakes the exact kernel at about 128 rows** (−8 % for Q4_K at 128,
  +31 % and +38 % for Q6_K and Q5_0, +24/+76/+91 % at 512) and is far behind below it;
- **a resident form costs 1.187 GiB on Llama 3.2 1B Q4_K_M**, whose Q4_K/Q6_K/Q5_0 tensors hold
  0.745 GiB: +0.38 bytes per weight, +0.44 GiB — cheaper than the +1.2 GB guessed above,
  because a Q4_K_M file is not 0.56 bytes per weight all the way through.

**Recommendation** (the owner's call): build it **resident**, in the packed-weight cache, keyed
by the file's hash and the form's version. It is the faster of the two at every width the mode
is for, it needs no conversion in the token path, and 0.44 GiB on the 1B is the price. The
per-pass conversion is the fallback only if that memory is not available, and with the build as
it stands it would need to be four times faster before it competed below 128 rows.

**The conformance.** Peregrine's codes and scales are identical to the fork's arithmetic on
1 441 792 weights of the real 1B file (Q4_K and Q6_K, six tensors, `cmp` of every scale and
every code). The intended oracle — the fork's own exported conversion, called from a C harness
linked against the cached `libggml.so` — returned `true` and wrote zeros for every input tried,
including a hand-built four-row block whose only possible output is ±945 codes, so the
comparison is against a transcription of the fork's source lines with a correctly-rounded
`fmaf` (`fork_requant.py`). That is a finding about the cached build, recorded in the results
README, and it is the one open question this step leaves: the two engines' fast modes are
comparable in arithmetic, but not through the fork's binary.

**The re-rounding error**, measured on both models and over every Q4_K/Q6_K/Q5_0 tensor: mean
0.0018–0.00197 of the super-block's maximum, worst 0.00394 (**the bound, `max/254`, reached**),
0.4 % of Q4_K weights exactly on the grid. Q5_0's worst and mean are the same as the
k-quants'. No Q6_K block of either model is in the fork's exact case: its weights are never all
below 1.0 in a 256-weight block. Which leaves §4's bound (mean KLD ≤ 0.0015 on the 1B) where
the fork's own 0.0011 says it will land, and nothing here moves it.

## 5b. As built: the option, the dispatch and its cost (S5.4b)

Built 2026-11-12 on the desktop. The form is **resident** (§5a's recommendation): built once
per Q4_K and Q6_K matrix when the option is on and kept in memory. The per-pass conversion is
not wired in. Raw numbers and the exact commands:
`benchmarks/results/desktop-zen5-2026-11-12-s5.4b/`.

### The option

`PEREGRINE_FAST_PROMPT=1` (`--opt FAST_PROMPT=1`), plus `--fast-prompt` on `peregrine serve`,
`run` and `bench`. It is an ordinary entry of `crates/peregrine-core/src/options.rs`, off by
default, recorded by `pairs()` — so `/metrics`' `peregrine_option{name="fast_prompt"}`,
`peregrine tier`, `peregrine inspect` and `bench --json` all carry it. The process's option is
the engine's (`Engine::build`), so every model of a multi-model server sees the same mode. A
server logs one line at start; on a tier without a SIMD body the line says that the mode runs
through the scalar twin.

### Where the row flag comes from

The flag travels on the activation row: `QuantAct::prompt`, set by
`Model::forward_rows_marked` (and `forward_marked`) from a slice the engine builds, one flag
per token. `State::acts` is reused across layers and `QuantAct::fill` does not touch the flag,
so the same mark reaches every layer's matmuls of the pass.

* `Engine::prefill_chunk` marks every row of a token slot's chunk.
* `Engine::step`'s mixed pass marks the `n_dec` leading decode rows false and each prefilled
  chunk true (the pass is built decode rows first, then prompt chunks).
* `Engine::decode` and the verification pass mark nothing (`Model::forward_rows` clears every
  flag).
* Pooled (`Want::Pooled`), label (`Want::Labels`) and classifier-head (`Want::Head`) slots are
  never marked, even when their prompt shares the pass; `Model::forward_texts` (embeddings,
  rerank, decisions) clears every flag too. Drafter and MTP forwards have their own state and
  never see a mark, so they are decode.
* A model loaded without the form (the option off) has `TensorInfo::q8_off == None` everywhere,
  so a mark would be a no-op; the engine does not mark either.

### The dispatch

`blocks::linear::matmul_group` splits a pass into runs of one row kind when the pass is mixed
and any matrix of the group carries a form. Each run goes through `matmul_block` as if it were
alone, and a row's kernel depends only on its own flag: **a prompt row is 8-bit at every pass
width and chunk size, a generated row is exact at every width**, whatever else is in the pass.
Two kernels are chosen inside `matmul_block`:

* the repacked k-quant path (`MatPath::KqTiles`) and the per-row path (`MatPath::PerRow`) —
  the latter is where Q6_K lives on x86 — compute whole runs of eight rows from the form with
  `MatKernels::q8k_gemm`, and a matrix's tail rows (past the last whole run) stay exact;
* every other format keeps its kernel. Q5_0, Q5_K, Q8_0, the ternary and float formats have no
  form in this step.

`q8k_gemm` is the AVX-512 `q8k_gemm_zmm` on that tier, the AVX2 `q8k_gemm_avx2` on the AVX2
tier (§5d); S5.4d's NEON bodies exist (§5e) and S5.4e wires them into this dispatch: since then
aarch64 with `dotprod` runs them (§5f). Every other tier takes the scalar twin `kq8::gemm_q8k`.
The interleaved activation is filled for a
fast run at any width (`KqActs::fill_with`), and its whole-block sums are computed only then:
with the option off the exact kernels do exactly the bit of work they did before S5.4a.

One pass-size change was needed for the wide chunk: `MAX_BATCH` (the driver's scratch width)
is 512 and `DEFAULT_BATCH` (what one kernel call takes when the fast mode is not in play) is
still 128. A marked pass may therefore be 512 rows wide; every other pass keeps the split it
had, so the default mode's kernels see the same calls as before.

### The resident form's cost

Built at load from the file's own bytes (`crates/peregrine-core/src/q8form.rs`), so it does
not depend on `PEREGRINE_KREPACK` and a scalar tier gets it too. On Llama 3.2 1B Q4_K_M
(96 Q4_K + 17 Q6_K matrices, 762.6 MiB of weights) the form is **957.0 MiB** (measured by
`PEREGRINE_FAST_PROMPT=1 peregrine inspect`), and the load costs **0.52 s** with the AVX-512
builder against 1.29 s without the form (one run each, 1-minute load 8.4; the scalar twin
would take about 26 s). The form is not in the packed-weight cache in this step: S4.9e's file
header has room for two stores and a third would need a new version, while the build is half a
second. That entry is a follow-up.

The design guessed +1.2 GB; the measured +0.94 GiB is smaller because a Q4_K_M file's Q4_K and
Q6_K run at 0.56 and 0.82 bytes per weight rather than one number.

### The first generated token's row

The engine leaves a token slot's last prompt token for the first decode step
(`Slot::prefill_len` is `prompt.len() - 1` for `Want::Tokens`). So the logits the first
generated token is sampled from come from the **last prompt token, computed as a decode row:
exact** (§1's decode rule), whose attention reads the 8-bit K/V the prompt wrote. §5's brief
expected that row to be an 8-bit row; the design and the engine both say exact, and that is
intended: the first generated token is affected by the form through the cache, not through its
own row. A prompt row that wants logits directly (`forward_marked`, a label slot's row) is
8-bit when marked, as are the head's rows for it.

### The tests

`crates/peregrine-models/tests/fast_prompt.rs` (synthetic models, no model files):

* the cache and the logits after a prompt are bit-identical at chunks 16, 32, 64 and 128, at
  1, 2 and 4 threads, and at every chunk beside a decoding user's rows in the same passes;
* decode from a cache a fast-mode prefill produced equals the default engine's decode from the
  same cache (tokens and logits), on Q4_K and Q6_K;
* the prompt's logits are **not** the exact mode's, so the option cannot silently do nothing;
* every re-rounded weight is within `max|w| / 254`, checked end to end through the engine's
  load path on one real matrix of the synthetic file (Q4_K and Q6_K, >100 000 weights);
* embeddings (pooled) and decisions (labels) are bit-identical with the option on and off, on a
  model that carries the form;
* two slots, one prefilling and one decoding in the same passes, each get the tokens they get
  alone in the same mode;
* the prefix store: a prompt restored from it gives the same tokens as the same prompt read
  again (both are prompt rows), and the documented exception is pinned — a token whose cache
  entry was written by a generated (exact) row and the same token read as a prompt (8-bit) give
  different caches.

`crates/peregrine-models/tests/synthetic.rs` adds fast-mode goldens for one Q4_K and one Q6_K
synthetic model under `tests/golden/synthetic/<tier>/llama-<fmt>-fast.golden`, recorded on the
three x86 tiers (native AVX-512, `PEREGRINE_ISA=avx2`, `PEREGRINE_ISA=scalar`). The Q4_K
goldens are identical on all three; the Q6_K ones agree in argmax and greedy tokens but not in
the logits hash between scalar and AVX2, because the prompt's logits still pass through kernels
the form does not replace (the tier's exact decode rows, the head's tail rows and the tier's
norm/attention paths). The 8-bit form itself is tier-independent.

## 5d. As built: the AVX2 body (S5.4d, x86 half)

Built 2026-11-12 on bluefin (Ryzen 3 PRO 4350G, Zen 2, AVX2 + FMA, no AVX-512, no AVX-VNNI).
The body, its builder and the dispatch; raw numbers, commands and the other engines:
`benchmarks/results/bluefin-2026-11-12-s5.4d/`.

### The formulation

`vpdpbusd` is the AVX-512 body's whole trick, and AVX2 has nothing like it: `vpmaddubsw` gives
32 products per instruction and **saturates** its int16 result. The stored byte is `code + 128`
(1..255, so `vpdpbusd` can take it as its unsigned operand), and against an activation of
`127` two products reach `2 · 255 · 127 = 64 770` — twice int16. The AVX-512 bound does not
carry over, so the AVX2 body uses the `vpsignb` sign trick llama.cpp uses for its int8 × int8
dot product:

1. `ws = w − 128` recovers the signed code from the biased byte. The add is exact: the stored
   byte is `code + 128` in a byte, and `+128` is `^0x80`, so subtracting 128 mod 256 gives the
   code back for every code, `−128` included;
2. `wa = |ws|` as bytes, i.e. 0..=127 — and 128 for `code = −128`, where `vpsignb`'s result
   wraps to `0x80` and is read as the unsigned byte 128, which is still inside the bound;
3. `sa = sign(a, ws)`, the activation with the code's sign applied;
4. `vpmaddubsw(wa, sa)` is then `|c| · sign(c) · a = c · a` per pair, and its largest pair sum
   is `2 · 128 · 127 = 32 512 < 32 767`, so it never clamps — not even at the form's most
   negative code.

One `vpmaddwd` against ones widens each row's four int16 to two int32, and one `vpaddd`
accumulates: **four instructions per 32 products**, 8 MAC per instruction, where the AVX-512
body's one `vpdpbusd` is 64. A lane accumulates `2 · 32 · 4 · 128 · 127 = 4 161 536` over a
super-block, six hundred times inside int32, and the epilogue is the AVX-512 body's operation
for operation — one multiply `d · dk` and one fused multiply-add per (row, super-block).

**There is no bias term.** The sign trick already multiplies the *signed* code, so unlike the
AVX-512 body, which pays `−128 · Σa` back, the AVX2 body never reads `KqActs::sum256`. The
activation's codes are `−127..=127` (the quantiser's range, pinned by
`the_eight_bit_lanes_cannot_overflow`), which is what makes `sign` exact: an activation code of
`−128` would negate to itself in int8, and the engine never produces one.

The form's group window is 64 bytes — eight rows of eight codes — so a 256-bit register holds
four of the eight rows and the super-block is walked twice, one half of the window at a time,
with four float accumulators per activation row. Eight activation rows per group is the widest
that keeps the eight int32 accumulator vectors, the two weight windows and the temporaries in
the sixteen registers.

### The proof

* `crates/peregrine-kernels/src/kqsimd.rs`: `the_eight_bit_avx2_kernel_is_bit_identical_to_the_twin`
  — nine forms (random Q4_K, the tie tile, Q6_K just outside its exact case, and three
  hand-built: every code `−128`, every code `127`, at one, two and three and five
  super-blocks) against six activations (random, every code `−127`, every code `127`, and an
  alternating ±127 pattern) at the twenty width classes 1, 2, 3, 4, 7, 8, 9, 15, 16, 17, 31,

### What this step found: the mode is not faster on AVX2, and cannot be

On the 1B the fast mode is **0.88-0.92 of the exact engine** on every cell; against
ik_llama.cpp at its defaults that puts it at **0.93-0.95**, where the exact mode is 1.02-1.08.
The Qwen 0.5B is level (0.97-1.03) only because its file keeps 165 of its 374 MiB of weights in
Q5_0, which the form does not cover.

The cause is the instruction set, not this implementation. Four instructions per 32 products is
the floor for a bit-exact 8-bit dot on AVX2, because the products are too large to chain in
int16 (the exact Q4_K kernel's nibbles chain eight deep and get 21 MAC per instruction). The
body measures 14.5 MAC/cycle at 4.1 GHz, which is this core's two 256-bit vector ops per cycle;
the exact Q4_K kernel is at 18.9 MAC/cycle because it is latency-bound, not throughput-bound.
The nibble split of the codes and the int16 `vpmaddwd` path were both counted and both land
below the sign trick's rate.

So the trade the design note describes holds only where the exact kernel is weaker: **Q6_K is
1.30× the exact kernel's rate**, and a Q6_K-heavy file would show the mode ahead. On a
Q4_K-heavy file it is behind by about a tenth. The option stays off by default, its help text
now says so, and S5.4c's report (on the AVX-512 host) is where the *accuracy* of the trade is
published — the two modes' results are bit-identical across tiers, so that report is the same
arithmetic on this tier.

160.4/160.4 at 4096/4); 64 is 2 % behind and 512 is 2-9 % behind. The fast mode's default wide
chunk stays **256** (`WIDE_CHUNK_DEFAULT_FAST`): the brief's rule — move it only on a gain over
5 % on both models — is met by no chunk.

## 5f. As built on ARM: the dispatch and the numbers (S5.4e)

Built 2026-11-12 on the DGX Spark, on `origin/s5.4d-prompt-kernel-neon` (which carries
`origin/main` at `e4ad034`). Raw runs, the round script and the summarizers:
`benchmarks/results/spark-arm-2026-11-12-s5.4e/`. The mode's numbers do not depend on the body:
`cargo test --release -p peregrine-models --test fast_prompt` passes natively and under
`PEREGRINE_ISA=neon-dotprod`, `neon` and `scalar`, and every fast golden is recorded per tier and
checked again without the record switch.

**The dispatch.** Three functions in `crates/peregrine-kernels/src/table.rs` gained an aarch64
arm, inside `cfg(all(target_arch = "aarch64", feature = "fmt-kquant"))`, x86 untouched:

- `q8k_gemm`: when `cpu::have_dotprod()` holds it calls `neon::q8k_gemm`, which takes `smmla`
  where `cpu::have_i8mm()` holds and `sdot` otherwise; without `dotprod` (the `neon` and
  `scalar` caps) it stays on `kq8::gemm_q8k`. The SAFETY comments name the tier check and the
  bounds the wrapper re-checks.
- `q8k_build`: when `cpu::have_neon()` holds it calls `neon::q8k_build_q4k_neon` /
  `q8k_build_q6k_neon`. The builder needs only `neon`, so the `neon` cap gets the NEON build
  (a faster load) even though its multiply is the twin.
- `q8k_simd`: true where the multiply is a NEON body (`have_dotprod()`), false on `neon` and
  `scalar`, so the startup line and `peregrine tier` do not claim a body that is not there. A
  new `q8k_body()` returns the name (`AVX-512 body`, `NEON smmla body`, `NEON sdot body`, or
  the scalar-twin sentence); `peregrine serve` prints it in its one-line notice, and
  `peregrine tier` prints a `fast prompt` line when the option is on.

`neon.rs`'s own tier test still pins that `q8k_gemm` picks `smmla` on `neon-i8mm` and `sdot` on
`neon-dotprod`; a new test calls the table's entry points and checks the same counters, the
builder's bytes against the twin's, and the results against `kq8::dot_q8k` at four rows.

**The goldens.** `llama-Q4_K-fast` and `llama-Q6_K-fast` are now recorded per aarch64 tier:

No NEON body or builder change was needed: S5.4d's `q8k_build_q5_0_neon` already handles a row
that stops inside its last super-block (it builds `n_blk.div_ceil(8)` and leaves the missing
blocks' weights zero), and both multiply bodies read the padded activation's zeros.

**The padded tail.** The form of a 896-wide row holds 1024 codes: a quarter of its fourth
super-block is zero weights meeting zero activation codes, and the multiply walks them. The cost
is 13.7 % of the form's rate — 5.63× on a whole row against 4.86× on the 896-wide one at the same
width and tier, which is exactly the 1024/896 = 1.14 of traffic. It does not lose anywhere near
the 1.10× bar, so the shared layout and dispatch are untouched. **Skipping the four zero groups
would be bit-identical** (the integer sums are exact in any grouping, and the epilogue is per
super-block, which keeps its real half), and `neon.rs`'s
`a_q5_0_row_that_stops_inside_a_super_block_is_the_twins_bits` now proves it at every width class:
it rewrites the padded groups' codes with a non-zero pattern and gets the same bits, because every
activation code they meet is zero. It would not rescue x86 either: AVX2's whole-block ratio is
1.00×, so its 896-wide cell would move from 0.88× to about 1.00×, still under the bar; that is the
x86 goldens' and the AVX-512 SDE jobs' risk for no table entry.

**What the load path needed.** S5.4f's padded activation was built only when the *process option*
`--fast-prompt` was on (`quant::pad_k_layout`), which is right for the CLI but not for the
library's `load_with_fast` + `Engine::set_fast_prompt` pair, which S5.4b's tests use to compare
the two modes in one process: there the form exists while the option is off, and a padded Q5_0
matrix would read a plain activation. `kq8::note_padded_q5_form` now records, at the form's build,
that a Q5_0 matrix with a short last super-block is resident, and `pad_k_layout` pads for that as
well as for the option. Nothing else changed: a matrix without a form never reads the padded
codes, and the default engine neither builds a form nor pads.

## 5i. The fast pass against the fork at the same arithmetic (S5.4i)

Measured 2026-11-12/13 on the desktop, idle (the only load was the session's own runs), AVX-512.
The account, the two candidates that were built and rejected, the eight cells and the exact
commands: `benchmarks/results/desktop-zen5-2026-11-12-s5.4i/`. `perf` is not available on this host
(no binary, no `sudo`, `perf_event_paranoid` 2, WSL2), so the account is the engines' own timers —
`PEREGRINE_PROF2=full` through `promptbench`, and the fork's `libggml.so` called directly by the
probe of §10.3 — plus the fork's own pass ablated with `-rtr` and `-fa 0`.

**The account, Llama 3.2 1B Q4_K_M, 512 tokens, one thread** (`--fast-prompt`): wall 6.283 s
against the exact engine's 9.218. The weight matmul is 83.0 % of it and its kernel runs at
**96.2 GMAC/s for Q4_K and 103.9 for Q6_K in situ** (the `prof` format slots over the model's own
MAC counts), against §5a's isolated 91.9/95.5 and against **the fork's own `q8_k_r16` at 94.9
GMAC/s** at 512 activation rows and 85.1 at 256, measured through its library. By matrix group:
qkv 94.5, wo 97.0, gate/up 94.6, down 100.1 GMAC/s; the exact engine's are 60.4/74.0/74.1/44.5 on
the same groups. Attention is 9.1 % of the fast pass (scores 23.2, mix 13.3 GMAC/s/core — the same
code as the exact engine), the caller's serial steps 8.8 %, and the output head — one row, as §5b
designed — 5.8 GMAC/s, 46 ms, 0.7 %.

**At twelve threads** (512 tokens: 1.103 s against the exact engine's 1.573) the pass is
kernel 0.703 s (64 %), **barrier wait 0.115 s (10.4 %)**, attention 0.100 s (9.1 %), the caller's
serial steps 0.149 s (13.5 %), activation fill and untile 0.036 s. **At 4096 tokens** (12.087 s
against 15.615): kernel 5.31 s (44 %), **attention 4.59 s (38 %)**, barrier wait 1.28 s (10.6 %),
serial steps 1.14 s (9.4 %).

So: **the kernel is not where the pass loses.** It is at its isolated rate in situ, at the fork's
rate at both engines' chunk widths, and at 79 % of this core's byte-dot roof (121 GMAC/s, §10.4) —
the same fraction as the fork's. At 512 tokens the loss is the 36 % of the pass that is not the
kernel, and 10.4 of those points are the barrier wait; at 4096 tokens it is **attention, which is
38.0 % of our pass against 20.5 % of the fork's own** (its `-fa 0` ablation: 399.9 → 317.9 tok/s)
and 2.1× the fork's absolute time.

**What was built, and why none of it ships.**

* *A sixteen-output-row body* (the fork's `q8_k_r16` shape): `kqsimd::q8k_gemm16_zmm` plus

## 5j. A form with one scale per 32 weights: what it would cost and buy (S5.4i)

Built and measured 2026-11-12/13 on the desktop; the kernel, its numbers and the error tables:
`benchmarks/results/desktop-zen5-2026-11-12-s5.4i/` (§6). **Nothing in the engine dispatches it**:
`crates/peregrine-kernels/src/p32.rs` is an experimental module — not in `MatKernels`, not in

owner's decision between the two arithmetics, not a recommendation.

The finer form is the fork's *other* wide path (its default without `-rtr`: `Q8_1`/`Q8_0_R8`, one

between them, which is why this exists.

The epilogue is the whole difference: the byte dot is the same instruction for instruction (one

512-token one-thread pass with its kernel at 0.58×), a per-32 fast prompt mode would be **0.86× the

and the measured kernel ratio, not a measured mode, and it does not include the extra 207 MiB or
the load.

Measured on this code, the finer grid is **1.39× better in per-weight RMS**, not 8×: each 32-weight
block's step is its own `max/127`, and a 32-weight maximum is 0.7-0.8× its super-block's on these
files, so the error falls by the square root of that. The 3.6× between the fork's two KL numbers
therefore cannot be attributed to the grid alone. **The two sides of the decision, side by side:**
finer grid → 1.39× smaller per-weight error (and the fork's 0.000945 against 0.003401), for 1.7× the
kernel time (slower than the exact engine), +21 % of the form's memory, and 0.65 against 1.9 G
weights/s of build. A per-32 *Peregrine* pass's KL was not measured; wiring it in is what that
needs.

## 5k. The fast mode's attention order (S5.4j)

Measured 2026-11-13 on the desktop, AVX-512. Numbers, raw files and the drivers:
`benchmarks/results/desktop-zen5-2026-11-13-s5.4j/`. The code is `mod fast` in
`crates/peregrine-core/src/attn.rs` — beside the exact attention bodies, which is where this
tier's attention kernels already live (the value mix's 16-lane body, the score tree and the F16
tile are all in that file), so the fast order follows the existing placement rather than moving
the tier's attention into `peregrine-kernels`.

**Why an order at all.** §5i left one term that is bigger than the whole remaining gap: at
4 096 tokens and 12 threads attention was 4.59 s of a 12.09 s fast pass against the fork's
2.16 s. The exact engine's attention has a defined order and it is at the limit that order
allows (§12.2/§13.3 of the prefill study): a score row is an eight-lane tree, so a head's 64
dimensions cost eight fused multiply-adds and a transposed reduction, and the value mix is one
chain per element, four of them at `head_dim` 64. The fast mode does not have to keep that
order. It is lossy by definition, its prompt rows already carry the 8-bit form's bits, and **a
different order of the same sums moves a result by rounding only** — orders of magnitude below
the form's own error (§4's measurement shows it: the mean KL moved by 1.4 % of itself on the two
models measured, inside the run's error). That freedom buys the only thing the exact order
cannot have: several query rows sharing one pass over a decoded key and value tile, and a
16-lane reduction instead of an 8-lane one.

### The definition

Defined once, in writing, and implemented twice: the scalar twin *is* the definition (ADR 0005)
and the AVX-512 body must equal it bit for bit.

1. **Pieces.** A fast prompt row's visible keys are walked in pieces of at most `BLOCK` (64)
   keys on the **absolute position grid** — and, with a sliding window, from the row's own
   window start. The online soft-max folds pieces in ascending order, so the number of rescales
   is a function of the row's own visible range too. No position chunk ever cuts a fast row
   (`plan` gives it one), and there is no chunk combine.
2. **Scores.** `head_dim` is walked in ascending 16-lane blocks; lane `l` keeps one `f32`
   accumulator and takes one fused multiply-add per block,
   `acc[l] = fma(q[l], k[l], acc[l])` (dimensions past `head_dim` are a zero product). The lanes
   are reduced by `T16(v) = T8(v[l] + v[l+8])` with `T8(w) = ((w0+w1)+(w2+w3)) +
   ((w4+w5)+(w6+w7))`, and the result is multiplied by the soft-max scale (a separate `f32`
   multiply, as the exact kernels do).
3. **Soft-max.** The maximum is over the piece and is order-free. Each exponential is the
   engine's own (`vmath`'s polynomial, `exp_scalar` in the twin and `exp16` in the body, which
   are lane-for-lane the same function — *not* the C library). The denominator folds the piece
   in **16-key groups from the piece's first key, ascending**: a group's exponentials are
   reduced with `T16` in `f32`, and the group sums are added into the row's `f64` denominator in
   ascending order. The rescale is the engine's (`l = l·α + Σ`, `α = exp(m_old − m_new)`).
4. **Value mix.** Per element, one `f32` chain in ascending key order,
   `o = fma(p_j, v_j, α·o)` — the exact tier's own formula, so the mix moves no bit at all;
   what the fast order adds there is that four rows share one pass over V.

Everything else is the exact engine's: the causal and sliding-window ranges, the sinks, the
rotation, the head geometry, the `(o, m, l)` merge. Which rows take the order is the same flag
the weight dispatch reads (`QuantAct::prompt`, §5b): the engine fills one `bool` per batch row
(`State::fast_rows`) from it, and only on a tier whose table says so **and** on a model that
carries a form at all. A model whose formats are all outside the tier's table is therefore the
exact engine bit for bit, attention included (§3).

**The tier table.** `MatKernels::fast_attn()` is the per-tier property, next to
`q8k_uses_form`: **AVX-512 yes**; AVX2, aarch64 and scalar no, so their fast-mode goldens did not
move and the mode behaves there exactly as it did before this step. Their bodies are later
steps.

**What it reaches.** A score's 64 dimensions are four 16-lane FMAs, and four keys' trees share
one transposed reduction (fold each accumulator's 16 lanes to 8, then three `hadd`s give four
sums), so the reduction costs about three operations per key instead of seven. Four rows
(four keys at a time, sixteen accumulators) keep the query, key and accumulator vectors in the
ZMM file; the mix runs sixty-four dimensions at a time for four rows, so each position's four
value vectors are loaded once and each row's weight is broadcast once for sixteen FMAs. In a
kernel bench (`attnbench` with `PEREGRINE_FAST_ATTN=1`, which marks every row a prompt row),
attention's own time on Llama 3.2 1B, chunk 128:

| positions / threads | exact order | fast order | ratio |
|---|---|---|---|
| 512 / 1 | 583.8 ms | **503.7 ms** | **1.159** |
| 512 / 12 | 95.4 ms | **86.7 ms** | **1.100** |
| 4 096 / 1 | 32 458-32 827 ms | 33 778-33 919 ms | **0.96** |
| 4 096 / 12 | 4 851 ms | 4 980 ms | **0.974** |

The 4 096 rows are the bench's own data and not the engine's: `attnbench` fills the cache with a
regular small pattern, and at that length the widened f32 tile the fast bodies read is twice the
exact path's f16 bytes and out of L2. **In situ the same order saves 16.8 % of the attention at
512/12 and 3.0 % at 4 096/12**, and is level at one thread, where the bucket is the tile's decode
and the caller's per-row setup rather than the bodies (measured pairs in the results README §2.2;
`StepStats::attention` 118.2 → 98.3 ms and 4.69 → 4.55 s). The order is kept at every length and
on every pool: a row's bits may not depend on either, so there is one definition per row, not one
per thread count.

**End to end.** In a real fast pass the attention bucket falls by **16.8 %** at 512 tokens and 12
threads and by **3.0 %** at 4 096, and the pass gains **+2.1 % (Llama, 512/12), +1.9 % (512/1),
+5.6 % (Qwen3 512/12), +3.9 % (512/1), +3.9 % (Llama 4 096/12), +3.1 % (Qwen3 4 096/12), +3.1 %
(Llama 4 096/1) and +4.3 % (Qwen3 4 096/1)** on five/three/one interleaved rounds of the eight
cells (results README §4). The gain is proportional to attention's share and to the threads that
wait on it, which is why it is 2-6 % and not more: at 512 tokens attention is only 9 % of the pass.

**Accuracy.** The change from the attention order has to be invisible at the reported
precision, and it is: `kld`, the same corpus, 40 chunks of 512 tokens, Llama 3.2 1B and Qwen 3
1.7B, fast against the exact mode of the same file (`--ref-self`):

| model | mean KLD before | mean KLD after | same top p before → after |
|---|---|---|---|
| Llama 3.2 1B | 0.003514 ± 0.000049 | **0.003464 ± 0.000047** | 96.745 ± 0.176 % → 96.667 ± 0.178 % |
| Qwen3 1.7B | 0.017115 ± 0.000993 | **0.017336 ± 0.001186** | 93.912 ± 0.237 % → 94.196 ± 0.232 % |

−1.4 % and +1.3 % of itself, both inside the run's own error and both far under the 2 % bar the
step was given: a summation order cannot move the KL, and it did not. The bound of §4 is
re-baselined to 0.0040 with this step (the owner's confirmation pending).

**The tests.** `the_fast_score_body_is_the_twin`, `the_fast_mix_body_is_the_twin` and
`the_fast_denominator_body_is_the_twin` sweep every key count 1…70, 127/128/129, 511/512/513,
4 095/4 096/4 097, head dims 64, 128, 80, 16 (72 is the twin's: the 16-lane body takes whole
lane blocks), random values and the edge values a soft-max produces (a wide score spread, one
huge logit, all-equal scores), at one, three and four rows, bit for bit. They are gated to
`x86_64` — the twin is portable, the 512-bit body is not — and each says so. The invariance half
is the engine's: `fast_mode_is_prompt_invariant` passes unchanged (every chunk of 16…128, 1, 2
and 4 threads, alone and beside a decoding user) and grew a **4 096-token** case (chunks
16/64/128/256, 1/2/6 threads, beside a decoder), and
`a_fast_rows_attention_is_its_own_at_every_group_size` pins the group-count half directly: the
same row at the same position is its own bits at the head of a 1-, 2-, 4- and 8-row call, at one
and four threads.

**Found in review, fixed before the merge.** A prompt row that is alone in its cache beside
another user's row (the last row of a prompt chunk next to a decoding user) takes the mapped
pass's per-row path, `attn::run_row`, and that path still cut the row into the exact engine's
position chunks: a fast row past ~512 positions was then folded in pieces that are not the key
tiles, so its bits depended on which rows shared its pass. `run_row` now gives a fast row one
walk over its whole visible range, as `plan` does, and
`a_fast_row_alone_in_its_cache_is_the_solo_row` (`blocks/attn.rs`) compares the mapped row with
the same row alone, exact and marked; it failed before the change, natively and under SDE's
Sapphire Rapids. The same path now drops the flags on a tier without the order, like
`attend_scaled_window`. And the order is on only for a head width the 16-lane bodies cover
(`head_dim` a multiple of 16): at any other width only the definition's plain loops exist, which
are far slower than the exact attention those rows therefore keep.

**The goldens.** One file per tier moved, once, at the end: the AVX-512
`llama-Q6_K-fast.golden`, re-recorded natively here. The AVX-512 `llama-Q4_K-fast.golden` was
rewritten identically (that synthetic prompt's logits are insensitive to the reordering — its
argmax is one token throughout), and no other golden moved: the AVX2 and scalar fast goldens,
every exact golden, and the aarch64 set are untouched, and
`git diff --name-status origin/main...HEAD -- '*.golden'` lists exactly one `M` line.

S7.4 gave the AVX-512 tier `-windows` twins of both fast goldens, and the Q6_K one moves with
this order, so it had to be re-recorded on a Windows runner with AVX-512. Three
`record-goldens.yml` starts (`-f runner=windows-2025`) all drew an **AMD EPYC 7763** — Zen 3,
AVX2 and no AVX-512 — which records the `x86_64-avx2-windows` set (identically) instead. With no
AVX-512 runner drawn, the two AVX-512 `-windows` fast goldens are **deleted**: the Windows
AVX-512 job then skips them (it does not set `PEREGRINE_GOLDEN=require`), and the pinned-AVX2
Windows step that does require its own goldens is unaffected. The removal is the third commit of
this step, and the results README §2.4 records it.

**What is still behind the fork.** Our attention is 2.1× the fork's in absolute time and this
step does not change that verdict. **Corrected in §5o**: the fork's `-rtr` runs keep **f16** keys
and values and score them with an f32 × f16 dot product; the int8 machinery quoted here
(`block_q8_KV`, `iqk_gemm_q8kv_fa`) is taken only when the cache itself is quantised, which the
measured cells are not. The gap is the kernel's shape (f16 tiles read directly), not an integer
dot — and our own `KV=i8` does not close it (§5o A4). What reordering can do
is what this section measures: the f32 path, tiled, 17 % faster at 512 tokens and 12 threads
and 3 % at 4 096 (level at one thread). Closing the rest is a
quantising attention kernel, and it belongs in an accuracy report of its own.

## 5l. The pass's non-kernel share (S5.4j)

Measured 2026-11-13 on the desktop. Llama 3.2 1B Q4_K_M, `--fast-prompt`, 512 tokens, 12
threads, `PEREGRINE_PROF2=full` through `promptbench`, and the pool's own park log
(`PEREGRINE_ADAPTIVE_LOG=1`). "Serial" below means **the caller thread's own work between two
fork–joins**; everything else on the list runs on the pool, and its wall is a fork–join's cost.

| term | share of the pass | serial? |
|---|---|---|
| the 8-bit kernel | 64 % | no |
| **the caller's wait for its workers** | **10.4 %** in S5.4i's window, **12.0 %** of this one's | the wait itself |
| attention | 9.1 % | no (S5.2c: its fork and prologue are 6.8 % of a 4 096-token pass) |
| activation quantise (attention's output → `wo`'s input) | 2.8 % | no |
| SwiGLU | 4.2 % | no |
| RMSNorm ×2, RoPE, residual ×2 | 2.3 % | no |
| **KV write** | **1.9 %** | **yes** |
| **the form's interleaved activation fill** (`KqActs::fill_with`) | **~1.5 %** (estimate: 24 MiB of zeroing and copying a pass) | **yes** |
| activation fill + untile + loop | 3 % | no |

**Every step named.** The quantise, SwiGLU, the norms, RoPE and the residuals are already
threaded and at their floor (S5.2c measured the first four and offered three fusions, none of
which is a bit-exact win: the residual-into-norm fusion is worth 2 % and changes the signature of
every family's attention loop). Two steps are the caller's alone: the **KV write** (65 k f32→f16
conversions a chunk-layer, 20 µs over twelve threads against a ~200 µs fork–join, so running it
on the pool cannot pay — S5.2c's verdict, unchanged) and the **form's interleaved fill**, which
is new with the mode: `matmul_block` interleaves the activation rows into the k-quant layout
(`KqActs::fill_with`) before it forks, for every matrix group whose form is in play — three
times a layer, 24 MiB of zeroing and copying a pass. It is 1.5 % of the pass, and *parallelising
it adds a fork–join* to a step that currently has none; the cheap version (each worker fills the
4-row groups it will consume) needs the fill to be row-aligned with the kernel's tile split,
which is a change to `matmul_block`'s interface for 1.5 %. Written down, not taken.

**The wait, and the one lever that paid.** The wait is the caller's `barrier wait` slot: how long
it spins for the straggler after finishing its own share. It is not imbalance (the plan's tasks
are even) but **parking**: a worker that finds no job after its spin window parks on the
condvar, and the next job then pays the wake *and* the OS's reschedule. The pool's log says so
directly — in one 1.0 s fast pass at 512 tokens, **1 006 parks: 3 under 100 µs, 149 under 500 µs,
270 under 1 ms, 507 of 1-5 ms and 11 over 5 ms**.

The window was the wrong shape for a prompt pass. `peregrine_core::calib` measures the *wake
latency* at startup (50 fork–join cycles at 0 µs spin) and sets `spin_us = 2·L_wake`, clamped to
[50, 2000] — a window sized for decode, where joins are tens of microseconds apart. A prompt
pass's joins are **1-5 ms** apart, because its caller does that much serial work between them
(the KV write and the fill above, plus the tail of each step), so the window expires before the
next fork arrives and every join pays a park. Measured on the fast 512-token 12-thread cell, a
fixed window against the calibrated 1 000 µs: **2 000 µs +6 %, 4 000 µs +8 %, 8 000 µs +4 %**
(and S5.2b's loaded-host result — 4 000 µs costs 2-13 % — is why this cannot be a fixed default).

**As built.** `Pool` measures the gap between the end of one fork–join and the start of the next
(one clock read and one atomic per join, on the caller), smooths it with a one-quarter weight and
stretches the worker's spin window to cover it, capped at 8 000 µs; a gap over 20 ms is a pass
boundary and is ignored; a configured window of 0 (and `PEREGRINE_ADAPTIVE_SPIN=0`) is left alone,
so the calibration's own probe still measures what it measured. It is a scheduling choice only:
nothing a worker computes changes, and the exact engine's goldens are untouched.

| cell | before | after | ratio |
|---|---|---|---|
| Llama 3.2 1B, fast, 512/12 | 446.9 / 446.3 / 462.1 | **465.3 / 461.5 / 461.1** | **1.033** (medians of three interleaved rounds) |
| Llama 3.2 1B, exact, 512/12 | 343.1 | **349.3** | 1.018 (one pair; level) |

The exact engine gains what its own gaps allow (its joins are further apart — a longer pass — so
its window was also short) and it does not get slower. At 4 096 tokens the gap-shortening lever is
worth nothing measurable: the pass is 12 s and its 480 joins are 25 ms apart, so few workers park
in the first place.

**What is left, and why it is not more.** The wait is now the second-largest non-kernel term and
the biggest single reason the 512-token cells are behind: the fork does not have it because it
keeps twelve OS threads busy in one long region per layer, where Peregrine forks ~15 times a
layer. The lever that would remove it is fewer, larger fork–joins — running a worker's share of
several consecutive element-wise steps inside one region — and the steps that could share one
(attention's quantise, SwiGLU, the two norms, the two residuals) are separated by matmuls that
need the previous step's *whole* output (the k-quant activation's interleaved layout is
transposed across four rows), so the fusion is a change to `matmul_group`'s interface rather than
a loop merge. That is the next round's work, priced here: ~15 joins a layer, ~200 µs of wait
each, 10 % of a 512-token pass.

## 5m. As measured: the fast pass at 4 096 tokens on ARM (S5.4k)

S5.4h left the mode ahead of ik_llama.cpp at 512-token prompts (1.03-1.72×) and behind at
4 096 (Qwen 2.5 0.5B 0.86× at one thread, 0.91× at ten; Llama 3.2 1B 0.74× at ten), and
named the form's bytes as the suspect: 385.9 MiB resident against the file's 235.5 MiB of
multiplied weights, which ik streams. This round is the account of a fast pass at 512 and
at 4 096, one thread and ten, on both models — and it **moves the blame to attention**. No
engine file changed; the numbers are `benchmarks/results/spark-arm-2026-11-12-s5.4k/`, every
cell marked loaded (the 1-minute load average ran 4.0-13.8).

**The matmul rate does not depend on the prompt length, and the form is at 80-91 % of its
hot-tile rate.** Inside a real pass at one thread (GMAC/s over the group's own wall):

|---|---:|---:|
| Q5_0 form, 896-wide (Qwen qkv/wo/gate-up) | 268.3 | 204-225 |
| Q4_K form, whole rows (Qwen ffn_down, Llama qkv/wo/gate-up) | 308.4 | 270 / 268-275 |
| Q6_K form, whole rows (Llama ffn_down) | 307.0 | 277-279 |

The 4 096-token pass multiplies eight times the rows and takes eight times the matmul time;

microbenchmark's hot tile against a pass that streams the whole form from memory once per
chunk, not the activation's preparation (quantise plus the interleaved build: 1.8-1.9 % of the
pass) and not the chunk (chunks 64/128/256/512 at 4 096 tokens, one thread: 175.1/176.6/177.0/
176.5 tok/s on Qwen, 107.9/110.1/110.6/110.7 on the 1B — 512 is already the right chunk). The
896-wide row's padded fourth super-block is the 1.14 traffic S5.4h measured: 268.3/1.14 = 235
GMAC/s is its real-row rate, against 204-225 in a pass.

**Attention is the difference between 512 and 4 096.** Its share of a one-thread fast pass is
19.5 % → 65.1 % on Qwen (0.25 s of 1.30 → 15.17 s of 23.30) and 13.5 % → 54.5 % on the 1B
(0.34 of 2.51 → 20.21 of 37.09), because its MACs are O(n²) where the matmul's are O(n). At
4 096 the score half runs at 35 GMAC/s and the value-mix half (soft-max's maximum and
exponentials inside its loop) at 18-23 — the rates S4.9s/S4.9t measured for these kernels, and
the same rates at 512. The four-row bodies do fire: the cache is F16, head width 64, and the
64-row sub-blocks' rows see the same tile.

**At ten threads the account is the host's, not the engine's.** The same binary measured
176/349/594/793/879/543 tok/s at 1/2/4/6/8/10 threads on one cell in one sweep; the caller
spends 3.7-4.0 s of a 7.5-8.8 s pass waiting for a pool the co-tenant deschedules (load
4-14), and ik's own rounds on that cell spread 592.6-1021.6 tok/s. The ten-thread column is a
direction, not a standing.

**The eight cells.** Fast ÷ ik at 4 096 tokens: Qwen 0.94× at one thread (176.9 against
189.0; ik 188.7 and 189.3 in its two rounds, the stablest engine cell measured), Qwen 0.78×
at ten (570.7 against a 735.8 median whose rounds are 592.6/1021.6/735.8), Llama 0.94× at ten
(551.4 against 584.8). Fast ÷ llama.cpp is 1.60-6.87× on all eight; fast ÷ ik is ≥1.0 on the
four 512-token cells (1.09-1.75×) and 1.28× on the 1B at 4 096/1.

**ik's aarch64 wide path, from its source.** `iqk_gemm_kquants.cpp`'s `__aarch64__` family
(`mul_mat_qX_k_q8_1_x4` with `DequantizerQ4K`/`Q5K`, `mul_mat_q6_k_q8_0_x4`) does not
requantise the matrix into a resident form: it reads the file's own k-quant block, expands it
to eight-bit codes in registers per 32-weight group, and MMAs against a `q8_1`/`q8_0`
activation, four activation rows per call. It streams 0.5625/0.8125 bytes per weight and pays
the expansion in ALU; this form is 1.00 (1.16 padded) bytes per weight and pays nothing. At
one thread that trade is strongly ours (270 against the exact Q4_K kernel's 78 GMAC/s); its
4 096-token win is its CPU flash attention (`iqk_flash_attn.cpp`), not its matmul. `perf` is
unusable on this host (`perf_event_paranoid` = 4), so the engine's own counters and that
source reading are the profile.

**What it would take.** On Qwen 4 096/1 the pass is 65 % attention and 27 % matmul; making
the score and mix kernels 20 % faster would take the cell from 23.30 s to 20.8 s, 197 tok/s,
**1.04×** ik. That is a new loop shape on the S4.9t kernels (the mix is conversion-bound at one
`vcvtph2ps` per FMA; the score tile would keep two K blocks in flight), bit-identical and so
allowed in both modes, and it is the next step this account names. The other leftover is the
Q5_0 padded form's 12.5 % of that multiply — 2.4 % of the cell, measured and proven
bit-identical in §5h, and not worth the hot-path signature change on three architectures while
the cell stays below 1.0 for the attention reason.

## 5n. The fast mode's attention order on NEON (S5.4n)

Measured 2026-11-13 on the ARM host. Numbers, raw files and the drivers:
`benchmarks/results/spark-arm-2026-11-13-s5.4n/`. The definition is §5k's, unchanged:
pieces are the absolute 64-key tiles, a score is sixteen `f32` lanes and the `T16`
reduction, the denominator folds 16-key groups with `T16` in `f32` and the groups in
`f64` ascending, and the value mix is one ascending FMA chain per element. This step
adds aarch64's bodies for it and turns the tier on; the scalar twins remain the
definition and the aarch64 bodies are their bits.

**The bodies.** Three, in `crates/peregrine-core/src/attn.rs`, `mod fast`:

* `scores_neon` — sixteen lanes in four `f32x4` accumulators per row, up to
  `FAST_ROWS` (4) rows sharing one pass over the key, `T16 = T8(v[l] + v[l+8])` in
  registers (`vaddq` for the two halves, then `hsum4` twice);
* `mix_neon` — sixteen lanes per row, four rows over one pass of V, one ascending FMA
  chain per element (ARM's `vfmaq_f32` is `acc + a·b`, so the accumulator is the
  first operand);
* `denom_neon` — `vmath::exp4` (the already-proven lane-for-lane `exp`, now public)
  and the `T16` group sum, the groups added to the row's `f64` in ascending order.

**F16-direct, and why it matters.** The exact aarch64 prefill reads the cache's F16
halves in the kernels' registers (`f16_direct`) and the AVX-512 fast walk reads a
widened `f32` tile. Ported that way the NEON order *lost* at 4 096 tokens with ten
threads (kernel bench 0.95×, pass −0.2 %): the widened tile is twice the bytes of the
tile the exact path streams, and at that length the pass is memory-bound. The
conversion is exact, so the halves can be read in the fast bodies too — and then one
conversion per element feeds four rows, where the exact mix converts once per row.
With `scores_f16_neon` and `mix_f16_neon` the order wins everywhere (§1 of the
results). A fourth test, `the_fast_f16_bodies_are_the_widened_ones`, pins the halves
against the widened bodies bit for bit on the same grid.

### A1. What the fork's `-rtr` runs actually do (a correction to §5k)

§5k's last paragraph said the fork's flash attention "quantises the query and the key to int8".
That was an **inference from timing, and it is wrong**. The source of the fork
(`~/.cache/peregrine-bench/ik_llama.cpp-479074c`, `479074c`):

- `-rtr` is `--run-time-repack` and touches only the weights (`examples/llama-bench/llama-bench.cpp:822`,
  `common/common.cpp:2537`): it sets `repack_tensors` and disables mmap. The KV cache is not
  involved.
- The KV cache type of a `llama-bench` run defaults to **F16** for K and V
  (`examples/llama-bench/llama-bench.cpp:299-300`, `/* type_k */ {GGML_TYPE_F16}`,
  `/* type_v */ {GGML_TYPE_F16}`), and flash attention is on by default
  (`:309`, `/* flash_attn */ {true}`). The S5.4i/S5.4j sweeps passed neither `-ctk`/`-ctv` nor
  `-fa`, so **their `-rtr` cells read f16 keys and values**.
- With a f16 cache the kernel is chosen by `iqk_flash_helper_T`'s `switch (type_k)`
  (`ggml/src/iqk/fa/iqk_fa_templates.h:2204-2214`): `GGML_TYPE_F16` → `HelperF16`, whose `load`
  widens two halves (`F16::load`, `:198-208`). The scores are then a **f32 × f16 dot product**:
  `FlashQKfp32::multiply_mask_kq` (`:1262`) calls `iqk_gemm_default_floats(D, q_step, kh.block,
  kh.stride, info, k_step)` with the query kept in `float` on x86 (`compute_helper`, `:1388-1391`),
  i.e. `mul_mat_Qx_Qy_MxN_fa4<QFT<float,8>, QFT<ggml_half,8>>` (`ggml/src/iqk/iqk_gemm_floats.cpp:665`).
  The value mix is `FlashQKV::accumulate_qkv`: `F16::fmadd(vq, v0, vs0)` — f16 values times f32
  weights (`:996-1015`).
- The int8 machinery §5k quoted (`block_q8_KV`, `HelperQ8KV`, `iqk_gemm_q8kv_fa`,
  `iqk_fa_templates.h:210-243`, `:1323-1328`, `iqk_gemm_kquants.cpp:5323`) is taken **only when the
  cache itself is quantised** — `GGML_TYPE_Q8_0` → `HelperQ80` (`:2216`), `GGML_TYPE_Q8_KV` →
  `HelperQ8KV` (`:2229`), which is what `-ctk q8_0 -ctv q8_0` asks for. Our `-rtr` cells did not.

Two consequences, both measured here. First, the fork's advantage in the measured cells is its
**tile shape and its f16-key kernel**, not an integer dot: it reads the cache's halves directly
while our fast order widens every key tile to `f32` (§5k). Second, an int8 cache *is* a real lever
for that kernel — the fork's own 4 096/12 cell goes **369.9 → 445.3 tok/s (+20 %)** with
`-ctk q8_0 -ctv q8_0`, and 551.8 in its best of three rounds — but its measured cells do not use it,
and our own `KV=i8` (Part A2) has no integer dot to gain.

anywhere in our attention, so the fork's `q8_0` win (+20 %, A1) is not reachable by selecting our
cache; it needs a quantising *kernel*.

### A4. Conclusion: the int8 key is not the missing piece

- **How much of the 4 096-token gap it closes: none, and it widens it.** `fast+i8 ÷ fast` at
  4 096/12 is 0.890 (1B) and 0.859 (Qwen3); `fast ÷ ik -rtr` in the same window is 0.888 and 0.870,
  so the int8 cache would take those cells *down* by 11 % and 14 %, not up.
- **What it costs in KL on top of the fast mode's 0.0035**: +0.00015 (1B, +4.3 % of itself) and
  +0.00056 (Qwen3, +3.2 %), with the same-top-token share down 0.16 and 0.27 points. Within the
  0.0040 bound; but buying nothing with it is not a trade.
- **The fast order does work with the int8 path, and it does not bypass it.** `run_range_fast` →
  `fast_walk` (`attn.rs:748`) decodes the tile through `kv.decode_block` into the f32 scratch and
  Hadamard-rotates the query when `kv.rotated()` (`:770-772`); nothing in the fast module tests the
  precision, and the invariance test runs the int8 cache through it
  (`attn.rs:4173`, `setup(KvPrec::I8, …)`). So an int8 cache changes how a key reaches the tile,
  not which order scores it — no panic, no silent fallback to the exact path, and no wrong
  results; the measurements above are that path.
- **What the 4 096 gap actually is.** Not the cache precision: the fork's own cells are f16
  (A1), and its f16 score kernel is f32 × f16 with 8×8 tiles; ours widens the tile to f32 for the
  fast order and its score body is at 29 % of this core's f32 FMA roof (§5k). An integer dot is
  the fork's *other*, unmeasured path: with a quantised cache it is worth +20 % at 4 096/12
  (369.9 → 445.3 tok/s) but it is a different arithmetic and needs its own accuracy report — a
  Q8 key/query attention, not a `KvPrec` flag.
- **Kept**: no default changed. `KV=i8` remains an opt-in measurement cache, documented as not a
  speed lever at these lengths.

### B2. What was built, one lever per commit

**1. The dynamic grain follows the tail, not a constant (all engines).** `matmul_group` splits its
row space over the pool in chunks of `total/(width·8)`, clamped to [8, 256]; the caller's share
ends when the counter is exhausted, so what it then waits for is a chunk another worker claimed
just before it — 287 µs a join, 11 % of the pass. One 32nd per worker, capped at 64 rows, is the
grain that measured best; a decode pass (`nb == 1`, 224 joins a token and no tail worth chasing)
keeps the old grain, because the first cut cost 11 % of the decode rate. Five interleaved rounds,
medians: **512/12 444.5 → 470.1 (+5.8 %, one pair +6.7 %), 4 096/12 334.1 → 339.7 (+1.7 %)**, and
the exact engine gains the same way (it is the same driver). Bits cannot move: a chunk is a range
of output rows, and a row is a function of its own activation and weight row (ADR 0003).

**2. The form's interleaved activation, filled on the pool.** `KqActs::fill_with` was 78.9 ms of a
1.033 s pass (6.4 %, 112 MiB of interleaving a pass — S5.4j's "24 MiB, ~1.5 %" was low by the
`down` group's 32 super-blocks). Each group of four activation rows is an independent transpose, so
`fill_group` (`kq.rs`) is the layout definition once and `fill_form` (`linear.rs`) hands disjoint
groups to the workers through `Disjoint`; below 256 KiB of interleaved codes the join costs more
than the copy and the serial fill is kept. +7.5 % at 512/12 and +3.5 % at 4 096/12, five rounds
each. It adds one join per group (4 a layer) and still pays: the join's wait is ~100 µs against the
serial fill's ~600 µs a group. A unit test pins the parallel fill to the serial fill's bytes.

**3. The KV write rides the preparation pass's join.** The write was 37.4 ms (3.0 %) of a serial
pass: 4.2 M f16 conversions over a cache whose vectors are a page apart, latency-bound at one
thread as much as twelve. A prompt chunk is one run of consecutive positions, so each row's write
is `(layer, 0..n_kv_head, pos)` and rows' positions are distinct: `prepare_rows_kv` writes the row
the worker just rotated (`KvWriter`, raw buffers with a disjointness argument, as the recurrent
state's workers already do), and only the `advance` remains on the caller (0.035 ms). +3.4 %
measured on the 512-token cell before the grain lever, +3.3 % at 4 096/12. A multi-run pass (a
prompt chunk beside other users' decode rows) and a non-consecutive position list keep the serial
write. Two unit tests pin the writer's bytes to `put`'s on every precision.

**4. What was dropped.** Folding the *residual* into the matmul's store (2 joins a layer) needs an
accumulating `OutPtr` in every store path of `linear.rs`, which the bluefin worker is rewriting in
the same window; the residue is 2 of 19 joins and ~1.5 %, and it is written down rather than
raced. Folding the attention output's quantise into the attention join needs attention's tasks
split by row block rather than by KV head (1 join a layer, ~0.7 %). Neither is in this step.

### The tests, and what pins the bits

- The dynamic grain: a row's value cannot depend on the chunk (`prefill_chunk`, `attn_invariance`,
  the synthetic goldens).
- The parallel fill: `the_parallel_form_fill_is_the_serial_fill` (codes, scales, per-32 sums,
  per-16 sums, paired sums and the whole-block sums, at 71 rows — not a whole number of groups —
  with and without the 8-bit form's sums).
- The KV writer: `a_worker_write_is_the_serial_puts_bytes` (f16, f32 and int8, rotated and not),
  and the engine's own `fast_mode_is_prompt_invariant` / `prefill_chunk_does_not_change_a_long_prompt`
  over 16…256-row chunks at 1, 2, 4 and 6 threads.
- `PEREGRINE_ADAPTIVE_STALL=claim` runs the whole model suite in CI (S5.6), and the fill and the
  KV write go through the same `run`/`run_claimed` drivers, so a claimed job covers them too.

## 6. Open points

- **Q5_0.** Both aarch64 NEON caps select it since S5.4h (§5h). No x86 tier does: the form is
  0.99-1.03× AVX2's exact Q5_0 kernel on whole blocks and 0.88-0.90× at Qwen 2.5's 896-wide
  rows, where the padded last super-block costs. Skipping the padding is bit-identical (§5h)
  but would only bring AVX2's 896-wide cell to about 1.00×, still under the table's 1.10× bar.
  AVX-512 was not re-measured; a tier whose exact Q5_0 kernel is weaker can add it to the
  table. The accuracy report, when it lands, lists Q5_0 as its own line where a tier takes it.
- **Wider chunks and time to first token.** A wide prompt pass delays the decode steps of
  other users. The wide chunk already applies only when no slot is decoding (S5.1a); fast mode
  keeps that rule.
- **Decision models and embeddings** read prompts too, but their answers are read off the
  prompt's last row, so the option would change their numbers directly. They are excluded
  until a report covers them.

## 7. What is said in public

Measured wording (S5.4c/S5.4j, with S5.4f's tier table), and the same in the option's help:
`--fast-prompt` is **lossy, experimental and off by default**; it reads the weights of the
formats whose 8-bit form beats this CPU tier's exact kernel (AVX-512: Q4_K and Q6_K; AVX2:
Q6_K; a tier with no SIMD body: none), and on AVX-512 a prompt row's attention is computed in
the mode's own tiled summation order too (generated rows keep the exact attention everywhere);
prompt passes are **1.26-1.46×** faster on AVX-512 (1.05-1.08× on an AVX2 host, §5g); on
Llama 3.2 1B Q4_K_M, measured on AVX-512, the prompt's logits move **0.0035 nats of mean KL
divergence** from the default engine's (median 0.0025, 99 % 0.024) with **96.7 % of positions
keeping the same top token**; generated tokens keep the exact kernels, on a cache the 8-bit
prompt wrote, so a reply can differ; the report is
`benchmarks/results/desktop-zen5-2026-11-13-s5.4j/`. The 1B's number is the one quoted
everywhere, as §4 asks; the other four models are in the report and in `docs/targets.md`.
The word "Experimental" stays until §4's re-baseline has the owner's confirmation.

`docs/benchmark.md` keeps two prompt rows against ik_llama.cpp — Peregrine's default
(exact) and Peregrine with `--fast-prompt` — each against the fork **both** at its defaults
and with `-rtr`, because the fork has two wide paths: with `-rtr` off it converts to
`Q8_1`/`Q8_0` (one scale per 32 weights, 0.0009 nats from its own narrow path) and with
`-rtr` on it uses the `q8_k_r16` arithmetic this mode implements (0.0034). Saying "the
fork's default is the approximate path" (the sentence this section carried before the
measurement) is true but not the whole story: both of its wide paths are approximate, and
the one the form follows is the faster, coarser `-rtr` one. The README's "where Peregrine
is behind" sentence is rewritten from those rows: the fast mode is level with ik's defaults
at 512 tokens and 0.79-0.85× its `-rtr` path, and the design's 0.85× target is met against
the former and missed against the latter.
