# S5.4: an opt-in fast prompt mode (8-bit weights for prompt passes)

- Status: design, decided 2026-11-12. S5.4a (the kernel and its measurement), S5.4b
  (the option and its dispatch) and S5.4d are built: the AVX2 body on x86 (§5d, wired into the
  dispatch) and the NEON bodies on ARM (§5e, measured but not wired in yet). S5.4c (the
  accuracy report) is not published.
- Owner decision: build it, off by default.
- Depends on: `docs/design/s5-prefill-avx512.md` §9–§11 (the measurements this rests on).

## 0. Summary

ik_llama.cpp processes prompts faster than Peregrine on AVX-512 (Peregrine at 0.52–0.64 of
it, `docs/benchmark.md`), and §11 of the prefill study found why: for a wide pass it re-rounds
each 256-weight block of a Q4_K or Q6_K row onto a new 8-bit grid and runs a kernel that needs
no per-32-weight scale multiply and no minimum term. That kernel reaches 91 GMAC/s where the
exact Q4_K kernel is at its ceiling of 74–76 (the core's limit is 121). The re-rounding is an
approximation: the fork's own logits move by 0.0011 nats of mean KL divergence between a narrow
and a wide pass, and its top token changes on 2.1 % of positions.

Peregrine's default stays exact (ADR 0003). This design adds the same trade as an **explicit
option, off by default**: `--fast-prompt`. With it on, prompt tokens are read with the 8-bit
form of the weights; generated tokens are still computed with the exact weights. The option
ships with an accuracy report, as ADR 0003 requires of every lossy feature.

## 1. What the option changes, and what it does not

**Changes.** While `--fast-prompt` is on, every weight pass that carries *prompt* rows (the
prefill of a chat, completion or decision request) computes the Q4_K and Q6_K matrix products
from the 8-bit form defined in §2 instead of from the file's own codes.

**Does not change.**

- The default. Without the option nothing in the engine differs by a bit from today.
- Decode. A pass that carries only generated tokens uses the exact kernels. Given the same
  cache contents, sampling, speculation and the drafter behave exactly as they do today.
- Embedding and rerank passes, the float formats, Q8_0, Q5_K, the ternary formats, and Q5_0
  (see §6 for Q5_0).
- The chat template, the tokenizer, the sampler.

## 2. The 8-bit form

Per matrix row and per 256-weight super-block, exactly the fork's `q8_k_r16` arithmetic
(`docs/design/s5-prefill-avx512.md` §11.1), so the two engines' fast modes are comparable:

1. dequantise the block's 256 weights to f32 with the format's own formula, each sub-block in
   file order. Q4_K's is `w = q·Ld·d − dmin·Lm` with the fork's own operation order: `q·Ld` is
   an exact int16 product, `(−dmin)·Lm` one f32 multiply, and the weight one f32 fma. Q6_K
   never forms an f32 weight: its products are the int16 `(q − 32)·L` — the six-bit code is
   *signed*, the format's `−32` offset is inside the product — and the block's `d` enters only
   the scale;
2. `m = max |w|` over the 256 weights; `scale = m / 127` (f32, a division). An all-zero *Q4_K*
   block has scale 0 and codes 0 (Q6_K's all-zero block takes item 4 and keeps `scale = d`);
3. `code_i = round_to_nearest_even(w_i · (1/scale))`, an int8 in `-127..=127`, with the
   reciprocal rounded to f32 first — the fork multiplies by a rounded reciprocal, it does not
   divide (`PackerQ80::convert`, `iqk_gemm_kquants.cpp:16-26`, `:2464-2466`);
4. Q6_K's exact case is kept: when `max|p|·(1/127) < 1` — i.e. the block's integer products
   `(q − 32)·L` all fit in int8 — the codes are those products and `scale = d · 1 = d` (no
   rounding at all).

A product is then `Σ code_i · a_i` in integers over the block, times `scale`, times the
activation scale: one multiply per (row, block) where the exact kernel has one per 32 weights
plus a minimum term.

The **scalar twin is the definition** (ADR 0005): a plain loop that builds the form and one
that multiplies with it. Every SIMD body (AVX-512 first, then AVX2 and NEON) must equal it bit
for bit. The integer sums are exact in any grouping, so this is a statement about the epilogue
only, and the three tiers can agree with each other as well; the goldens stay per tier anyway.

**Where the form lives** is an implementation choice the first build step measures (§5): a
resident copy built at load (one byte per weight more memory: about +1.2 GB for a 1B Q4_K_M
file, cacheable in the packed-weight cache), or a conversion of each tile inside the pass (no
memory, a cost per pass that only wide passes amortise; this is what the fork does). The
results are identical either way; only speed and memory differ.

## 3. The guarantees in fast mode

ADR 0003's default guarantee has four parts. With `--fast-prompt` on:

| Guarantee | Default | With `--fast-prompt` |
|---|---|---|
| Same tokens as the exact reference path | yes | **no**: by how much is the accuracy report (§4), not published until S5.4c |
| A request's result does not depend on batch size, chunk size, other users or thread count | yes | **yes**: the 8-bit form is used for prompt rows at *every* pass width (the fork only switches above 32 rows, which is why its results depend on `-ub`) |
| The same tokens on every CPU tier, up to the tier's golden | yes | yes, with a fast-mode golden per tier |
| A conversation continues the same whether its beginning was restored from the cache or read again | yes | **no**: a token that was *generated* has an exact cache entry, and the same token read again as *prompt* (after the prefix store dropped it, or on another server) gets the 8-bit one |

The last row is the one new kind of difference, and it is inherent in the trade: making it go
away would mean decoding with the 8-bit form too, which is slower for decode (twice the bytes
per weight through a memory-bound pass). It is stated in the option's help and in the report.

The option is a property of the server or the command, not of a request: all requests of a
process see the same mode, so the prefix store never mixes caches of the two modes. A packed
8-bit copy on disk is keyed by the file's hash and the form's version.

## 4. The accuracy report (required before it ships)

On the gate models of `docs/targets.md` that have Q4_K/Q6_K matrices (Llama 3.2 1B, Qwen 2.5
0.5B, SmolLM2 360M, Gemma 3 1B, Qwen 3 1.7B; all Q4_K_M), 40 chunks of 512 tokens of wikitext-2
with the `kld` tool (`docs/dev/accuracy.md`), each chunk read as a prompt:

1. fast mode against Peregrine's exact mode: mean, median and 99 % KL divergence, RMS Δp, same
   top token;
2. both modes against the unquantised (F16) model, so the report says how much of the Q4_K_M
   error budget the option spends (the fork's is 44 % on the 1B);
3. the task-accuracy suite (`benchmarks/accuracy/`) with the option on and off;
4. the tool-calling comparison (`scripts/tool-e2e.py`) on Qwen 2.5 0.5B with the option on:
   the same calls or not.

**Bound to ship:** mean KL divergence of fast against exact no worse than 0.0015 on the 1B
(the fork measures 0.0011 with the same arithmetic; a larger number means the form was built
wrongly), and no task-accuracy score outside the suite's run-to-run spread. The numbers go in
`docs/targets.md` beside the KV-cache precisions, and the option's help text quotes the 1B's.

## 5a. As built: the kernel, and what it costs (S5.4a)

Built 2026-11-12 on the desktop. The form, its scalar twin, the AVX-512 bodies of both, and a
`kqbench` mode that measures them; nothing is dispatched (`crates/peregrine-kernels/src/kq8.rs`,
`kqsimd.rs`'s `q8k_*`, `KQBENCH_PROMPT=1`). Raw numbers, the conformance harness and the exact
commands: `benchmarks/results/desktop-zen5-2026-11-12-s5.4a/`.

**The layout.** Eight output rows of a matrix are interleaved per 256-weight super-block, the
way the engine's `Q4K8` tile interleaves them, because the AVX-512 kernel's weight operand is
one 512-bit load per (eight-weight group, activation row): eight rows × eight codes. One
super-block of the form is 2112 bytes — 2048 of codes (`qs[group·64 + row·8 + k]` is weight
`group·8 + k` of row `row`, stored as the fork's `code + 128` so `vpdpbusd` can take it as its
unsigned operand), the eight rows' f32 scales, and 32 bytes of padding that keep every 64-byte
load on one cache line. One weight costs **1.03125 bytes**, against the file's 0.5625 (Q4_K)
and 0.8203 (Q6_K). Q5_0's form is the same object built from its 32-weight blocks, one scale
per 256 weights, so one kernel multiplies all three.

**The multiplication.** `vpdpbusd` over the biased bytes; the bias is paid back once per
(row, super-block) as `−128 · Σa` in int32 lanes, where `Σa` is the activation's
whole-super-block sum (`KqActs::sum256`, which the exact kernels do not read); then one
`d · dk` multiply and one fused multiply-add per (row, block). The integer lanes cannot
overflow: a lane sees 32 instructions of four products, `128 · 255 · 127 = 4 145 280`, and
`vpdpbusd` wraps rather than saturating six orders of magnitude above that. Eight activation
rows per group is the widest that keeps the sixteen accumulators and the scale vector in the
ZMM file — the same budget the exact Q4_K tile kernel uses, and the same eight.

**The measurement** (one thread, 2048 × 8192, 1024 tiles, load 8.3, MONOTONIC 10 % fast so
every GMAC/s is ~10 % conservative; exact = today's kernel, resident = the form built once,
per-pass = built inside the pass):

| format | 1 act | 8 | 16 | 64 | 128 | 512 |
|---|---|---|---|---|---|---|
| Q4_K exact | 33.6 | 65.3 | 62.7 | 63.2 | 74.4 | 66.2 |
| Q4_K resident | 22.0 | 85.3 | 73.6 | 84.0 | 95.5 | 91.9 |
| Q4_K per-pass | 1.6 | 10.6 | 18.6 | 45.4 | 68.3 | 82.1 |
| Q6_K exact | 18.8 | 39.7 | 38.9 | 43.3 | 46.7 | 45.3 |
| Q6_K resident | 19.4 | 92.2 | 73.4 | 83.2 | 89.0 | 90.1 |
| Q6_K per-pass | 1.4 | 10.0 | 17.0 | 42.8 | 61.1 | 79.9 |
| Q5_0 exact | 21.4 | 42.4 | 49.0 | 49.2 | 45.1 | 42.9 |
| Q5_0 resident | 22.0 | 87.3 | 81.5 | 89.8 | 92.2 | 90.6 |
| Q5_0 per-pass | 1.5 | 10.0 | 20.9 | 51.7 | 62.1 | 81.8 |

GMAC/s/core. The conversion runs at 1.4–2.0 G weights per second, and §10/§11's number for
the fork's own kernel at this shape is 91 GMAC/s at 512 activation rows: the resident form
measures 91.9.

From that table:

- the resident form is **ahead of the exact kernel at every width above eight rows** (+17 % to
  +132 %), and *behind* at one row, where the pass is bandwidth-bound and the form's 1.03
  bytes per weight cost Q4_K 35 %;
- the per-pass form **overtakes the exact kernel at about 128 rows** (−8 % for Q4_K at 128,
  +31 % and +38 % for Q6_K and Q5_0, +24/+76/+91 % at 512) and is far behind below it;
- **a resident form costs 1.187 GiB on Llama 3.2 1B Q4_K_M**, whose Q4_K/Q6_K/Q5_0 tensors hold
  0.745 GiB: +0.38 bytes per weight, +0.44 GiB — cheaper than the +1.2 GB guessed above,
  because a Q4_K_M file is not 0.56 bytes per weight all the way through.

**Recommendation** (the owner's call): build it **resident**, in the packed-weight cache, keyed
by the file's hash and the form's version. It is the faster of the two at every width the mode
is for, it needs no conversion in the token path, and 0.44 GiB on the 1B is the price. The
per-pass conversion is the fallback only if that memory is not available, and with the build as
it stands it would need to be four times faster before it competed below 128 rows.

**The conformance.** Peregrine's codes and scales are identical to the fork's arithmetic on
1 441 792 weights of the real 1B file (Q4_K and Q6_K, six tensors, `cmp` of every scale and
every code). The intended oracle — the fork's own exported conversion, called from a C harness
linked against the cached `libggml.so` — returned `true` and wrote zeros for every input tried,
including a hand-built four-row block whose only possible output is ±945 codes, so the
comparison is against a transcription of the fork's source lines with a correctly-rounded
`fmaf` (`fork_requant.py`). That is a finding about the cached build, recorded in the results
README, and it is the one open question this step leaves: the two engines' fast modes are
comparable in arithmetic, but not through the fork's binary.

**The re-rounding error**, measured on both models and over every Q4_K/Q6_K/Q5_0 tensor: mean
0.0018–0.00197 of the super-block's maximum, worst 0.00394 (**the bound, `max/254`, reached**),
0.4 % of Q4_K weights exactly on the grid. Q5_0's worst and mean are the same as the
k-quants'. No Q6_K block of either model is in the fork's exact case: its weights are never all
below 1.0 in a 256-weight block. Which leaves §4's bound (mean KLD ≤ 0.0015 on the 1B) where
the fork's own 0.0011 says it will land, and nothing here moves it.

## 5b. As built: the option, the dispatch and its cost (S5.4b)

Built 2026-11-12 on the desktop. The form is **resident** (§5a's recommendation): built once
per Q4_K and Q6_K matrix when the option is on and kept in memory. The per-pass conversion is
not wired in. Raw numbers and the exact commands:
`benchmarks/results/desktop-zen5-2026-11-12-s5.4b/`.

### The option

`PEREGRINE_FAST_PROMPT=1` (`--opt FAST_PROMPT=1`), plus `--fast-prompt` on `peregrine serve`,
`run` and `bench`. It is an ordinary entry of `crates/peregrine-core/src/options.rs`, off by
default, recorded by `pairs()` — so `/metrics`' `peregrine_option{name="fast_prompt"}`,
`peregrine tier`, `peregrine inspect` and `bench --json` all carry it. The process's option is
the engine's (`Engine::build`), so every model of a multi-model server sees the same mode. A
server logs one line at start; on a tier without a SIMD body the line says that the mode runs
through the scalar twin.

### Where the row flag comes from

The flag travels on the activation row: `QuantAct::prompt`, set by
`Model::forward_rows_marked` (and `forward_marked`) from a slice the engine builds, one flag
per token. `State::acts` is reused across layers and `QuantAct::fill` does not touch the flag,
so the same mark reaches every layer's matmuls of the pass.

* `Engine::prefill_chunk` marks every row of a token slot's chunk.
* `Engine::step`'s mixed pass marks the `n_dec` leading decode rows false and each prefilled
  chunk true (the pass is built decode rows first, then prompt chunks).
* `Engine::decode` and the verification pass mark nothing (`Model::forward_rows` clears every
  flag).
* Pooled (`Want::Pooled`), label (`Want::Labels`) and classifier-head (`Want::Head`) slots are
  never marked, even when their prompt shares the pass; `Model::forward_texts` (embeddings,
  rerank, decisions) clears every flag too. Drafter and MTP forwards have their own state and
  never see a mark, so they are decode.
* A model loaded without the form (the option off) has `TensorInfo::q8_off == None` everywhere,
  so a mark would be a no-op; the engine does not mark either.

### The dispatch

`blocks::linear::matmul_group` splits a pass into runs of one row kind when the pass is mixed
and any matrix of the group carries a form. Each run goes through `matmul_block` as if it were
alone, and a row's kernel depends only on its own flag: **a prompt row is 8-bit at every pass
width and chunk size, a generated row is exact at every width**, whatever else is in the pass.
Two kernels are chosen inside `matmul_block`:

* the repacked k-quant path (`MatPath::KqTiles`) and the per-row path (`MatPath::PerRow`) —
  the latter is where Q6_K lives on x86 — compute whole runs of eight rows from the form with
  `MatKernels::q8k_gemm`, and a matrix's tail rows (past the last whole run) stay exact;
* every other format keeps its kernel. Q5_0, Q5_K, Q8_0, the ternary and float formats have no
  form in this step.

`q8k_gemm` is the AVX-512 `q8k_gemm_zmm` on that tier, the AVX2 `q8k_gemm_avx2` on the AVX2
tier (§5d); S5.4d's NEON bodies exist (§5e) and S5.4e wires them into this dispatch: since then
aarch64 with `dotprod` runs them (§5f). Every other tier takes the scalar twin `kq8::gemm_q8k`.
The interleaved activation is filled for a
fast run at any width (`KqActs::fill_with`), and its whole-block sums are computed only then:
with the option off the exact kernels do exactly the bit of work they did before S5.4a.

One pass-size change was needed for the wide chunk: `MAX_BATCH` (the driver's scratch width)
is 512 and `DEFAULT_BATCH` (what one kernel call takes when the fast mode is not in play) is
still 128. A marked pass may therefore be 512 rows wide; every other pass keeps the split it
had, so the default mode's kernels see the same calls as before.

### The resident form's cost

Built at load from the file's own bytes (`crates/peregrine-core/src/q8form.rs`), so it does
not depend on `PEREGRINE_KREPACK` and a scalar tier gets it too. On Llama 3.2 1B Q4_K_M
(96 Q4_K + 17 Q6_K matrices, 762.6 MiB of weights) the form is **957.0 MiB** (measured by
`PEREGRINE_FAST_PROMPT=1 peregrine inspect`), and the load costs **0.52 s** with the AVX-512
builder against 1.29 s without the form (one run each, 1-minute load 8.4; the scalar twin
would take about 26 s). The form is not in the packed-weight cache in this step: S4.9e's file
header has room for two stores and a third would need a new version, while the build is half a
second. That entry is a follow-up.

The design guessed +1.2 GB; the measured +0.94 GiB is smaller because a Q4_K_M file's Q4_K and
Q6_K run at 0.56 and 0.82 bytes per weight rather than one number.

### The first generated token's row

The engine leaves a token slot's last prompt token for the first decode step
(`Slot::prefill_len` is `prompt.len() - 1` for `Want::Tokens`). So the logits the first
generated token is sampled from come from the **last prompt token, computed as a decode row:
exact** (§1's decode rule), whose attention reads the 8-bit K/V the prompt wrote. §5's brief
expected that row to be an 8-bit row; the design and the engine both say exact, and that is
intended: the first generated token is affected by the form through the cache, not through its
own row. A prompt row that wants logits directly (`forward_marked`, a label slot's row) is
8-bit when marked, as are the head's rows for it.

### The tests

`crates/peregrine-models/tests/fast_prompt.rs` (synthetic models, no model files):

* the cache and the logits after a prompt are bit-identical at chunks 16, 32, 64 and 128, at
  1, 2 and 4 threads, and at every chunk beside a decoding user's rows in the same passes;
* decode from a cache a fast-mode prefill produced equals the default engine's decode from the
  same cache (tokens and logits), on Q4_K and Q6_K;
* the prompt's logits are **not** the exact mode's, so the option cannot silently do nothing;
* every re-rounded weight is within `max|w| / 254`, checked end to end through the engine's
  load path on one real matrix of the synthetic file (Q4_K and Q6_K, >100 000 weights);
* embeddings (pooled) and decisions (labels) are bit-identical with the option on and off, on a
  model that carries the form;
* two slots, one prefilling and one decoding in the same passes, each get the tokens they get
  alone in the same mode;
* the prefix store: a prompt restored from it gives the same tokens as the same prompt read
  again (both are prompt rows), and the documented exception is pinned — a token whose cache
  entry was written by a generated (exact) row and the same token read as a prompt (8-bit) give
  different caches.

`crates/peregrine-models/tests/synthetic.rs` adds fast-mode goldens for one Q4_K and one Q6_K
synthetic model under `tests/golden/synthetic/<tier>/llama-<fmt>-fast.golden`, recorded on the
three x86 tiers (native AVX-512, `PEREGRINE_ISA=avx2`, `PEREGRINE_ISA=scalar`). The Q4_K
goldens are identical on all three; the Q6_K ones agree in argmax and greedy tokens but not in
the logits hash between scalar and AVX2, because the prompt's logits still pass through kernels
the form does not replace (the tier's exact decode rows, the head's tail rows and the tier's
norm/attention paths). The 8-bit form itself is tier-independent.

## 5d. As built: the AVX2 body (S5.4d, x86 half)

Built 2026-11-12 on bluefin (Ryzen 3 PRO 4350G, Zen 2, AVX2 + FMA, no AVX-512, no AVX-VNNI).
The body, its builder and the dispatch; raw numbers, commands and the other engines:
`benchmarks/results/bluefin-2026-11-12-s5.4d/`.

### The formulation

`vpdpbusd` is the AVX-512 body's whole trick, and AVX2 has nothing like it: `vpmaddubsw` gives
32 products per instruction and **saturates** its int16 result. The stored byte is `code + 128`
(1..255, so `vpdpbusd` can take it as its unsigned operand), and against an activation of
`127` two products reach `2 · 255 · 127 = 64 770` — twice int16. The AVX-512 bound does not
carry over, so the AVX2 body uses the `vpsignb` sign trick llama.cpp uses for its int8 × int8
dot product:

1. `ws = w − 128` recovers the signed code from the biased byte. The add is exact: the stored
   byte is `code + 128` in a byte, and `+128` is `^0x80`, so subtracting 128 mod 256 gives the
   code back for every code, `−128` included;
2. `wa = |ws|` as bytes, i.e. 0..=127 — and 128 for `code = −128`, where `vpsignb`'s result
   wraps to `0x80` and is read as the unsigned byte 128, which is still inside the bound;
3. `sa = sign(a, ws)`, the activation with the code's sign applied;
4. `vpmaddubsw(wa, sa)` is then `|c| · sign(c) · a = c · a` per pair, and its largest pair sum
   is `2 · 128 · 127 = 32 512 < 32 767`, so it never clamps — not even at the form's most
   negative code.

One `vpmaddwd` against ones widens each row's four int16 to two int32, and one `vpaddd`
accumulates: **four instructions per 32 products**, 8 MAC per instruction, where the AVX-512
body's one `vpdpbusd` is 64. A lane accumulates `2 · 32 · 4 · 128 · 127 = 4 161 536` over a
super-block, six hundred times inside int32, and the epilogue is the AVX-512 body's operation
for operation — one multiply `d · dk` and one fused multiply-add per (row, super-block).

**There is no bias term.** The sign trick already multiplies the *signed* code, so unlike the
AVX-512 body, which pays `−128 · Σa` back, the AVX2 body never reads `KqActs::sum256`. The
activation's codes are `−127..=127` (the quantiser's range, pinned by
`the_eight_bit_lanes_cannot_overflow`), which is what makes `sign` exact: an activation code of
`−128` would negate to itself in int8, and the engine never produces one.

The form's group window is 64 bytes — eight rows of eight codes — so a 256-bit register holds
four of the eight rows and the super-block is walked twice, one half of the window at a time,
with four float accumulators per activation row. Eight activation rows per group is the widest
that keeps the eight int32 accumulator vectors, the two weight windows and the temporaries in
the sixteen registers.

### The proof

* `crates/peregrine-kernels/src/kqsimd.rs`: `the_eight_bit_avx2_kernel_is_bit_identical_to_the_twin`
  — nine forms (random Q4_K, the tie tile, Q6_K just outside its exact case, and three
  hand-built: every code `−128`, every code `127`, at one, two and three and five
  super-blocks) against six activations (random, every code `−127`, every code `127`, and an
  alternating ±127 pattern) at the twenty width classes 1, 2, 3, 4, 7, 8, 9, 15, 16, 17, 31,
  32, 33, 64, 127, 128, 129, 256, 511 and 512 activation rows — `to_bits` equal to
  `kq8::dot_q8k`, 8 rows × every activation of every form;
  `the_eight_bit_avx2_build_is_bit_identical_to_the_twin` — the builder, byte for byte, on the
  same edge tiles (all-zero, one huge weight, the six-bit limits, the tie tile, Q6_K's exact
  case and one just outside it) at one, three and five super-blocks;
  `the_eight_bit_avx2_int16_stage_cannot_saturate` — the bound above, and the naive
  formulation's failure of it; and `the_tier_dispatches_a_body_that_is_the_twin`, which holds
  `MatKernels::q8k_body`/`q8k_gemm`/`q8k_build` to the twin so the dispatch cannot rot.
* The tier's fast goldens (`tests/golden/synthetic/x86_64-avx2/llama-Q4_K-fast.golden`,
  `llama-Q6_K-fast.golden`) were recorded with the scalar twin and pass **unchanged**: no
  golden file moves in this PR.
* `cargo test --release -p peregrine-models --test fast_prompt` passes natively (where
  `q8k_body()` is `Some("AVX2")`) and with `PEREGRINE_ISA=scalar`.

### What this step found: the mode is not faster on AVX2, and cannot be

On the 1B the fast mode is **0.88-0.92 of the exact engine** on every cell; against
ik_llama.cpp at its defaults that puts it at **0.93-0.95**, where the exact mode is 1.02-1.08.
The Qwen 0.5B is level (0.97-1.03) only because its file keeps 165 of its 374 MiB of weights in
Q5_0, which the form does not cover.

The cause is the instruction set, not this implementation. Four instructions per 32 products is
the floor for a bit-exact 8-bit dot on AVX2, because the products are too large to chain in
int16 (the exact Q4_K kernel's nibbles chain eight deep and get 21 MAC per instruction). The
body measures 14.5 MAC/cycle at 4.1 GHz, which is this core's two 256-bit vector ops per cycle;
the exact Q4_K kernel is at 18.9 MAC/cycle because it is latency-bound, not throughput-bound.
The nibble split of the codes and the int16 `vpmaddwd` path were both counted and both land
below the sign trick's rate.

So the trade the design note describes holds only where the exact kernel is weaker: **Q6_K is
1.30× the exact kernel's rate**, and a Q6_K-heavy file would show the mode ahead. On a
Q4_K-heavy file it is behind by about a tenth. The option stays off by default, its help text
now says so, and S5.4c's report (on the AVX-512 host) is where the *accuracy* of the trade is
published — the two modes' results are bit-identical across tiers, so that report is the same
arithmetic on this tier.

### The chunk

128 and 256 are tied within 0.2 % on the 1B (54.3/54.4 at 512/1, 204.9/204.5 at 512/4,
160.4/160.4 at 4096/4); 64 is 2 % behind and 512 is 2-9 % behind. The fast mode's default wide
chunk stays **256** (`WIDE_CHUNK_DEFAULT_FAST`): the brief's rule — move it only on a gain over
5 % on both models — is met by no chunk.

## 5e. S5.4d on ARM: the NEON bodies

Built 2026-11-12 on the DGX Spark, in `crates/peregrine-kernels/src/neon.rs`; raw numbers and the
conformance harness: `benchmarks/results/spark-arm-2026-11-12-s5.4d-neon/`. **As built**, the
bodies were not wired in: S5.4b's dispatch still took `kq8::gemm_q8k` on NEON, `q8k_gemm` here was
the tier entry point for the tests and `neonbench`, and no default-path file changed. **S5.4e
wired them into `MatKernels::q8k_gemm`/`q8k_build`; §5f is that build and its numbers.**

**The bodies.** The build (`q8k_build_q4k_neon`, `q8k_build_q6k_neon`, `q8k_build_q5_0_neon`) is
vectorised: the nibble loads, the exact integer product, the f32 fused multiply-add with the min
term, the vector max, `vcvtnq_s32_f32` (round ties even), a saturating `vqmovn` pair and the
form's `+128` bias. The multiply has one body per tier: `q8k_gemm_sdot` (four int32 row-pair
lanes per 16-byte weight load, the activation's eight codes duplicated into the other operand)
and `q8k_gemm_i8mm` (`smmla` over two output rows × two activations, four row pairs and two
activation pairs per four-row group, the 1–3-row tail on `sdot`). The form stores `code + 128`
for x86; ARM's `sdot` and `smmla` are signed, so the kernel undoes the bias with `eor 0x80` and
computes `Σ code·a` directly. The integer sums are exact in any grouping, and the epilogue is the
twin's own `d·dk` multiply then one fused multiply-add per (row, super-block), in the twin's
order. `q8k_gemm` picks `smmla` on `neon-i8mm`, `sdot` on `neon-dotprod` and the twin otherwise.

**The conformance.** Builds are byte-identical to the twin on random Q4_K/Q6_K/Q5_0 tiles and on
every edge tile S5.4a uses (all-zero, one huge weight, six-bit limits, exact halves, Q6_K's exact
case and one just outside it; Q5_0's short last super-block included). Both multiply bodies are
bit-identical to `kq8::dot_q8k` on four forms at every width 1..=40 and 63/64/65, 127/128/129,
511/512/513. The tier test sees each cap pick its own body. All pass under `PEREGRINE_ISA=scalar`,
`neon`, `neon-dotprod` and `neon-i8mm`; no golden moved.

**The measurement** (one thread and ten, GMAC/s; `4096 × 512` is the S4.9q layer shape, `8192 ×
2048` streams 256 forms from L3/DRAM; exact = today's tile kernel, form = the resident form):

| Q4_K form | sdot | 59.8 | 169.7 | 180.0 | 176.2 | 351 | 1484 | 1762 | 1733 |
| Q4_K exact | i8mm | 48.6 | 121.6 | 124.5 | 123.4 | 376 | 1155 | 1212 | 1190 |

## 5f. As built on ARM: the dispatch and the numbers (S5.4e)

Built 2026-11-12 on the DGX Spark, on `origin/s5.4d-prompt-kernel-neon` (which carries
`origin/main` at `e4ad034`). Raw runs, the round script and the summarizers:
`benchmarks/results/spark-arm-2026-11-12-s5.4e/`. The mode's numbers do not depend on the body:
`cargo test --release -p peregrine-models --test fast_prompt` passes natively and under
`PEREGRINE_ISA=neon-dotprod`, `neon` and `scalar`, and every fast golden is recorded per tier and
checked again without the record switch.

**The dispatch.** Three functions in `crates/peregrine-kernels/src/table.rs` gained an aarch64
arm, inside `cfg(all(target_arch = "aarch64", feature = "fmt-kquant"))`, x86 untouched:

- `q8k_gemm`: when `cpu::have_dotprod()` holds it calls `neon::q8k_gemm`, which takes `smmla`
  where `cpu::have_i8mm()` holds and `sdot` otherwise; without `dotprod` (the `neon` and
  `scalar` caps) it stays on `kq8::gemm_q8k`. The SAFETY comments name the tier check and the
  bounds the wrapper re-checks.
- `q8k_build`: when `cpu::have_neon()` holds it calls `neon::q8k_build_q4k_neon` /
  `q8k_build_q6k_neon`. The builder needs only `neon`, so the `neon` cap gets the NEON build
  (a faster load) even though its multiply is the twin.
- `q8k_simd`: true where the multiply is a NEON body (`have_dotprod()`), false on `neon` and
  `scalar`, so the startup line and `peregrine tier` do not claim a body that is not there. A
  new `q8k_body()` returns the name (`AVX-512 body`, `NEON smmla body`, `NEON sdot body`, or
  the scalar-twin sentence); `peregrine serve` prints it in its one-line notice, and
  `peregrine tier` prints a `fast prompt` line when the option is on.

`neon.rs`'s own tier test still pins that `q8k_gemm` picks `smmla` on `neon-i8mm` and `sdot` on
`neon-dotprod`; a new test calls the table's entry points and checks the same counters, the
builder's bytes against the twin's, and the results against `kq8::dot_q8k` at four rows.

**The goldens.** `llama-Q4_K-fast` and `llama-Q6_K-fast` are now recorded per aarch64 tier:
`aarch64` (twin forced with `PEREGRINE_ISA=scalar`), `aarch64-neon` (NEON builder, twin
multiply), `aarch64-neon-dotprod` (`sdot`) and `aarch64-neon-i8mm` (`smmla`), with
`PEREGRINE_GOLDEN=record cargo test --release -p peregrine-models --test synthetic -- fast_prompt_mode`.
The Q4_K golden is **identical on all four tiers** (the form's integers are exact and the Q4_K
path adds no tier kernel the test reaches); the Q6_K golden is identical on the three NEON
tiers and differs from the forced-scalar one, the same split S5.4b saw on x86: the prompt's
logits still pass through the tier's exact decode rows and norm/attention paths. No existing
golden file changed; the new ones are the only `*-fast.golden` under an aarch64 directory.

**The chunk.** At ten threads the fast mode's 512-row pass is best on all four cells of both
models, 7.7–26.6 % over 256 (Llama 3.2 1B 512: 645.5 against 517.3 tok/s; Qwen 2.5 0.5B 4 096:
399.7 against 336.9), and at one thread 512 is level with 256 (81.0 against 81.0, 88.5 against
89.0). That clears the "over 5 % on both models" bar, so **aarch64's fast-mode wide chunk is
512** (`WIDE_CHUNK_DEFAULT_FAST_ARM` in `options.rs`); x86 keeps S5.4b's 256. No limit moves: a
512-row pass is `MAX_BATCH`.

**The numbers.** Medians over interleaved rounds (the host was shared; the load is beside every
cell in the results README). At ten threads, Llama 3.2 1B Q4_K_M: 254.4 exact, 645.5 fast
(chunk 512) — **2.54× the exact default**, 3.32× llama.cpp and 1.43× ik_llama.cpp; at 4 096
tokens 183.1 → 375.0 (**2.05×**), 2.13× llama.cpp, 0.81× ik. At one thread: 93.6 → 192.5
(**2.06×**) at 512 tokens and 55.8 → 81.0 (**1.45×**) at 4 096; the 4 096-token one-thread cell
is 0.96× ik, the only one-thread cell where an engine is ahead. Qwen 2.5 0.5B, whose 165 MiB of
Q5_0 and 139 MiB of Q8_0 have no form, gains 1.07–1.91× (247.4 → 399.7 at 4 096/10 threads;
141.8 → 161.5 at 512/1), is 1.76–2.61× ahead of llama.cpp on its one-thread cells, and is
behind ik on all four cells (0.47–0.69×). Where it is behind: every Qwen cell against ik,
and Llama's 4 096-token cells against ik — Q5_0/Q8_0's absence and ik's own repack.

The form costs +966 MiB of peak RSS and +0.48 s to load on the 1B (957.0 MiB of form), +110 MiB
and +0.14 s on Qwen; decode after a fast prompt is level with decode after an exact one
(1.006× and 1.012× at one thread, where the host's noise could not reach). Greedy tokens of two
plain prompts on the 1B: one identical, one differs at its 11th word ("horizon" against
"waters"). The accuracy report remains S5.4c's.

**What S5.4e leaves.** Q5_0's form (design §6), and a quiet-host rerun of the ten-thread cells
for S5.4c's table. AVX2's body landed in parallel as §5d and does not change this section's
numbers (the ARM dispatch never takes it).

## 6. Open points

- **Q5_0.** Qwen 2.5 0.5B's Q4_K_M file keeps part of its weights in Q5_0, whose exact kernel
  is bound by a fold per 32 weights (§11.5 of the study). The same 8-bit form applies to it
  and would remove that fold, but it is a second re-rounding with its own error. S5.4a
  measures the kernel; it joins the option only if S5.4c's report shows the accuracy bound
  still holds with it, and it is then listed in the report as its own line.
- **Wider chunks and time to first token.** A wide prompt pass delays the decode steps of
  other users. The wide chunk already applies only when no slot is decoding (S5.1a); fast mode
  keeps that rule.
- **Decision models and embeddings** read prompts too, but their answers are read off the
  prompt's last row, so the option would change their numbers directly. They are excluded
  until a report covers them.

## 7. What is said in public

`docs/benchmark.md` keeps two rows against ik_llama.cpp: Peregrine's default (exact) and
Peregrine with `--fast-prompt`, each against the fork at its defaults, and states that the
fork's default is the approximate path. The README's "where Peregrine is behind" sentence is
rewritten from those two rows when S5.4c lands.
