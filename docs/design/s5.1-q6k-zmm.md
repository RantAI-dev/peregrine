# S5.1, Q6_K: the 512-bit tile kernel, as built

- Status: built and measured, no result moved
- Date: 2026-11-11
- Host: AMD Ryzen AI 9 HX 370 (Zen 5, 12 cores / 24 threads, AVX-512 F/BW/VL/VNNI/VBMI), WSL2
- Baseline for this change: `s5.1-kq-epilogue` (S5.1's PR 1)
- Raw measurements: `benchmarks/results/desktop-zen5-2026-11-11-s5.1-q6k-zmm/`

This is item 2 of `docs/design/s5-prefill-avx512.md` §6: Q6_K was 15.4 % of Llama 3.2 1B's
prefill and its kernel ran at 37–39 GMAC/s ("9 % of the 455 GMAC/s roof, the worst placed of all").
The "as built" note for item 1 is `docs/design/s5.1-kq-epilogue.md`; both fold into the study's §6
when PR #194 lands.

---

## 1. What was built

`q6k8_gemm_zmm` beside `q6k8_gemm`, on the same eight-row `Q6K8` tile and reading the same
interleaved activation:

- **The codes come out of a 64-byte load.** The tile already holds a window as eight rows'
  eight bytes, so the Q4_K kernel's shape applies directly: the low or high nibble of `ql`
  (`high = g ≥ 2`) OR'd with bits `2g..2g+2` of `qh`, moved into bits 4..6, gives eight six-bit
  codes per row.
- **`vpdpbusd` into int32, with no int16 stage.** The codes (0..63) are the unsigned operand and
  the activation the signed one, four products per int32 lane. The AVX2 kernel widens every two
  `vpmaddubsw` because four products per *int16* lane is its bound; VNNI has no such bound.
- **The run is the unit, because the scale is.** The run's two windows are added and scaled once
  with an exact int32 `vpmulld`, then added into the super-block's sum — 16 runs per super-block.
- **The `-32` offset is the AVX2 kernel's.** `Σ_runs scale · Σq` against the activation's per-16
  sums, in eight `vpdpwssd` of paired scales against paired sums (both int16: `Σq ≤ 2032`,
  `scale ≤ 127`), then `- 32 ·` it in int32. The activation's sixteen per-16 sums are narrowed
  from `KqActs::bs16` with one load and one `vpmovdw`.
- **The fold is `dot_q6k8_ref`'s, unchanged**: `(d · dk) · sum`, then an add, then the whole
  thing added to the accumulator.
- **A group is eight activation rows, window-major**, as the Q4_K kernel learned to: the run loop
  is outside the row loop so sixteen `vpdpbusd` chains overlap.

**The decode path is untouched.** `q6k8_gemv` (the AVX2 one-row kernel the tile store's GEMV
dispatches to) keeps its layout and its bits; the ZMM kernel is selected only for the batched
path (`kq_tiles_q6k`, four rows or more). The task's condition was "a GEMV only if it is faster
than the present one-row path"; a ZMM one-row kernel was not built because the measurement above
(24.8 GMAC/s at one activation row) is on the *batched* API and the row path is the faster shape
for one row, so decode has nothing to gain from being moved.

## 2. The kernel

`kqbench`, `taskset -c 2`, one tile of sixteen super-blocks (18 KiB, L1), median of three rounds.
GMAC/s per core; 2 048 MACs per (tile, activation row, super-block). `row` is the AVX2 per-row
path, `tile` the AVX2 eight-row tile, `zmm` the new kernel.

| acts | row (AVX2) | tile (AVX2) | **zmm** | zmm vs tile |
|---|---|---|---|---|
| 1 | 20.5 | 20.4 | 24.8 | +21 % |
| 4 | 24.1 | 33.0 | **52.9** | +60 % |
| 16 | 37.6 | 39.2 | **62.0** | +58 % |
| 64 | 34.2 | 36.5 | **60.2** | +65 % |
| 128 | 33.7 | 33.9 | **57.2** | +68 % |

The study's reference points: Q6_K tile 37–39 GMAC/s before (matches), ik_llama.cpp's
`Q6_K_R4` 123.1 at 16 acts and 152.8 at 128. The target of 2× was passed; ik is still 2–2.7×
ahead, and the reason is visible in the mix: Q6_K changes scale every sixteen weights, so this
kernel spends 16 int32 scale multiplies per (super-block, activation row) against Q4_K's 8, and
the run's 32 `vpdpbusd` cannot be reduced.

On a DRAM-sized tile (32 768 super-blocks, 55 MiB) the same three kernels read `tile` 31–32 and
`zmm` 45–50 GMAC/s: +41–52 %. That is the operating point of a sixteen-token pass.

## 3. End to end

`peregrine bench --prompt-tokens 512 --tokens 4 --no-profile`, median of five interleaved rounds,
twelve threads, against the branch's own base (PR 1):

| model | before | after | ratio |
|---|---|---|---|
| Qwen 2.5 0.5B Q4_K_M | 505.9 | 497.9 | 0.984 |
| Llama 3.2 1B Q4_K_M | 297.0 | 302.2 | **1.017** |

Decode: 1.032 (Qwen) and 0.988 (1B) in the same series — noise around 1.0, and the Q6_K GEMV is
the same kernel, so there is nothing to move there.

The 1B gains 1.7 % where 15.4 % of its prefill got 60 % faster would predict about 7 %. The same
reason as in the item-1 note: at chunk 16 the matmul streams every weight matrix from DRAM once
per pass, so the kernel's compute rate is only part of its time in situ (§2's DRAM row). Qwen's
Q6_K share is 9.6 % and its series read 1.6 % *down* — inside the noise of a host whose agent's
own UI was running; the kernel's 60 % is not in dispute, the engine-level effect at this chunk is
small.

## 4. What is left

- **Mix the two kernels in one pass**: the Q6_K kernel is 60 % faster than the AVX2 tile but the
  engine's pass is memory-bound at chunk 16, so the remaining win is the wider pass (item 3).
- **A run-pair scale madd** (the AVX2 `vpmaddwd` trick at 512 bits: keep four products per int16
  lane and apply two runs' scales in one `vpmaddwd`) would halve the 16 int32 scale multiplies per
  (super-block, row). That is where the remaining 20–30 % of this kernel is, and it does not
  change any integer.
- **A ZMM one-row GEMV** was not written: the row path is the faster shape for one row, and the
  Q6_K GEMV is not the decode bottleneck.

## 5. Bits

No golden moved. The new kernel's integer sums are the AVX2 kernel's (`vpdpbusd` accumulates the
same products in int32 with no saturation, the scale is an exact int32 multiply, the offset is the
same `Σ scale · Σq` shifted by 32) and the fold is the same expression in the same order.
`the_avx512_q6_k_kernel_agrees_with_the_avx2_one_bit_for_bit` walks four to forty activation rows
at four tile widths and checks one row per width against the scalar reference.
