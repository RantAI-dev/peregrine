# S2.6 Design: Every Format on AVX2, AVX-VNNI-256 Tier, and Startup Calibration

- Status: Proposed
- Date: 2026-11-07
- Target: Roadmap item S2.6 (1.0 person-week)
- Author: Antigravity (Design Sub-Agent)

## 1. Context and Scope

Roadmap item S2.6 covers three interrelated performance and breadth initiatives for Peregrine on modern x86-64 platforms:

1. **AVX2 Format Coverage**: Auditing all 16 formats in `Format::ALL` (`crates/peregrine-kernels/src/format.rs`) to ensure full AVX2 vectorisation across both single-row decode and multi-row batched prefill paths.
2. **AVX-VNNI-256 Kernel Tier**: Introducing a dedicated runtime kernel tier exploiting VEX-encoded 256-bit `VPDPBUSD` (`avxvnni`) on client architectures that omit or disable AVX-512 (Intel Alder Lake through Lunar Lake / Arrow Lake), replacing dual-instruction `VPMADDUBSW` + `VPMADDWD` integer dot-product sequences while maintaining strict bit-identity with AVX2.
3. **Startup Calibration**: Measuring memory bandwidth ridge points and thread barrier wake-up characteristics dynamically on process startup within a sub-second budget (<250 ms) to configure `decode_threads`, `prefill_threads`, and `spin_us` without requiring offline tuning profiles, while maintaining bit-identical outputs.

### 2.2 Findings on AVX2 Coverage

1. **Every format in `Format::ALL` has an AVX2 kernel today.**
   The original roadmap milestone anticipated implementing missing AVX2 kernels during S2.6. However, during the execution of Stage 2 (specifically S2.1d for `Q2_K`/`Q3_K`, S2.1e for `F32`/`F16`/`BF16`, S2.1f for `MXFP4`, and S2.5 for MoE formats), AVX2 single-row and batched tile-4 kernels were implemented ahead of schedule for all 16 formats.
2. **What remains on AVX2:**
   - **Wide Batched Kernels (`wide_*`)**: In `crates/peregrine-kernels/src/simd.rs:1630-1640`, only `Q4_K`, `Q5_K`, and `Q6_K` possess wide kernels that process `nb` = 8, 16, 24, or 32 activations in a single weight streaming pass. For all other formats (`Q8_0`, `Q4_0`, `Q5_0`, `Q2_K`, `Q3_K`, `IQ4_NL`, `IQ4_XS`, `MXFP4`), `dot_batch` chunks activations into slices of `TILE = 4` (`simd.rs:1603-1670`). When prefill batches have 32 or 64 tokens, the weight row must be streamed from L1/L2 cache multiple times. Adding `wide_q8_0` and `wide_kquant` for `Q2_K`/`Q3_K` would complete AVX2 batch efficiency.
   - **Format Gaps Outside `Format::ALL`**: If GGUF formats currently absent from Peregrine are ever in scope (e.g. `IQ2_XXS`, `IQ2_XS`, `IQ3_XXS`, `Q4_1`, `Q5_1`), they lack kernels entirely. Within Peregrine's defined format set, AVX2 coverage is 100%.

## 3. The AVX-VNNI-256 Tier

### 3.1 Hardware Landscape: CPUs with AVX-VNNI without AVX-512

#### Intel Client Architectures
Intel introduced hybrid core architectures starting with Alder Lake (12th Gen Core). Because the Gracemont efficient cores (E-cores) lacked AVX-512 hardware pipelines, Intel disabled AVX-512 across the processor package to preserve ISA symmetry across cores. To prevent AI inference degradation on these client parts, Intel introduced **AVX-VNNI** (CPUID flag `avxvnni`, CPUID.(EAX=7, ECX=1):EAX[bit 4]), which provides VEX-encoded 256-bit and 128-bit vector neural network instructions (`VPDPBUSD`, `VPDPBUSDS`, `VPDPWSSD`, `VPDPWSSDS`) without requiring EVEX prefixes, AVX-512 Foundation (`AVX512F`), or 512-bit registers (`ZMM`):

- **Alder Lake (12th Gen Core)**: Golden Cove P-cores + Gracemont E-cores. AVX-512 fused off / disabled in microcode; full `AVX_VNNI` support (*Source: Intel 64 and IA-32 Architectures Software Developer's Manual; Tom's Hardware, 2022*).
- **Alder Lake-N (Processor N95, N100, N200, N305)**: Pure Gracemont E-core parts. Support AVX2 and `AVX_VNNI`; entirely lack AVX-512 silicon (*Source: Intel Ark specifications; Phoronix, 2023*).
- **Raptor Lake & Raptor Lake Refresh (13th & 14th Gen Core)**: Raptor Cove P-cores + Gracemont E-cores. AVX-512 permanently silicon-fused off; native `AVX_VNNI` (*Source: Intel SDM Vol 1-4*).
- **Meteor Lake (Core Ultra Series 1)**: Redwood Cove P-cores + Crestmont E-cores. No AVX-512; supports `AVX_VNNI` and introduces `AVX_VNNI_INT8` (*Source: Hot Chips 35, Intel Meteor Lake Architecture Brief*).
- **Arrow Lake (Core Ultra 200S/H) & Lunar Lake (Core Ultra 200V)**: Lion Cove P-cores + Skymont E-cores. No AVX-512 on client desktop/mobile; supports `AVX_VNNI`, `AVX_VNNI_INT8`, and `AVX_VNNI_INT16` (*Source: Hot Chips 36, Lion Cove / Skymont Whitepapers*).
- **Sierra Forest (Xeon 6700E)**: Pure Sierra Glen (E-core) server parts. No AVX-512; native `AVX_VNNI` support (*Source: Intel Xeon 6 Architecture Specification*).

#### AMD Architectures: Verification of Zen 5 Claims
It has occasionally been claimed that certain AMD Zen 5 mobile client processors feature AVX-VNNI without AVX-512. **This claim is architecturally false regarding ISA support, though partially true regarding physical datapath width**:
- **ISA Level**: *All* AMD Zen 5 client processors (both Ryzen 9000 "Granite Ridge" desktop and Ryzen AI 300 "Strix Point" / "Krackan" mobile APUs) support both VEX-encoded `AVX-VNNI` and full EVEX-encoded `AVX-512` (`AVX512F`, `AVX512VL`, `AVX512BW`, `AVX512_VNNI`, `AVX512_BF16`, etc.) (*Source: AMD Zen 5 Core Architecture Technical Brief, Hot Chips 36; Phoronix AMD Zen 5 Instruction Set Tests*).
- **Microarchitectural Execution**: On desktop Ryzen 9000, Zen 5 features a native 512-bit physical floating-point/vector datapath. On mobile Ryzen AI 300 (Zen 5 and Zen 5c cores), the physical vector execution pipeline is 256 bits wide to optimize die area and battery efficiency; full 512-bit AVX-512 instructions are split ("double-pumped") across two cycles on the 256-bit units.
- **Implication for Peregrine**: No AMD Zen 5 CPU requires an AVX-VNNI-only tier to run fast dot products; they can all execute Peregrine's AVX-512 tier. However, for systems where the user forces `PEREGRINE_ZMM=0` or on 256-bit mobile Zen 5 parts where 256-bit VEX instructions avoid split-dispatch penalties, an AVX-VNNI-256 tier is microarchitecturally beneficial. On Intel client systems from Alder Lake through Lunar Lake, the AVX-VNNI-256 tier is the *only* way to execute hardware-accelerated integer dot products.

### 3.2 Accelerating Integer Dot Products with `VPDPBUSD`

#### The Baseline: AVX2 Arithmetic Emulation
In current AVX2 kernels (`crates/peregrine-kernels/src/simd.rs` and `crates/peregrine-kernels/src/tern.rs`), integer dot products are computed using the MADD pair:

```rust
// AVX2 integer dot product of unsigned codes and signed activations:
unsafe fn madd_ps(codes: __m256i, acts: __m256i) -> __m256 {
    // 1. Multiply unsigned u8 by signed i8 -> pairs of i16 sums
    let prod = _mm256_maddubs_epi16(codes, acts);
    // 2. Multiply i16 pairs by 1 and sum adjacent pairs -> 8 exact i32 lane sums
    let s = _mm256_madd_epi16(prod, _mm256_set1_epi16(1));
    // 3. Convert i32 to f32
    _mm256_cvtepi32_ps(s)
}
```

This sequence has three notable overheads:
1. **Two Vector Instructions**: `VPMADDUBSW` followed by `VPMADDWD`, consuming 2 execution ports and introducing a 5–6 cycle latency chain before reduction.
2. **Register Pressure**: Demands a dedicated vector register pinned to the constant `ones = _mm256_set1_epi16(1)`. In 16-register AVX2, this constant register steals an accumulator slot, restricting tile width `TILE` to 4.
3. **Accumulator Accumulation**: The resulting `i32` or `f32` vector must be explicitly added to running accumulators with `_mm256_add_epi32` or `_mm256_fmadd_ps`.

#### The AVX-VNNI Transformation: `VPDPBUSD`
The `VPDPBUSD` instruction computes:
$$\text{dst}[i] = \text{dst}[i] + \sum_{k=0}^{3} \text{src1}[4i + k]_{\text{unsigned}} \times \text{src2}[4i + k]_{\text{signed}}$$
for each of the 8 32-bit lanes $i \in [0, 7]$ of a 256-bit `YMM` register.

```rust
// AVX-VNNI 256-bit dot product:
#[target_feature(enable = "avx2,fma,f16c,avxvnni")]
unsafe fn dpbusd_ps(acc_i32: &mut __m256i, codes: __m256i, acts: __m256i) {
    *acc_i32 = _mm256_dpbusd_epi32(*acc_i32, codes, acts);
}
```

#### Kernel-by-Kernel Opportunity:
1. **PQ2_0 and PTQ1_0**:
   - `crates/peregrine-kernels/src/tern.rs:46` already contains `pq2_vnni<const T: usize>`. However, its target feature attribute is currently:
     `#[target_feature(enable = "avx2,fma,f16c,avx512vnni,avx512vl")]`
     and it checks `have_vnni()` (`crate::cpu_has!("avx512vnni") && crate::cpu_has!("avx512vl")`).
   - Consequently, Alder Lake and Raptor Lake run `pq2_avx2` instead of `pq2_vnni`!
   - Gating `pq2_vnni` on `avxvnni` immediately gives client Intel CPUs the 4-plane `VPDPBUSD` pipeline without needing AVX-512.
2. **Legacy Quants (Q4_0, Q5_0, Q8_0)**:
   - `Q4_0`: Unsigned codes `[0, 15]` multiplied by signed activations `[-128, 127]`. Currently uses `madd_offset_ps::<3>`. `VPDPBUSD` folds the product directly into `acc_i32` initialized with `- (lane_sums << 3)`.
   - `Q5_0`: Unsigned codes `[0, 31]` multiplied by signed activations `[-128, 127]`. Initializes accumulator with `- (lane_sums << 4)` and computes product in a single `VPDPBUSD`.
   - `Q8_0`: Weights are signed `i8`, activations are signed `i8`. `VPDPBUSD` expects unsigned $\times$ signed. Handled via either:
     - Method A (Current sign trick): `absw = _mm256_sign_epi8(w, w)` (unsigned `0..127`), `sa = _mm256_sign_epi8(a, w)` (signed). Then `_mm256_dpbusd_epi32(acc, absw, sa)`.
     - Method B (Bias shift): Add 128 to weights (`w_u8 = _mm256_xor_si256(w, 0x80)`), accumulate with `_mm256_dpbusd_epi32`, and subtract `128 * lane_sums` at block end.
3. **K-Quants (Q2_K, Q3_K, Q4_K, Q5_K, Q6_K)**:
   - All k-quants unpack 2-bit, 4-bit, 5-bit, or 6-bit codes into unsigned nibbles/bytes before multiplying against signed activation scales and quantized bytes.
   - `tile_q4_k` and `wide_q4_k` currently execute 4 to 8 `maddubs` + `madd` pairs per 256-element super-block. Replacing them with `_mm256_dpbusd_epi32` reduces instruction count in the inner loop by ~40% and frees vector registers, enabling wider unrolling.

### 3.3 Exactness and Bit-Identity Invariant

Peregrine's Invariant 1 (`ARCHITECTURE.md`) requires:
> **Same tokens.** For a fixed seed, a user's tokens do not depend on batch size, on other users, on speculation being on or off, or on which CPU kernel tier ran.

**Question: Must the outputs of AVX-VNNI be bit-identical to AVX2?**
**Answer: Yes, and integer arithmetic guarantees they are.**

#### Why Integer Accumulation is Exactly Identical
1. **Mathematical Equivalence**:
   In AVX2:
   `vpmaddubsw` computes $p_0 = c_0 \cdot a_0 + c_1 \cdot a_1$ and $p_1 = c_2 \cdot a_2 + c_3 \cdot a_3$ in 16-bit signed arithmetic. `vpmaddwd` with `ones` computes $s = 1 \cdot p_0 + 1 \cdot p_1 = c_0 \cdot a_0 + c_1 \cdot a_1 + c_2 \cdot a_2 + c_3 \cdot a_3$ in 32-bit signed arithmetic.
   In AVX-VNNI:
   `vpdpbusd` computes $s = c_0 \cdot a_0 + c_1 \cdot a_1 + c_2 \cdot a_2 + c_3 \cdot a_3$ directly in 32-bit signed arithmetic.
   Because $c_k \in [0, 255]$ and $a_k \in [-128, 127]$, each term $c_k \cdot a_k \in [-32640, 32385]$. The pair sum in `vpmaddubsw` never overflows 16-bit signed integer limits for any format in Peregrine (verified: max sum for ternary is 508; for Q4_0 is $15 \times 127 \times 2 = 3810$; for Q8_0 is $127 \times 127 \times 2 = 32258 < 32767$). Thus, intermediate truncation never occurs in AVX2.
   Both instruction sequences yield **identical 32-bit integers** in all 8 lanes of the `__m256i` register.

2. **The Float Folding Boundary Rule**:
   Floating-point addition is non-associative. If an AVX-VNNI kernel accumulated across multiple blocks in 32-bit integers before converting to float, while AVX2 converted each 32-element block to float and accumulated with `vfmadd231ps`, the intermediate floating-point rounding would differ, causing logits and tokens to diverge.
   **Crucial Design Rule**: An AVX-VNNI kernel must convert integer accumulators to float at the exact same architectural boundary as the AVX2 kernel:
   - For `Q4_0`, `Q5_0`, `Q8_0`: convert to float every 32 elements (1 block), multiply by block scale $d \cdot d_{\text{act}}$, and fold into the float accumulator.
   - For K-quants (`Q4_K`, `Q5_K`, `Q6_K`): accumulate in integer across the 32-element sub-blocks of a super-block, and convert to float at the 256-element super-block boundary.
   - For `PQ2_0`: accumulate in integer across the 4 bit-planes of a 128-element group, subtract `tls`, and convert to float at the 128-element boundary.

Following this rule guarantees that AVX-VNNI produces **bitwise-identical logits and tokens** to AVX2 on every model.

### 3.4 Tier Architecture, `PEREGRINE_ISA`, and CI Testing

#### 1. Tier Hierarchy and Naming
In `crates/peregrine-kernels/src/cpu.rs`:
```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub enum Tier {
    Scalar,
    Avx2,
    AvxVnni,  // New tier between Avx2 and Avx512
    Avx512,
}
```

- **Tier Ordering**: `Scalar < Avx2 < AvxVnni < Avx512`.
- **Tier String**: `Tier::AvxVnni.as_str()` returns `"avx-vnni"`.
- **Tier Detection**:
  ```rust
  #[inline]
  pub fn have_avx_vnni() -> bool {
      #[cfg(target_arch = "x86_64")]
      {
          static ON: OnceLock<bool> = OnceLock::new();
          *ON.get_or_init(|| {
              crate::cpu_has!("avx2") && crate::cpu_has!("fma") && crate::cpu_has!("avxvnni")
          })
      }
      #[cfg(not(target_arch = "x86_64"))]
      false
  }
  ```
- **Tier Name String (`tier_name()`)**:
  On an Alder Lake machine or under SDE `-adl`, `tier_name()` will produce:
  `x86_64-avx2-vnni256`
  This separates it cleanly from AVX-512 VNNI (`x86_64-avx2-avx512-vnni-gfni-vbmi`).

#### 2. `PEREGRINE_ISA`
`PEREGRINE_ISA` allows capping instruction sets for testing and reproducibility:
- Accepted values: `scalar`, `avx2`, `avx-vnni` (or `avxvnni`), `avx512`.
- Setting `PEREGRINE_ISA=avx-vnni` on an AVX-512 machine masks off AVX-512 flags (`avx512f`, `avx512vl`, `avx512vnni`, `gfni`, `vbmi`), allowing AVX-512 hardware to run and test the AVX-VNNI tier natively without an emulator!

#### 3. Golden Directory Scheme
Golden tests (`crates/peregrine-models/tests/synthetic.rs:136-155`) locate goldens at:
`crates/peregrine-models/tests/golden/synthetic/<tier_name>/`
- Because AVX-VNNI integer accumulations match AVX2 bit for bit, all synthetic model outputs for `x86_64-avx2-vnni256` are identical to `x86_64-avx2`.
- Strategy: Golden regression tests check `x86_64-avx2-vnni256`. Rather than duplicating dozens of golden files in Git, `crates/peregrine-models/tests/synthetic.rs` will look for `<tier_name>`, and if absent for `x86_64-avx2-vnni256`, fallback to matching against `x86_64-avx2`. A dedicated test will assert that `x86_64-avx2-vnni256` and `x86_64-avx2` outputs match identically across every synthetic model.

#### 4. Testing in CI: Intel SDE `-adl`
Standard GitHub Actions runners (such as `ubuntu-latest` Azure VMs) run on either Intel Xeon (Cascade Lake/Ice Lake with AVX-512) or AMD EPYC (Zen 2/Zen 3 without VNNI). None present a CPUID with AVX-VNNI *without* AVX-512.
To test AVX-VNNI in CI:
1. **Native Testing via Cap**: On an AVX-512 runner (Intel Xeon or AMD Zen 4/5), run tests with `PEREGRINE_ISA=avx-vnni`. Because these CPUs support `avxvnni` instructions in hardware, they execute the 256-bit VEX `VPDPBUSD` instructions at full native speed with AVX-512 masked off.
2. **True Architectural Emulation with Intel SDE**:
   Download and cache Intel SDE in CI (`sde-external-*.tar.xz`), running:
   ```bash
   sde64 -adl -- cargo test -p peregrine-models --test synthetic
   ```
   Under `-adl`, SDE configures the synthetic CPU to match an Alder Lake Core i9-12900K: `avx2`, `fma`, `avxvnni` are active; `avx512*` and `gfni` are disabled. If any EVEX or AVX-512 instruction leaks into the AVX-VNNI kernel path, SDE immediately traps with an Illegal Instruction fault.

## 4. Startup Calibration

### 4.1 What Must Be Measured and the Budget

Peregrine's single-token decode latency is primarily bound by DRAM streaming read bandwidth ($B$), while multi-token prefill is bound by SIMD vector arithmetic intensity ($F$). Today, `EngineOptions` (`crates/peregrine-core/src/options.rs`) provides static defaults:
- `spin_us`: 1000 µs (`SPIN_DEFAULT_US`)
- `yield_us`: 0 µs
- `decode_threads`: `physical_cores()` or all threads

However, optimal values vary drastically across hardware:
- On desktop dual-channel DDR5 (Intel Alder Lake / AMD Zen 4), DRAM bandwidth saturates at 4 to 6 threads. Running 16 threads during single-row decode wastes core energy and incurs barrier synchronization jitter.
- On client hybrid CPUs (Alder Lake 8P+8E), worker threads placed on Gracemont E-cores run slower than P-cores, stalling the fork-join barrier.
- In virtualized or container environments (WSL2, Docker, cloud VMs), condvar thread wake-ups take 30–60 µs instead of 5–10 µs, demanding longer spin windows to avoid throughput collapse.

#### Calibration Targets
1. **Decode Thread Count (`decode_threads`)**: The thread count $T_{\text{dec}} \in [1, N_{\text{phys}}]$ that maximizes single-row matmul streaming bandwidth.
2. **Prefill Thread Count (`prefill_threads`)**: The thread count $T_{\text{pref}} \in [1, N_{\text{logical}}]$ that maximizes batched matrix multiplication FLOPs.
3. **Spin Window (`spin_us`)**: The minimum spin duration before parking that prevents condvar wake-up penalties during back-to-back layer transitions.

#### Latency Budget: < 250 ms
Startup calibration must not introduce perceptible latency when launching the CLI or starting the server.
- Existing comparison: `Machine::probe` (`crates/peregrine-core/src/telem.rs:96-101`) measures bandwidth and flops in **80–146 ms**.
- Target calibration budget: **$\le$ 200 ms** (hard timeout at 300 ms). If calibration exceeds this budget, it aborts immediately and adopts safe defaults.

```
+-----------------------------------------------------------------------------------+
|                        STARTUP CALIBRATION BUDGET (<200 ms)                       |
+--------------------------+------------------------------+-------------------------+
| Phase 1: Ridge Probe     | Phase 2: Decode Thread Sweep | Phase 3: Spin Window    |
| (Memory & FPU)           | (1, 2, 4, 8, N_phys)         | (Round-trip Barrier)    |
| Duration: ~60 ms         | Duration: ~80 ms             | Duration: ~30 ms        |
+--------------------------+------------------------------+-------------------------+
```

### 4.2 Invariant: Bit-Identity Across Thread Counts

**Claim**: Calibrating thread count changes throughput and latency, but never changes the generated tokens or logits.
**Verification in Code**:
In `crates/peregrine-models/tests/synthetic.rs:120-135`:
```rust
fn check_model(model: Model, name: &str) -> Option<String> {
    let a = run(&model, 4);
    if run(&model, 4) != a {
        return Some(format!("{name}: two runs differ"));
    }
    for t in [1, 2] {
        if run(&model, t) != a {
            return Some(format!("{name}: {t} threads differ from 4"));
        }
    }
    ...
```
`check_model` explicitly asserts that the model's forward pass produces bit-identical logits and greedy token selections across 1, 2, and 4 threads.

**Why this holds**:
1. Output rows of each weight matrix are statically partitioned into disjoint index slices (`crates/peregrine-core/src/pool.rs:397-401` `share(total, w, n)`).
2. Each worker computes its assigned output rows independently without cross-worker communication or reduction.
3. Attention reductions and SwiGLU non-linearities are strictly row-wise.
4. MoE expert outputs accumulate in deterministic slot order (`docs/design/moe.md:48-52`).

Because arithmetic operations are not re-ordered across thread boundaries, varying the thread count has **zero impact on numerical results**.

### 4.3 Relationship to `peregrine tune` Profiles

`peregrine tune` (roadmap S1.7, `crates/peregrine/src/tune.rs`) conducts an offline coordinate search over `TUNABLE` parameters (`decode_threads`, `spin_us`, `yield_us`, `prefetch_bytes`) across multiple iterations over 60 seconds, recording results to `$XDG_CONFIG_HOME/peregrine/profiles/<model>-<fnv>.profile`.

#### Recommendation: Calibration is the Fallback when No Profile Exists
Startup calibration must **serve as the automatic runtime fallback** when no tuning profile is available, rather than replacing `peregrine tune`.

| Dimension | Startup Calibration (S2.6) | Offline Profile (`peregrine tune`) |
|---|---|---|
| **Execution Time** | < 200 ms at engine startup | 60+ seconds (offline CLI tool) |
| **Model Awareness** | Synthetic buffers (dimension-agnostic) | Real model weights and real token context |
| **Search Space** | Coarse 1D sweep (threads, barrier ping-pong) | Multi-round coordinate descent over full Cartesian product |
| **Persistence** | In-memory only (ephemeral per process) | Persistent on disk, keyed by CPU & model FNV-1a hash |
| **Target User** | Zero-config out-of-the-box CLI & server users | Production deployments maximizing throughput |

#### Hierarchy of Configuration Precedence:
1. **Explicit Environment / CLI Flags** (`PEREGRINE_DECODE_THREADS`, `PEREGRINE_SPIN_US`, `--opt ...`) [Highest]
2. **Tuned Profile** (`<model>-<fnv>.profile` written by `peregrine tune`)
3. **Startup Calibration** (Measured dynamically in <200 ms on uncalibrated machines)
4. **Static Defaults** (`physical_cores()`, `SPIN_DEFAULT_US = 1000`) [Lowest]

This preserves reproducibility: benchmark scripts and automated deployments can pin options explicitly or supply tuned profiles, while ad-hoc users benefit from machine-calibrated settings automatically.

---

### 4.4 Mitigating Noise and Over-subscription

Running a micro-benchmark at startup on a shared or busy machine introduces noise:
- A temporary CPU spike from another process during the 4-thread probe could make 4 threads appear slower than 2 threads.
- In hyper-threaded environments, background tasks may cause high variance.

#### Calibration Robustness Protocol
1. **Micro-burst Median Filtering**:
   Each candidate setting runs 3 micro-bursts of 500 µs each. The calibration takes the median, dropping the highest outlier.
2. **Variance / Noise Detection**:
   If the coefficient of variation ($CV = \frac{\sigma}{\mu}$) across repetitions exceeds 15%, the machine is deemed noisy/busy. Calibration immediately aborts and falls back to safe architectural defaults (`physical_cores()` and 1000 µs spin).
3. **Monotonicity Guardrails**:
   - Bandwidth vs. Thread Count: $T_{\text{dec}}$ starts at 1 and increases powers of two (1, 2, 4, 8) up to $N_{\text{phys}}$. A higher thread count is selected only if it yields at least **$\ge$ 5% higher bandwidth** than the previous count. If bandwidth plateaus or regresses, the sweep stops immediately (early exit).
   - $T_{\text{dec}}$ is never allowed to exceed physical cores $N_{\text{phys}}$ (SMT cores never improve memory-bound single-row decode).
   - $T_{\text{pref}}$ is capped at logical cores $N_{\text{logical}}$.

## 6. Open Questions for the Orchestrator

1. **Tier Directory vs Symlink for Golden Outputs**:
   Because `x86_64-avx2-vnni256` is mathematically bit-identical to `x86_64-avx2`, should we commit duplicate `.golden` files to `tests/golden/synthetic/x86_64-avx2-vnni256/`, or allow `synthetic.rs` to alias `x86_64-avx2-vnni256` directly to the `x86_64-avx2` directory?
   *Recommendation*: Allow `synthetic.rs` to fall back to `x86_64-avx2` when testing AVX-VNNI, keeping repository size lean while maintaining a strict equality test between the two tiers.

2. **SDE `-adl` CI Cadence**:
   Running the complete synthetic test suite under Intel SDE emulation takes ~3–4 minutes per run due to dynamic binary translation overhead. Should `sde64 -adl` run on every PR modifying `crates/peregrine-kernels`, or as a nightly / merge-queue release check?
   *Recommendation*: Run SDE `-adl` on PRs touching `crates/peregrine-kernels/` or `crates/peregrine-core/src/cpu.rs` only, skipping it for docs/facade/models PRs.

3. **Placement of Calibrated Decode Pool vs Prefill Pool**:
   Today `narrow_pool` (`crates/peregrine-core/src/pool.rs:390`) optionally creates a narrower pool for single-row decode steps. Should calibration create two distinct static pools (`decode_pool` with $T_{\text{dec}}$ workers and `prefill_pool` with $T_{\text{pref}}$ workers), or dynamically activate a subset of workers on a single pool?
   *Recommendation*: Keep two pools as `pool.rs` does today (`narrow_pool` for decode, main pool for prefill). Workers in the idle pool park on their condvar after their spin window, costing zero CPU cycles.

4. **Spin Window Calibration Methodology**:
   Should `spin_us` calibration probe barrier round-trip latency against OS thread sleep, or rely on a formula based on measured system context-switch penalty?
   *Recommendation*: Measure 50 back-to-back fork-join cycles across the thread pool with 0 µs spin (forcing condvar sleep) to measure actual kernel wake-up latency ($L_{\text{wake}}$), and set `spin_us` to $2 \times L_{\text{wake}}$ (clamped between 50 µs and 2000 µs).

## Decisions (orchestrator review)

1. **Goldens for the VNNI-256 tier:** no separate directory. `synthetic.rs` reads the `x86_64-avx2` goldens for
   `x86_64-avx2-vnni256`, so every VNNI run is checked against AVX2's files, which is the bit-identity claim itself.
   Under `PEREGRINE_GOLDEN=require` that alias counts as present.
2. **SDE `-adl`:** a CI job on every PR, beside the existing `-spr` job; at 3–4 minutes in parallel it costs no
   wall time. Path filters drift as the code moves, so none are used.
3. **Pools:** two pools, as `pool.rs` does today with the narrow decode pool.
4. **Spin window:** measured: back-to-back fork-join cycles with no spin give the wake-up latency, and `spin_us`
   is twice that, clamped to 50–2000 µs.
5. **To check in PR 1:** the sign trick's edge case. A Q8_0 weight of −128 makes `sign_epi8(w, w)` give 128, and
   with an activation of −128 a `vpmaddubsw` pair reaches 128·128·2 = 32768, one past `i16::MAX`. Confirm the
   activation quantiser clamps to ±127, or that weights never hold −128, and pin it with a test, before
   claiming VNNI and AVX2 agree bit for bit.
6. **Calibration** runs only when no `peregrine tune` profile matches. It can be switched off
   (`PEREGRINE_CALIBRATE=0`, through `EngineOptions`), and its result is printed and reported like any option, so
   a benchmark records what it ran with.
