# S5.1, the wide pass: as built

- Status: built and measured, no result moved
- Date: 2026-11-12
- Host: AMD Ryzen AI 9 HX 370 (Zen 5, 12 cores / 24 threads, AVX-512 F/BW/VL/VNNI/VBMI), WSL2
- Baseline for this change: `s5.1-q6k-zmm` (S5.1's PR 2)
- Raw measurements: `benchmarks/results/desktop-zen5-2026-11-11-s5.1-wide-pass/`

Item 3 of `docs/design/s5-prefill-avx512.md` §6. The matmul's write-out was a transposed scatter,
so a wider pass cost the 1B 8 % at twelve threads and 30 % at one (measured in the study), and
`PEREGRINE_PREFILL_CHUNK` could not be raised without paying for it. The other two "as built"
notes are `s5.1-kq-epilogue.md` and `s5.1-q6k-zmm.md`.

---

## 1. What was built

Nothing allocates and no result moved; only the order of the stores changed.

The kernels write a tile as `blk[i · nb + b]` — row `i` of the tile, activation `b`. The output is
the other way round, `out[(b0 + b) · rows + row]`, and the old loop walked it row-first:

```rust
for i in 0..KQ_TILE_ROWS { for b in 0..nb { out.set((b0 + b) * rows + row, blk[b * 8 + i]) } }
```

For one tile that is `8 · nb` single-float stores, each `rows` floats from the next (32 KiB on the
1B at chunk 128), so every store is its own cache line and a wide pass touches a new line per
element. Turned around, the same data is contiguous: for one activation, the tile's eight rows are
eight consecutive floats in the tile block *and* eight consecutive floats in the output. The new
`untile` helper copies each activation's rows as one slice (`copy_from_slice`, 32 bytes per
activation for a k-quant tile), so a tile is `nb` copies instead of `8 · nb` scattered stores, and
the tile block stays in L1.

A repacked tile's block is activation-major (`blk[b · 8 + i]`), which is what makes the copy
possible. The packed-float panel path (`MatPath::Tiles`) and the two per-row paths (`RowsPq2`,
`RowsPtq1`) build their blocks row-major (`blk[i · nb + b]`), so their output would need a real
transpose rather than a copy; they keep the scatter and are the next step, not this one. The rows
a worker owns can start or end inside a tile, so `untile` copies only the sub-range the worker
owns — the same rows the scatter wrote.

`crates/peregrine-models/tests/prefill_chunk.rs` passes unchanged: the chunk is how a prompt is
read, not what it produces.

## 2. Prefill against chunk, before and after

`peregrine bench --prompt-tokens 512 --tokens 0 --no-profile` with `PEREGRINE_PREFILL_CHUNK` set,
interleaved old/new rounds, medians; prompt tok/s. Host load average was 10–28 through these
series (the agent's own UI), so the ratios are the quantity to read.

Twelve threads, 3 rounds:

| model | chunk | before | after | ratio |
|---|---|---|---|---|
| Qwen 2.5 0.5B | 16 | 520.9 | 536.0 | 1.029 |
| Qwen 2.5 0.5B | 32 | 566.2 | 595.1 | 1.051 |
| Qwen 2.5 0.5B | 64 | 586.8 | 636.8 | 1.085 |
| Qwen 2.5 0.5B | 128 | 605.6 | **618.1** | 1.021 |
| Llama 3.2 1B | 16 | 294.5 | 324.6 | 1.102 |
| Llama 3.2 1B | 32 | 298.9 | 346.0 | 1.158 |
| Llama 3.2 1B | 64 | 285.8 | 341.4 | 1.194 |
| Llama 3.2 1B | 128 | 266.2 | **347.7** | **1.306** |

One thread, 1 round (the series is long at one thread; the ratios are consistent with an earlier
two-round run of the same change):

| model | chunk | before | after | ratio |
|---|---|---|---|---|
| Qwen 2.5 0.5B | 16 | 99.3 | 101.9 | 1.026 |
| Qwen 2.5 0.5B | 32 | 101.6 | 106.3 | 1.047 |
| Qwen 2.5 0.5B | 64 | 104.6 | 109.1 | 1.043 |
| Qwen 2.5 0.5B | 128 | 95.8 | 105.5 | 1.101 |
| Llama 3.2 1B | 16 | 50.0 | 52.1 | 1.043 |
| Llama 3.2 1B | 32 | 44.2 | 51.9 | 1.173 |
| Llama 3.2 1B | 64 | 35.7 | **56.1** | **1.570** |
| Llama 3.2 1B | 128 | 35.0 | 50.1 | 1.431 |

The goal was "a wider pass is never slower than a narrow one", and it now holds at both thread
counts for both models. The 1B at twelve threads: 347.7 at chunk 128 against 324.6 at 16, where
before 128 was the *worst* (266.2 against 294.5). The 1B at one thread: 56.1 at 64 and 50.1 at 128
against 52.1 at 16, where before both were about 30 % slower than 16. Qwen's curve was already
rising with the chunk and rises further.

## 3. The default chunk on this tier

**Left at 16** (`PREFILL_CHUNK_DEFAULT`), against what the throughput numbers alone would say.

- For throughput at twelve threads — the tier's default pool — chunk 64 is the best for Qwen
  (636.8 against 536.0 at 16, +19 %) and chunk 128 for the 1B (347.7 against 324.6, +7 %); at one
  thread chunk 64 is the best for both (Qwen 109.1 against 101.9, 1B 56.1 against 52.1).
- The default also decides what a user who is *decoding* waits for while another user's prompt is
  processed: a mixed step reads one chunk per pass, so chunk 16 is a 16-token slice of someone
  else's prompt between decode rows and chunk 64 is four times that. The reason 16 was chosen
  (`options.rs`) was that trade, checked on another machine with a 1B that preferred 16 by 7.5 %.
  That reason is gone for the 1B at twelve threads, but the fairness half of it was **not measured
  here**: this change measured prefill alone, with no decoding user beside it.
- So the honest statement is: chunk 64 is what this tier should use for throughput, and 16 is kept
  as the default only because the mixed decode-and-prefill latency that the default protects was
  not measured in this change. Re-tuning it needs a mixed run (a decoder's inter-token latency while
  a 512-token prompt is prefilled), not another single-user prefill sweep. `PEREGRINE_PREFILL_CHUNK=64`
  gives the throughput today.

What was checked for exactly that purpose: `prefill_chunk.rs` in both its synthetic and real-model
forms (the cache, the logits, the tokens and the engine's tokens are identical at 16, 32, 64 and
128), and that the change does not touch what a decode step computes — the write-out change is the
order of copies into the same buffer, and the decode path's own step is unchanged.

## 4. Bits

No golden moved and nothing allocates in the pass: `untile` copies from a stack block into slices
of the output buffer the caller already owns, and the `no_alloc` tests pass. Goldens pass
unchanged on `x86_64-avx2-avx512-vnni-gfni-vbmi`, `x86_64-avx2` and `x86_64` (scalar) for Llama
3.2 1B, Qwen 2.5 0.5B and Gemma 3 1B.
