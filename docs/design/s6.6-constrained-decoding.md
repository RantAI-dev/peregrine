# S6.6a: constrained decoding, `response_format` JSON mode and JSON schema

**Status:** adopted. This is the "a" half of S6.6. The "b" half — forcing a tool call
with `tool_choice: "required"` or a named tool — is the project lead's wiring on top of
the public combinators described in §8.

## 1. Where it lives

A new module, `crates/peregrine-core/src/constrain/`, pure Rust with no dependency and no
`unsafe`:

| file | what it is |
| --- | --- |
| `schema.rs` | the JSON Schema subset → an internal grammar (an instruction arena) |
| `matcher.rs` | an incremental byte-level recogniser: given the bytes written so far, which bytes may come next, and may the reply end here |
| `mask.rs` | the token masks: the byte trie of a vocabulary, per-state allowed token ids, per-token string fast-path flags |

The forward pass is **not touched**. Logits are bit-for-bit what they were; the constraint
is a mask applied between the logits and the existing sampler. A request without a
constraint takes exactly the code path it took before (the extra work is one `Option::is_none`
per sampled row, and the slot struct has one more `Option` field).

## 2. The grammar

JSON is RFC 8259. The schema compiles to a byte-level pushdown automaton whose state is a
*set of stacks* of items (a nondeterministic pushdown automaton, as in llama.cpp's
`llama-grammar.cpp`, but over a JSON-specific small instruction set). Nondeterminism is
needed for overlapping prefixes (`anyOf`), for optional properties (a later required
property can force an earlier optional one to be skipped), and for a number or a repeated
constraint that can end or continue on the same byte.

### Supported keywords

`type` (`object`, `array`, `string`, `number`, `integer`, `boolean`, `null`, and a list of
types), `properties`, `required`, `additionalProperties` (`false`, `true` or a schema;
default `true`, as JSON Schema says), `items`, `prefixItems`, `minItems`, `maxItems`,
`enum`, `const`, `anyOf`, `oneOf` (treated as `anyOf`), `allOf` only of one element or of
unambiguous pure-`$ref`/object merges, `$ref` to a local pointer (`#`, `#/$defs/...`,
`#/definitions/...`; recursion is allowed), `minLength`, `maxLength`,
`minimum`/`maximum`/`exclusiveMinimum`/`exclusiveMaximum` for integers only when both
bounds make a finite set of at most 1 000 values, or when the single bound is a sign
constraint (`minimum: 0`, `maximum: 0`, and the exclusive spellings that mean the same),
`description`, `title`, `default`, `examples` (ignored), and the annotation keys
`$schema`, `$id`, `$comment`, `$defs`, `definitions`, `deprecated`, `readOnly`,
`writeOnly` (ignored).

`"strict": true` on the enclosing `json_schema` means what OpenAI defines: the object's
`additionalProperties` is treated as `false` and every declared property is required.

### Refused, never silently ignored

Every keyword that is not on the list above is refused with a 400 that names the keyword
and the JSON pointer at which it appears, for example:

```
unsupported JSON Schema keyword "pattern" at #/properties/name:
  it would restrict the reply and this backend cannot honour it
```

That includes `pattern`, `format`, `patternProperties`, `dependentRequired`, `if`/`then`,
`not`, `uniqueItems`, `multipleOf`, `minProperties`, `maxProperties`, `contains`,
`propertyNames`, `unevaluatedProperties`, `minContains`, and any other unknown key. A
schema whose `type` is absent while `properties`, `items`, `minLength`, bounds, … are
present is refused naming `type`: those keywords constrain only one JSON type, and
inferring the type would silently change the language.

`enum` and `const` are emitted as exact JSON text. They may be combined with `type` (the
values are filtered against it) but with no other restricting keyword; combining them with
`minLength` or `pattern` is refused, because a value could then be emitted that the
keyword forbids.

### Property order

An object's declared properties are emitted in the order of the schema's `properties`
object. Required properties must appear; an optional property may be skipped, but only if
no later required property forces it out (the object's stack chooses the smallest
not-yet-emitted property, and may skip optional ones up to and including the next
required one). Additional properties, where allowed, come after the declared ones. This is
what OpenAI's structured outputs do and it keeps the automaton small. Duplicate keys are
not emitted by choice but are not forbidden by RFC 8259; the matcher's corpus tests follow
the RFC here.

`json_object` is the schema `{"type": "object"}`: any JSON object, keys in any order.

## 3. Whitespace

Whitespace is bounded, following llama.cpp v0.9.0
(`common/json-schema-to-grammar.cpp:229`):

```
SPACE_RULE = | " " | "\n"{1,2} [ \t]{0,20}
```

i.e. nothing, a single space, or one or two newlines followed by at most twenty spaces or
tabs. It is allowed exactly where JSON allows it: after `{`, `[`, `,`, `:` and before `}`,
`]`; never before the first byte of the reply; after the top-level value closes only the
end tokens of §5 are allowed. This is what stops a model from looping on whitespace: the
longest run is 22 bytes, and a whitespace byte is a byte the automaton counts.

## 4. Strings

Only valid UTF-8. The matcher tracks a multi-byte sequence across token boundaries: a
token may end after the first byte of a three-byte character, and the next token may finish
it. Overlong forms, UTF-16 surrogates in raw UTF-8 (`ED A0 80`), code points above
`U+10FFFF`, and continuation bytes without a lead byte are rejected at the byte that makes
the sequence invalid.

Control characters (`U+0000`–`U+001F`) must be escaped. The escapes are JSON's
(`\" \\ \/ \b \f \n \r \t \uXXXX`). `\uXXXX` is checked for surrogates: a high surrogate
must be followed by `\uDC00`–`\uDFFF`, a lone surrogate is not allowed, and the pair counts
as one character. `minLength`/`maxLength` are counted in characters, not bytes, and a
string may only close when the count satisfies them.

## 5. Ending

The end-of-reply tokens are the slot's stop tokens (`app.stop` on the server: the chat
template's own end-of-turn ids plus the tokenizer's EOS). They are allowed only when the
matcher can finish. When the top-level value has closed (the stack is empty), **only** end
tokens are allowed, so the reply ends exactly there.

A number or a repeated constraint at the end of a reply is a slightly different case: while
it is accepting, both its next byte and an end token are allowed, exactly as RFC 8259
allows `12` to end after `1` or continue to `120`. Only a structurally closed value (an
object after `}`, an array after `]`, a string after its quote, a literal after its last
byte) removes the content bytes, which is what rule 5 is about.

`max_tokens` can still cut a reply short. It finishes with `finish_reason: "length"` and
the text is then an incomplete prefix of a valid document, exactly as OpenAI documents for
JSON mode.

## 6. The mask

`mask::Vocabulary` precomputes, once per model vocabulary and lazily on the first
constrained request:

* the detokenised bytes of every token (`Tokenizer::token_bytes`, the same bytes the
  decode loop appends to the reply through `Utf8Stream`), except special/control tokens
  and empty tokens;
* a byte trie over those tokens;
* per-token flags for the common string state: a token all of whose characters are plain
  string content (valid UTF-8, none below `U+0020`, none `"` or `\`), with its character
  count, and a second trie over the remaining ("boundary") tokens.

Per step, for one matcher state:

* if the top-level value has closed, the mask is the end tokens;
* if the state is "inside a plain string", the mask is the precomputed plain-token set
  filtered by the remaining `maxLength`, plus a walk of the small boundary trie (the tokens
  that can close the string or write an escape). The whole vocabulary is not walked;
* otherwise the trie is walked with a copy of the matcher state, and a branch is pruned at
  the first byte the matcher rejects. A leaf is an allowed token when its bytes leave a
  non-empty matcher state.

Masks are cached per (constraint instance, slot) by the structural key of the matcher
state, in a 256-entry LRU. The states that repeat — "inside a string", "after a number",
"between object members" — are hits after their first token. The state is cheap to clone
and hash: a sorted vector of stacks of small `Copy` items.

Budget, measured with the real vocabularies (`benchmarks/results/shiro-2026-11-12-s6.6a/`):
the median mask call is **143–169 µs**, which is 0.3–0.7 % of a 4-thread decode step on
Qwen 2.5 0.5B (24 ms) and Llama 3.2 1B (44 ms); the warm p99 is 0.55–5.55 ms and the warm
worst 0.57–6.06 ms. The tail is the first request that reaches a new bounded-string length
or a new parent state; the memo holds those after they occur. The **cold first request**
pays the tries' first touch: its median was 48–90 µs and its worst 3.0–7.4 ms on this
shared host (load 2.5–6.4 on 8 vCPUs), most of it page faults on a 22 MB trie. Building the
vocabulary (151 936 / 128 256 tokens: token bytes, classification, three byte tries) took
a median of 221 ms / 187 ms there, and 148 ms when the host was not saturated; it is
one-time and happens on the first constrained request. The vocabulary is held by the
engine, so later requests reuse it.

## 7. Sampling

The allowed set is applied as `-inf` on every other logit, on a copy of the row, and then
the existing sampler chain runs unchanged: temperature 0 is the argmax of the masked row;
temperature + top-k/top-p/min-p operate on the masked distribution; repetition penalties
are applied first, as today. The raw logits row is not edited, so another row of the same
batch, the prefix store and `logprob_of` see exactly what they saw before.

If the allowed set is empty — which cannot happen if the matcher and trie are right — the
slot fails with `Finish::Error` and the request is answered with a 500 saying so. An
unconstrained token is never emitted.

## 8. Interplay

* **Speculation.** A constrained slot does not use the engine's MTP block and does not
  attach a drafter: a draft would have to be verified against a sampler whose allowed set
  changes with every accepted token, and turning it off is the simple, lossless rule. A
  slot in the same batch that has no constraint still speculates as before. A row's bits
  never depend on the batch: the mask is a function of the slot's matcher state only.
* **Streaming.** Unchanged: chunks are still text deltas. The bytes are the same bytes the
  non-streamed reply is built from.
* **Reasoning models.** The constraint applies to the assistant's content, not to a
  reasoning span. When the server knows the reply opens in reasoning — the template opens
  a thinking block and `thinking` is on, or the model has a `<think>` token and thinking is
  on — `response_format` is refused with a 400: "response_format is not supported while
  the model is thinking; send the request with thinking off". Starting the constraint at
  the first content byte would need to know, inside the engine, when the server's reasoning
  parser has closed the span; the server tracks that (`Run::in_think`) but the engine's
  sampler only has the slot config. Refusing is correct and honest; joining the two is a
  later change.
* **`max_tokens`** still cuts the reply short (see §5).

## 9. API (server and CLI)

`response_format` on `POST /v1/chat/completions`:

* `{"type": "text"}` — today's path;
* `{"type": "json_object"}` — any JSON object;
* `{"type": "json_schema", "json_schema": {"name": "…", "schema": {…}, "strict": true}}` —
  the schema subset above. `strict` defaults to false.

Errors are OpenAI-shaped 400s with `type: "invalid_request_error"` and
`param: "response_format"`. A request with both `tools` and `response_format` answers
`400 response_format with tools is not supported yet`; the project lead joins the two in
S6.6b. An unconstrained request on the same server is unaffected.

CLI (`peregrine run`): `--json-schema <FILE>` and `--json-object` (`--json` already means
"print one JSON object of timings"). A constrained CLI run on a reasoning model with
thinking on is refused with the same message.

## 10. Public combinators (S6.6b's API)

The project lead's tool wiring builds a constraint from parts and alternatives:

```rust
use peregrine_core::constrain::{Constraint, Part, Schema};

// <|call|>{"name":"weather","arguments":{…}}<|end|>
let c = Constraint::sequence(vec![
    Part::Literal("<<A>>".into()),
    Part::Json(Schema::new(schema)),
    Part::Literal("<<B>>".into()),
]);

// one of several call shapes
let c = Constraint::any_of(vec![call_a, call_b]);

// several calls in one reply (max: Option<usize>, None = unbounded)
let c = Constraint::repeat(call_a, 1, Some(3));
```

Literals are matched byte-exactly. `repeat` refuses a nullable inner constraint (the
automaton would loop without consuming a byte). A constraint is attached to a generation
request by putting it in `SlotCfg::constraint` — the same path `response_format` uses; the
server's `Plan` builds one and `generate` hands it to the engine.

## 11. Tests and measurements

* The matcher accepts every document of a hand-written corpus (deep nesting, every escape,
  surrogate pairs, the number grammar's edges `-0`, `1e-10`, `0.0`, big integers) and
  rejects the classic invalid documents at the right byte.
* Forty-plus schemas covering every supported keyword are checked byte by byte: every
  prefix of a valid instance is accepted as a prefix, the full instance is accepting, an
  invalid instance is rejected at the byte that makes it invalid.
* A random-model property test: seeded random logits, a synthetic vocabulary of single
  bytes, multi-byte tokens, tokens spanning structural characters and tokens ending
  mid-UTF-8, 2 000 runs per schema over 20+ schemas. Every completed reply is parsed and
  validated by an independent validator written in the test support code (it shares no
  code with the matcher). The step count is bounded and whitespace is bounded, so "stuck"
  is a failure. Failing seeds are kept as regressions.
* Mask equivalence: for random matcher states, the trie-walk mask equals the brute-force
  mask (every token tried on a cloned matcher).
* Server: `response_format` cases on a synthetic model through `common::start`.
* No golden moves; the unconstrained decode speed is measured before and after.

The measurements live in `benchmarks/results/<host>-<date>-s6.6a/`.
